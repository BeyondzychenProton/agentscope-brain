# 会议预订

把一句口语化的会议需求，走完「消歧 → 收槽位 → 查忙闲 → 选会议室 → 确认卡 → 落库 → 验证」七个环节，最后给用户一张结果卡。

核心原则：**读操作可以自动跑，写操作必须人确认。** 任何一步的事实（会议室、时间、人名）都必须来自工具返回，不许靠猜或靠训练记忆补全。

## 红线（Hard rules）

违反任意一条即为失败执行：

1. **同名未消歧，禁止调写工具。** 「萤火虫/郁金香/向日葵/满天星/蒲公英」在会议室与系统之间歧义未消除时，禁止调用任何 `office.room_*` 工具。
2. **写前必须有确认卡，且必须收到明确肯定答复。** 「嗯」「好」「可以」「确认」「就这个」算肯定；「再说吧」「改一下 X」不算。
3. **多匹配人名不许自动选。** 同名多人时列候选让用户点选。
4. **只读忙闲，不外泄日程详情。** 不得向用户转述他人会议主题、参会名单、地点等具体内容，只回答「忙/闲」。
5. **不编造工具返回值。** 工具没返回的会议室、容量、设备、空闲时段，一律视为未知，要么再查一次，要么如实说「查不到」。

## 流程

### Step 1 · 实体消歧（最先做，不是最后做）

用户话里出现五个同名实体之一时，先判定指向。判定顺序见 `references/room-directory.md`：

1. 上下文出现「开会 / 会议室 / 预订 / 楼层 / 16F·17F·18F / 容纳 N 人 / 投屏 / 场地」→ 会议室。
2. 上下文出现「系统 / 平台 / 登录 / OA / 流程 / 审批 / 故障 / 账号 / 密码 / 项目管理 / 运营 / 安全」→ 系统，**本 Skill 不介入**。
3. 两条都不满足（例如只说「帮我去郁金香」）→ 必须提问：「您是指预订 17F 的郁金香会议室，还是登录郁金香商务管理平台？」用户回答前不得往下走。

### Step 2 · 抽取槽位

| 槽位 | 说明 | 必填 | 默认 |
| --- | --- | --- | --- |
| `subject` | 会议主题 | 是 | 无，缺失必问 |
| `participants` | 参会人（姓名 / 部门） | 是 | 至少含发起者本人 |
| `start_time` | 开始时间 | 是 | 见 Step 3 取整规则 |
| `duration_minutes` | 时长 | 是 | 30（用了默认值必须告知） |
| `location` | 会议室 | 是 | 无，由 `office.room_recommend` 推荐 |
| `equipment` | 投屏 / 视频会议 / 白板 | 否 | 无 |
| `description` | 会议说明 | 否 | 无 |
| `attachment` | 会议资料 | 否 | 无 |

时间口语映射：上午 = 09:00–12:00，下午 = 13:00–18:00，下班前 = 17:00–18:00。「下周三」「明天」等相对时间必须用系统当前时间换算成绝对日期，禁止凭空推断年份。

周期会议（「每天」「每周三」）首期不支持：明确告知，并询问是否先建单场。

### Step 3 · 补齐缺失（一次问完）

- `start_time` 缺失：以用户时区当前时间为基准，向上取整到 5 分钟粒度（15:33 → 15:35，15:36 → 15:40，已对齐则不变），把取整结果作为默认值**告知用户**，而不是默默采用。
- `duration_minutes` 缺失：默认 30 分钟并告知。
- 一次提问最多 2–3 个关键问题，禁止挤牙膏式连环追问；用结构化提问卡片呈现选项，别让用户打大段字。
- 用户说「时间你定」→ 按 Step 5 的候选优先级自动选最优时间，但仍要在确认卡里说明为什么选它。

### Step 4 · 解析人名

调用 `office.attendee_resolve`（契约见 `references/tool-contract.md`），三分支：

| 结果 | 动作 |
| --- | --- |
| 唯一匹配 | 直接使用，确认卡中带部门展示（例：张伟（销售部））供核对 |
| 多匹配 | 列候选（姓名 + 部门），用户点选，绝不自动猜 |
| 无匹配 | 告知并请用户确认姓名或改用邮箱 |

- 部门表达（「拉上市场拓展部」）→ 解析为该部门负责人，并提示可指定具体成员，避免一次拉进几十人。
- 外部邮箱：暂不支持自动邀请，明确提示并给出手动添加指引。

### Step 5 · 查忙闲与选时间

按序调用：

1. `office.attendee_resolve` → 参会人身份、部门
2. `office.calendar_freebusy` → 忙闲布尔（15 人一批）
3. `office.calendar_find_slots` → 共同空闲时段

冲突处理（工具无 `find_slots` 时，用 `freebusy` 结果本地求交集）：

| 情况 | 动作 |
| --- | --- |
| A · 全员在目标时段空闲 | 直接进入选会议室 |
| B · 部分人忙但有其他共同空闲 | 给 2–3 个候选，按「最接近原要求 > 全员空闲 > 避开 11:30–13:00 午休、17:00 后、周末与节假日」排序，**让用户选，不替用户决定** |
| C · 当天完全无共同空闲 | 先扩到 ±1 天，再 ±3 天；仍无则如实报告并请用户手动指定时间 |
| D · 关键人忙 | 用户明确某人必须到场 → 优先保留其时间；未明确 → 问清谁可以缺席或改期 |

### Step 6 · 选会议室

调用 `office.room_recommend`（人数 + 时段 + 设备）。找不到合适会议室时，优先建议调整时间或放宽楼层/设备条件，不要硬塞一个容量不足的房间。

### Step 7 · 确认卡 + 写操作

确认卡必须包含：主题、开始时间、时长、地点（会议室名 + 楼层）、参会人（带部门）。示例：

> 建议：2026-10-17（下周三）15:30–16:30
> 地点：17F 郁金香会议室（20 人）
> 参会人：张三（产品部）、李四（研发部）
> 主题：产品评审会
> 是否创建会议？

收到肯定答复后调用 `office.room_book`（带幂等键），再调用 `office.booking_verify` 验证：日历事件存在、会议室确实被占、参会人无冲突。**三项全过才能回报「预订成功」**，否则如实说明失败原因。

### Step 8 · 结果卡

按 booked / failed / pending_approval / cancelled 四态输出，附会议号与「取消 / 改期」入口。

## 取消与改期

1. 先定位目标会议（时间 + 主题 + 参会人，不确定就列候选让用户选）。
2. 判断归属：操作**他人创建**的会议 → 必须走人工审批，本 Skill 只能提交申请，不得直接落库。
3. 改期 = 取消 + 新建，但必须先向用户展示新时段并确认，不能在同一轮里静默执行两步写操作。
4. 取消后调用 `office.booking_verify` 确认会议室已释放。

## 状态机

`draft → gathering → awaiting_confirm → booking → booked`，异常分支 `expired`（确认超时）/ `failed`（写失败）/ `cancelled`。

- `awaiting_confirm` 超时未响应 → 转 `expired`，不自动提交。
- `booking` 中途失败 → 转 `failed`，必须回滚已占用的会议室。
- 每次状态迁移写 booking_log，并携带 trace_id 便于回放。

## 失败兜底

| 场景 | 处理 |
| --- | --- |
| 会议室被占 | 推荐备选，或让用户选 |
| 参会人冲突 | 给候选时段，或异步询问参会人 |
| 工具调用失败 | 重试 1 次（仅对幂等读操作）；写操作重试前必须先查状态确认未重复创建，仍失败则转人工 |
| 超时未确认 | 转 `expired`，告知需重新发起 |

## 安全与审计

- 单次最多邀请 20 人。
- 所有写操作二次确认。
- 模型调用、工具调用、审批、成本全链路可审计可回放（trace_id 贯穿）。
