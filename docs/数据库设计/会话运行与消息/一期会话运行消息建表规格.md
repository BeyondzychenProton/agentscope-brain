## 1. 适用范围和依赖

一期只落地 Web 入口。`platform_user.id` 已由[身份建表 SQL](../../../db/schema/01_用户与管理员建表.sql)定义，以下表以 `BIGINT UNSIGNED` 逻辑引用它。数字员工定义及发布版本表尚未完成，因此 `employee_id`、`employee_release_id`、`target_release_id` 先保持同型数值引用，不伪造目标表或外键。AgentScope 框架状态使用单独的 MySQL 后端与状态表；本规格只保存它的受控会话槽和核对所需的版本观察值。

**与 AgentScope v2.0.4 MySQL 状态表的映射。**每次 Run 从可信业务 Session 取 `platform_user.id` 并转为框架的 `userId` 字符串，把 `business_session.state_session_key` 原样作为框架的逻辑 `sessionId`；不能预先拼接用户 ID，也不能由浏览器提供这两个值。该 MySQL 实现内部才把两者拼成物理 `session_id = userId + ":" + sessionId`，并用 `state_key = agent_state` 读取 Agent 当前状态。本期服务端生成不复用的 32 位小写十六进制随机状态槽，不接受客户端输入；这样也避免业务列 `ascii_bin` 与框架默认 `utf8mb4_unicode_ci` 排序规则不同造成大小写碰撞。即使用户 ID 达到 `BIGINT UNSIGNED` 的 20 位上限，物理键也只有 53 字符，低于框架物理列的 255 字符上限。[状态槽编码源码](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-extensions/agentscope-extensions-mysql/src/main/java/io/agentscope/extensions/mysql/state/MysqlAgentStateStore.java#L3713-L3739)、[状态列和排序规则源码](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-extensions/agentscope-extensions-mysql/src/main/java/io/agentscope/extensions/mysql/state/MysqlAgentStateStore.java#L2616-L2633)

[官方分布式 MySQL 文档](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/docs/v2/zh/integration/distributed/mysql.md#L225-L239)写有独立 `user_id`、`state_value`、`state_type`；但同版本[实际建表源码](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-extensions/agentscope-extensions-mysql/src/main/java/io/agentscope/extensions/mysql/state/MysqlAgentStateStore.java#L2616-L2633)是 `session_id`、`state_key`、`item_index`、`state_data`、`version` 及时间列。框架表由选定的状态后端管理，不加入本文件十张业务表的 DDL；部署时按锁定的依赖版本和实际表核验。该文档的 `MysqlDistributedStore` 还提供 Workspace KV、沙箱快照和执行锁，不能据此把 Agent 当前状态当作完整原始消息、媒体原件、Run 或会议写操作记录。[分布式存储组件](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/docs/v2/zh/integration/distributed/mysql.md#L240-L283)、[当前状态与原始历史的区别](../../调研/状态与持久化/AgentScope%20SQL多模态消息持久化能力.md)

与现有身份表相同，平台业务表使用 MySQL 8.0.16+、InnoDB、`utf8mb4`，每表都有 `id BIGINT UNSIGNED AUTO_INCREMENT`、`gmt_create`、`gmt_modified` 和中文表列注释。业务时间由应用按 UTC 写入；不建物理外键、级联或存储过程。索引名使用 `uk_`、`idx_`。状态码、请求号及状态槽使用区分大小写的 ASCII 排序规则，防止默认不区分大小写的排序规则放宽代码或标识比较。

## 2. 十张平台业务表

| 表 | 保存的事实 | 主要约束和读取路径 |
| --- | --- | --- |
| `business_session` | 稳定所有者、员工、固定发布版本、Web 入口、直接来源会话、归档/生命周期/恢复状态、AgentScope 状态槽 | 状态槽全长唯一；成功后继的来源唯一；按用户、员工、归档和活动时间列会话。 |
| `session_upgrade_attempt` | 一次升级预检、候选会话、首轮与激活 Run、空闲截止时间及结果 | 每个来源最多一个开放尝试和一个成功尝试；一个目标会话最多属于一次尝试。 |
| `business_message` | 已接纳用户输入或已完成员工回复、会话顺序、Web 提交键和关联 Run | 会话内消息序号唯一；同用户提交键唯一；一期每 Run 最多一条正式员工回复。 |
| `message_media` | 素材归属、私有对象存储配置版本/对象键/可选对象版本、种类、MIME、字节数和 SHA-256 | 不保存二进制或临时 URL；完整对象定位唯一；原件可读性由应用核对。 |
| `message_content_block` | 正式消息内 `TEXT`/`MEDIA` 内容块及原始交错顺序 | 消息内块序号唯一；素材记录最多被该消息的一个内容块引用。 |
| `business_run` | 输入消息、调用人、固定版本、请求幂等键、重试链、执行/核对状态和候选结果 | 同一 Session 最多一个非终态 Run；按 Session 时间和输入消息读执行历史。 |
| `run_progress` | 可供重连读取的部分答复片段与关键进度 | Run 内事件序号唯一；不要求逐 token 入库。 |
| `tool_operation` | 跨业务逻辑工具操作、固定目标/契约/Adapter/策略版本、可信身份绑定、参数、稳定内部请求号、上游幂等及核对能力和结果 | 内部请求号全长唯一；Run 内操作编号唯一；未知结果保留 `UNKNOWN`，本地请求号不等于上游幂等保证。 |
| `operation_confirmation` | 对一次具体操作的目标、版本、身份和参数的一次性确认 | 一份提案一条确认；参数和完整操作摘要匹配；凭据摘要唯一；十分钟过期。 |
| `conversation_audit_event` | 会话动作和固定管理员的内容访问记录 | 按操作者、目标用户和 Session 追查；不复制正文、图片或操作参数。 |

## 3. 数据库保证与服务事务保证的边界

数据库直接保证完整的提交键、Run 请求键、逻辑操作请求号和对象定位唯一，内容块与事件的局部顺序，“最多一个”活动 Run、开放升级尝试及成功后继。实现依靠可空生成列与唯一索引：终态行生成 `NULL`，MySQL 唯一索引允许多条 `NULL`。[MySQL 8.0 唯一索引规则](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)、[生成列索引规则](https://dev.mysql.com/doc/refman/8.0/en/generated-column-index-optimizations.html)。状态取值和文字/素材互斥由 `CHECK` 约束限制；部署版本需支持强制执行 `CHECK`。[MySQL 8.0 CHECK 约束](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)。

以下完整性不能由这些单表约束独自证明，必须在服务事务、权限检查和关联巡检中实现：

1. `business_session.user_id` 必须存在；消息、媒体、Run、确认、操作的 `UserId` 与所在 Session 相同。会话来源链不能跨用户或员工，目标版本必须确实不同，且不能成环。
2. 用户消息插入后创建首次 Run，并在同一事务回填 `initial_run_id`；提交时不得为空。内容块至少一条、序号连续；素材引用必须属于同一正式消息，原件已上传且摘要/字节数正确。正式员工回复必须对应一个已成功且状态可恢复的 Run。SQL 不能独自保证对象存在或模型支持该类型。
3. 一个升级尝试的候选 Session、首次 Run、激活 Run、预检历史摘要与来源/目标状态必须相互一致。`READY_FOR_FIRST_MESSAGE` 到期时只对无目标消息与 Run 的尝试解冻来源；已接纳的失败候选须保留，显式放弃后不得复活。
4. `tool_operation` 与确认必须绑定同一 Run、操作者、参数摘要及完整操作摘要。工具绑定固定目标、契约、Adapter 和策略；确认所依赖的授权、安全和身份绑定版本重新检查，会议绑定继续检查当前号码与 `phone_revision`。十分钟过期、一次性消费及上游业务权限由服务保证。`UNKNOWN` 写结果先核对，不自动换号重发或释放 Run 阻断；本地唯一键不证明上游具备幂等能力。
5. 管理员查看正文、图片、过程或完整操作参数前先检查固定管理员身份并成功追加审计；审计失败不返回内容。查看权限不改变原消息归属或会议工具调用人。

没有物理外键也意味着删除受引用的身份、Session、消息或素材会破坏历史。本期没有永久删除会话按钮；应用不得将硬删除当作归档。对象原件、SQL 和历史存储配置必须联合备份及恢复，正式引用对象不能被临时上传清理误删。2026-10-23 用户将数据保留策略延后，留存期限、自动过期及彻底删除规则不作为一期验收前置。

## 4. 关键写入顺序

**接纳输入。**先按 `UserId + submission_key` 查重；新输入的全部素材先上传私有对象存储并校验。再在 SQL 事务内锁定 Session、重新核对提交键和权限，写正式消息、素材元数据、内容块、Run，并回填首次 Run 和消息序号。模型只能在提交后调用。对象上传与 SQL 不是同一事务；明确回滚后未引用对象延迟清理，提交结果不明先核对，清理与新引用必须互斥。详见[上传与清理规则](通用素材与工具操作设计.md#22-接纳失败与清理)。显式重试另建 Run，复用输入消息。

**完成 Run。**流式片段先按批次写入 `run_progress`。完整结果进入 Run 候选状态；核实 AgentScope 状态可恢复后，才在平台事务中写正式员工消息并标记 Run 成功。框架状态后端和平台事务不能仅因共用 MySQL 就被假定为原子提交；中途失败保持 `RECONCILING` 并阻断新 Run。固定版本的状态写入顺序、状态版本能力和重启恢复须另做真实集成验收。

**升级。**按成功来源链预检全部正式消息、对象原件及新版模型支持能力，不能以签名 URL 过期代替原件缺失的判断。写 `READY_FOR_FIRST_MESSAGE` 尝试后来源暂停新 Run。首条新版输入才创建候选 Session、用户消息与首次 Run。成功时在平台事务中同步标记尝试成功、目标激活、直接来源只读；失败候选保留供查看、重试或显式放弃。空闲 30 分钟过期只处理无首条消息的尝试。

**工具操作与查看。**先保存固定目标、版本、身份、策略及规范化参数的操作提案；受控查询可无需确认，会议预约和取消必须确认。确认消费与操作转待发送在同一事务；发送前再次鉴权、原子领取并先落盘发送意图。未知写结果按 Adapter 声明的实际能力核对，不能默认每个接口支持去重或请求号查询。管理员内容查看、原件下载或签发访问凭据以成功追加审计作为前置条件；审计行不保存内容副本。

## 5. 通用化与模型约束

- 消息素材表不按具体文件格式扩表，内容块保持 `TEXT`/`MEDIA`；具体解析和模型输入由素材 Adapter 负责，一期仍只验收文字与图片。
- 操作表不按 Skill 或业务扩表；`normalized_arguments`、`normalized_result` 由固定 Schema 和 Adapter 校验。平台拥有独立业务生命周期时才另行设计业务表。
- `tool_binding_version` 固定工具目标、契约、Adapter 和策略；`operation_sha256` 覆盖完整执行语义，具体编码及身份映射见[通用工具操作设计](通用素材与工具操作设计.md#3-通用工具操作)。提案不可原地改变，改目标或参数须使旧确认失效并创建新提案。
- `request_id` 是内部逻辑操作标识；`provider_request_id` 仅在上游实际支持幂等键时存在，会议 Adapter 继续使用稳定上游 `requestId`。`SENT` 包含“可能已发出”，不能作为自动重放依据。
- 本文件仍是十张表的初建规格，不是对既有库执行的迁移脚本。若已有旧版表或二进制原件，须另写迁移方案并逐件核对对象，不得直接删列或重建有数据表。

## 6. 已做结构检查与后续验收

- 旧版图片 BLOB/会议专用模型曾于 2026-10-19 在隔离 MySQL 8.0.45 建立 17 张表并通过九项拒绝探针；这是旧版证据，不能证明本版对象存储和通用操作模型有效。

- 仍需在应用实现后验证完整图文接纳事务回滚、升级并发与全历史预检、AgentScope 状态与业务提交错开失败、未知会议写结果及管理员审计失败时拒绝返回内容。建表成功和上述单表约束探针不代表这些跨表业务行为已通过。

- 未来渠道只保留 `entry_kind` 和独立业务 Session 的扩展位置；一期不创建绑定、位置、投递、回执或改绑表。
