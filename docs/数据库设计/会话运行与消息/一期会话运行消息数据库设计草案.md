# 一期会话、运行与消息数据库设计草案

> 状态：物理模型讨论草案，2026-10-19；后续字段和索引已展开为[建表规格](一期会话运行消息建表规格.md)与[建表 SQL](../../../db/schema/02_会话运行消息建表.sql)，已做隔离 MySQL 结构检查，仍待整体评审和应用集成验收。本文同步 2026-10-19 用户确认的通用化决定；素材与操作的细节以[通用素材与工具操作设计](通用素材与工具操作设计.md)为准，不表示应用或渠道已实现。  
> 业务规则以[业务会话、运行、消息与跨渠道续传设计规格](业务会话运行消息与跨渠道续传设计规格.md)为准；身份主键与建表约定以[用户与管理员建表规格](../用户与管理员/用户与管理员建表规格.md)及现有 SQL 为准。

## 1. 一期边界

一期只实现 Web 入口的业务 Session、Run、正式消息、文字与图片、版本续接、写操作确认及可恢复审计。未来渠道只保留业务 Session 与入口来源分开的扩展位置，不在一期建立绑定、聊天位置、投递、回执或改绑的具体表。将来外部渠道仍须使用独立 Session；本轮已讨论的渠道续传行为仅是未来设计约束，不能作为一期已实现能力。

数字员工定义与发布版本表尚未落地。一期会话模型引用同型的数值 `employee_id` 与 `employee_release_id`，但不能把目标表当作现存表。`platform_user.id` 是稳定 `UserId`；手机号、Web 登录会话、渠道发送人 ID 都不是业务 Session 的所有者主键。

## 2. 已确认的落库语义

1. 新建空白工作区不写入业务 Session。平台接纳首条用户输入时，在一个业务事务中创建 Session、正式用户消息和 Run；既有 Session 的新输入也在一个事务中写入正式消息与 Run。模型失败不删除已接纳输入；明确失败且状态可恢复时，用户可以重试同一消息或继续发送新消息。
2. 重试沿用原正式用户消息，创建可独立追查的新 Run。结果不明的会议写操作必须先核对，不得以“重试”自动重新发出写请求。
3. 一期消息由有序文字与图片内容块组成。素材原件保存在私有对象存储，MySQL 独立媒体记录保存归属、稳定对象定位、类型、长度和摘要；全部原件上传且校验成功后，才在 SQL 事务中接纳正式消息与 Run。任一素材失败不留下半条正式消息；失败上传的未引用对象按租约与提交核对规则延迟清理。
4. 完整员工回复才进入正式消息。过程进度、流式片段与中断内容归 Run；重新打开页面可查看累计的已保存输出与关键进度，无需逐字重播。只有正式回复和可恢复的 AgentScope 状态都持久保存后，Run 才算完成。持久化中断进入待核对，并暂停该 Session 的新 Run；不得把已经显示在浏览器中的文字直接视为完成。
5. 一段会话固定所属 `UserId`、数字员工与发布版本。归档、历史只读、运行暂停和当前授权是不同维度。运行或等待确认的 Run 阻止同会话新普通输入；确认与取消仍作用于原 Run。
6. “在新版继续”预检全版本链正式消息及必需素材；用户首条新版消息触发首次新版 Run。待激活期间来源 Session 暂停新 Run，可显式放弃；预检后 30 分钟内未发送首条新版消息，则结束空闲尝试并恢复来源会话接收新 Run。已有消息或 Run 的尝试不按空闲规则自动清除。新版首轮成功且状态持久化后，新 Session 成为当前会话，直接来源旧 Session 才转只读。失败不锁死旧 Session，已接纳的新版输入及失败 Run 不可静默抹去。V1→V2→V3 的 V3 首轮读取 V1 与 V2 的全部正式对话，原消息仍各归原 Session。
7. 通用工具操作保存固定目标及绑定版本、可信身份绑定、规范化参数及完整操作摘要、稳定内部请求号、上游幂等/核对能力、发起人、状态与必要结果；会议操作是第一个实例。会议系统仍是预约事实和业务权限的权威来源。固定管理员可直接查看用户完整正式消息、图片、归档及历史只读会话、停用用户历史、Run 过程输出和完整会议写操作记录，不作展示脱敏；查看不赋予代用户发送、确认或调用工具的权力。查看内容时追加访问审计，只记查看人、目标用户、会话或操作、时间与入口，不复制正文。
8. AgentScope 当前状态使用持久化 MySQL 后端，采用与平台原始消息分开的框架存储。Session 与其受控状态槽建立映射；框架当前上下文、压缩后的状态或 Transcript 均不充当平台完整原始历史。
9. 首次新版 Run 失败后，用户可以放弃这次升级；待激活目标 Session、已接纳输入和失败 Run 留作可查看的失败尝试，不进入成功版本链，来源旧 Session 恢复可运行。以后再升级应建立新尝试，不能复活已放弃的候选 Session。
10. Web 提交使用与消息正文分离的提交标识。网络超时后携同一标识重发，只返回原 Session、正式消息和 Run；用户主动再次发送相同正文但使用新标识，视为新的输入。对同一正式消息发起的显式 Run 重试另有自己的请求标识。

## 3. 候选关系与表职责

下表保留职责和关键引用，当前字段与约束以关联建表规格和 DDL 为准。所有业务关联以 `BIGINT UNSIGNED` 表示，不建物理外键；写入事务与关联巡检承担完整性责任。

| 候选表 | 核心事实 | 主要唯一性与关联 |
| --- | --- | --- |
| `business_session` | 所有者、员工、固定发布版本、入口类型、来源旧会话、归档与可运行状态、AgentScope 状态槽 | `id` 为业务 SessionId；`user_id` 引用 `platform_user.id`；来源旧会话不能跨用户或员工。 |
| `session_upgrade_attempt` | 来源 Session、待激活目标 Session、版本链预检、首次 Run、尝试状态与失败原因 | 同一来源最多一个进行中的升级及一个成功后继；失败尝试保留可核对记录。 |
| `business_message` | 所属 Session、会话内顺序、发送方、Web 提交标识、来源 Run | `(session_id, message_no)` 与 `(user_id, submission_key)` 唯一；用户输入可被多次 Run 引用，员工完成消息只对应产出它的 Run。 |
| `message_content_block` | 一条正式消息内的有序 `TEXT`/`MEDIA` 块 | `(message_id, block_no)` 唯一；文字块与素材引用互斥。 |
| `message_media` | 所属正式消息、私有对象定位、素材种类、MIME、字节数与摘要 | 媒体可读性必须在接纳消息和升级预检时验证；读取权限经所属消息与 Session 判定。 |
| `business_run` | 输入消息、执行尝试及请求标识、调用人、固定版本、生命周期、结果与待核对原因 | 一条输入可有多个 Run；同一 Session 至多一个运行中、等待确认或待核对的 Run。 |
| `run_progress` | 按序保存的关键进度、部分回答片段及中断标记 | 读取时汇总已落盘片段；不把逐 token 事件当成必须保存的业务事实。 |
| `operation_confirmation` | 某次展示给用户的具体操作、有效期、一次性使用和失效原因 | 绑定原 Run、操作者、参数及完整操作摘要；十分钟过期，使用一次。 |
| `tool_operation` | 一次逻辑工具操作的不可变提案、稳定请求号、上游能力及核对结果 | 复用跨业务模型；内部请求号不证明上游幂等；未知写结果不能换号重发。 |
| `conversation_audit_event` | 会话升级、归档、取消、拒绝、恢复及管理员查看内容等结构化事实 | 管理员查看事件记录查看人与目标范围，不复制被查看的正文；审计不代替原始消息或会议操作记录。 |

### 3.1 公共物理约定

目标是与现有身份 SQL 相同的 MySQL 8.0、InnoDB、`utf8mb4` 方案。每张平台业务表均有 `id BIGINT UNSIGNED AUTO_INCREMENT`、`gmt_create DATETIME(6)`、`gmt_modified DATETIME(6)` 和中文表列注释；应用按 UTC 写入时间。`is_xxx` 使用 `TINYINT UNSIGNED` 并限制为 0/1。唯一索引以 `uk_` 命名，普通索引以 `idx_` 命名；不建物理外键、级联或存储过程。状态值用字符串加 `CHECK` 限定。框架自建的 AgentScope 状态表属于另一存储边界，不机械套用平台业务表规约。

`submission_key` 和 Run 请求键拟使用经服务端验证的 16 字节 UUID；摘要使用 `BINARY(32)` 保存 SHA-256 结果。唯一性必须覆盖完整键，不用可能把不同长字符串误判为相同的前缀唯一索引。消息文字不建正文索引；素材原件不进入 SQL，完整对象定位建立唯一索引。MySQL 8.0 的唯一索引允许多条 `NULL`，因此可用受状态控制的生成列唯一索引限制“最多一个活动项”；该用法须在本地建表验收中验证。[MySQL 唯一索引与前缀语义](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)、[生成列索引](https://dev.mysql.com/doc/refman/8.0/en/generated-column-index-optimizations.html)。

### 3.2 核心字段与约束草案

**`business_session`**

- 身份：`user_id`、`employee_id`、`employee_release_id BIGINT UNSIGNED NOT NULL`；`entry_kind VARCHAR(16) NOT NULL` 一期只接受 `WEB`。`source_session_id BIGINT UNSIGNED NULL` 仅用于版本链，不用于跨渠道复用。
- 生命周期：`lifecycle_status` 取 `ACTIVE`、`PENDING_ACTIVATION`、`READ_ONLY`、`ABANDONED`；`is_archived` 单独保存；`recovery_status` 取 `READY`、`STATE_MISSING`、`RECONCILING`。当前授权及发布版本是否仍可运行每次重新计算，不固化为历史会话状态。
- 运行与展示：`state_session_key VARCHAR(128)` 是服务端生成、不可复用的框架状态槽；`last_message_no BIGINT UNSIGNED` 是会话内正式消息序号；`row_version BIGINT UNSIGNED` 用于并发更新；`last_activity_at DATETIME(6)`、可空 `title VARCHAR(200)` 用于列表。
- 约束：`uk_state_session_key`；`idx_user_employee_archive_activity (user_id, employee_id, is_archived, last_activity_at)`；`idx_source_session_id`。成功目标会话的生成列 `successful_source_session_id` 在状态为 `ACTIVE`/`READ_ONLY` 且有来源时等于 `source_session_id`，其余为 `NULL`，以唯一索引防止同一来源出现两个成功后继。服务事务另核对来源与目标同一用户、同一员工、不同发布版本且无循环。

**`session_upgrade_attempt`**

- `source_session_id`、可空 `target_session_id`、`requested_by_user_id`、`target_release_id`、`status`、`expires_at`、可空 `first_run_id` 与 `activation_run_id`、`failure_code`、`finished_at`。首轮失败后可由同一已接纳输入发起新 Run；真正使目标激活的 Run 记在 `activation_run_id`。预检证据记录 `history_message_count`、`history_sha256`、`source_last_message_no`；摘要须由完整有序前序链的正式消息及必需素材摘要计算，不把模型压缩状态当输入。
- 状态至少区分 `READY_FOR_FIRST_MESSAGE`、`FIRST_RUN_ACTIVE`、`FAILED_RETRYABLE`、`RECONCILING`、`SUCCEEDED`、`ABANDONED`、`EXPIRED`。空闲过期只适用于尚无目标消息和 Run 的 `READY_FOR_FIRST_MESSAGE`。
- 生成列 `open_source_session_id` 只在进行中、可重试或待核对状态取来源 ID，配 `uk_open_source_session_id`；`successful_source_session_id` 只在 `SUCCEEDED` 取来源 ID，配 `uk_successful_source_session_id`。另设 `uk_target_session_id` 和 `idx_source_session_id_gmt_create`。这些约束只证明“最多一个”，具体完整性由事务与巡检保证。

**`business_message`、`message_content_block`、`message_media`**

- 正式消息记录 `session_id`、`user_id`、`message_no BIGINT UNSIGNED`、`sender_kind`（`USER`/`ASSISTANT`）、可空 `submission_key BINARY(16)`、可空 `submission_sha256 BINARY(32)`、可空 `initial_run_id`、可空 `produced_by_run_id`、`accepted_at`。用户消息必须有提交键、提交语义摘要和首个 Run 引用且不带产出 Run；员工消息必须关联成功 Run 且不带提交键。`uk_session_message_no` 保证顺序，`uk_user_submission_key` 保证浏览器同次提交只接纳一次，`uk_produced_by_run_id` 限制一期每个 Run 最多一条完整员工回复。提交语义摘要覆盖目标 Session 或新建意图、所选员工、客户端显式版本选择（如有）、有序文字块和素材原件摘要；不纳入可能在网络超时期间变化的“当前最新版本”求值结果。同键改变稳定提交语义即报冲突，相同正文可以因不同提交键成为两条消息。
- 内容块记录 `message_id`、`block_no`、`block_kind`（`TEXT`/`MEDIA`）、可空 `text_content LONGTEXT` 与 `media_id`。两类内容必须恰有其一，`uk_message_block_no` 保证素材与文字的原始交错次序；可空 `media_id` 上的完整唯一索引保证一份原件不被多处内容块引用。正式消息至少一个内容块由事务保证。
- 素材记录 `message_id`、`user_id`、不可变 `storage_profile`、服务端生成且不复用的 `object_key`、可空 `object_version`、`media_kind`、`mime_type`、`byte_count`、`content_sha256 BINARY(32)` 和展示文件名。`uk_storage_profile_object_key` 覆盖完整定位，`idx_message_id` 支持清点；块与素材须属于同一消息。原件由私有对象存储保存，不存二进制、Base64 或临时 URL。类型、完整性、权限、读取及对象清理详见[通用素材设计](通用素材与工具操作设计.md#2-消息素材与私有对象存储)。

**`business_run`、`run_progress`**

- Run 记录 `session_id`、`input_message_id`、`actor_user_id`、`employee_release_id`、`run_request_key BINARY(16)`、`request_sha256 BINARY(32)`、可空 `retry_of_run_id`、`status`、`started_at`、`ended_at`、`reconcile_reason`、`state_version_before/after`（以实际框架后端能力为准）与待正式提交的 `result_candidate JSON`。用户消息可被多次 Run 引用；显式重试用新 Run 键，不复用旧 Run 行。同一 Run 键携不同输入或动作应拒绝为冲突。
- Run 状态至少区分 `ACCEPTED`、`RUNNING`、`WAITING_CONFIRMATION`、`CANCEL_REQUESTED`、`RECONCILING`、`SUCCEEDED`、`FAILED`、`CANCELLED`。`uk_actor_run_request_key` 保证同一次 Run 请求幂等。生成列 `busy_session_id` 对非终态取 `session_id`，终态为 `NULL`；`uk_busy_session_id` 阻止同会话并行活动 Run。`idx_session_id_gmt_create` 与 `idx_input_message_id` 支持会话历史及重试链读取。
- `run_progress` 记录 `run_id`、`event_no`、`event_kind`、可空 `display_text LONGTEXT`、`occurred_at`；以 `uk_run_event_no` 顺序读取关键进度和已落盘的部分答复。平台按可恢复的批次保存增量，不承诺每个流式 token 都单独落库。终态员工消息从完整结果生成，不能把过程片段直接提升为正式消息。

**`tool_operation`、`operation_confirmation`**

- `tool_operation` 表达逻辑工具操作，固定提供方/工具/绑定版本、参数 Schema、可信身份绑定、读写性质和确认策略，保存规范化参数、参数及完整操作摘要、稳定内部 `request_id`、上游实际幂等键与核对能力、状态、资源号和必要结果。同一 Run 内操作序号唯一；请求号全长唯一。`SENT` 先持久化发送意图，退出后按可能已发送核对。`UNKNOWN` 不能改成失败后换号重写。会议、请假、邮件复用结构；具体契约和恢复见[通用操作设计](通用素材与工具操作设计.md#3-通用工具操作)。
- `operation_confirmation` 保存 `operation_id`、原 Run、操作者、参数及完整操作摘要、展示时的授权/安全/身份绑定版本、凭据摘要、有效期和消费状态。一份提案最多一条确认，十分钟有效且至多消费一次；改目标或参数须新提案，实际调用前重新检查权限与绑定。会议身份版本继续映射 `phone_revision`；当前版本一致性不能仅靠单表约束证明。

**`conversation_audit_event`**

- `actor_user_id`、`target_user_id`、可空 `session_id`/`run_id`/`operation_id`、`action_code`、`outcome`、`entry_kind`、`occurred_at`、可空 `reason_code`。管理员查看正文、图片、Run 过程或会议写操作时记录查看范围和结果，不在审计行复制聊天正文、图片或参数。`idx_actor_user_id_occurred_at`、`idx_target_user_id_occurred_at`、`idx_session_id_occurred_at` 支持追查；身份变更仍写现有 `identity_audit_event`。

## 4. 事务与恢复约束

### 4.1 接纳输入与重试

1. 服务端从已认证 Web 登录会话取得 `UserId`，核对账号、员工授权、发布版本及目标 Session 的归属和可运行条件。新建普通会话时尚无数据库 Session，首次消息负责创建它；已有会话须先锁定该 Session 行并核对无活动 Run、无升级占用和无恢复阻断。
2. 先检查同一 `submission_key` 是否已有消息；若有，核对包含目标与有序内容的 `submission_sha256`，一致则返回原 Session/消息/Run，不一致则报提交冲突。全部素材在接纳前完成私有对象上传及类型、长度、摘要校验。一个 SQL 事务内依次写入 Session（首次时）、用户消息、素材元数据、内容块、Run 和会话序号；创建 Run 后回填用户消息的 `initial_run_id`，由事务保证提交时不为空。SQL 中任何一步失败全部回滚；对象不属于该事务，明确失败的未引用上传延迟清理，提交结果不明先核对，清理须与接纳互斥。并发同键请求仍由唯一索引裁决，冲突方回查已提交记录后按上述语义返回。外部模型调用只能在该事务提交后开始。
3. 显式重试复用 `input_message_id`，创建新的 Run 和 `run_request_key`，不创建消息。先确认先前会议写操作无待核对结果、框架状态可恢复且同会话没有活动 Run。同一个 Run 请求键重发时只返回原 Run；键相同而语义不同时报冲突。
4. 会话内正式消息顺序由锁定 Session 后递增的 `last_message_no` 确定，不依赖浏览器时间、跨会话自增主键或未来渠道消息 ID。重试不占新消息序号；完整员工回复在完成事务中取得新序号。唯一索引是并发冲突的最终防线，不能代替服务端权限检查。

### 4.2 Run 完成、取消与重启

1. 执行时逐批保存可供重连读取的部分输出和关键事件。模型生成完毕但尚未保存框架状态或正式员工消息时，完整结果仍是 Run 的候选结果，不对历史显示为已完成答复。
2. `SUCCEEDED` 的前提是 AgentScope 状态可恢复且完整员工消息已经提交。框架状态写入和平台业务事务即使位于同一 MySQL 实例，也不能预设由一个事务原子提交；必须用 Run 状态、候选结果及状态版本核验处理中途失败。候选结果的可靠持久化顺序、框架保存回调和状态版本能力须在固定版本集成时验收，验收前不能把方案宣称为已实现的原子提交。
3. 进程重启后，未终结的 Run 和已发出但结果不明的会议操作进入 `RECONCILING`/`UNKNOWN` 核对路径，保留其占用并阻止新 Run。不得自动重放模型调用或会议写操作。用户主动取消先进入 `CANCEL_REQUESTED`；已发出的写操作以会议系统核对结果为准，不能因本地取消认定写入不存在。
4. 明确失败且状态可恢复的 Run 转 `FAILED` 后释放活动占用，原正式用户消息仍在历史中。用户可重试它，也可发下一条新消息；后续上下文包括已接纳的失败输入。若状态缺失或写结果不明，Session 保持暂停直至核对或显式开关联新会话。

### 4.3 版本续接

1. 按成功的 `source_session_id` 链逐级读取全部前序 Session 的正式用户与员工消息，按版本链先后和各会话 `message_no` 组装输入；不读取旧系统指令、工具调用、工具结果或 Run 部分输出。逐一核对对象原件、长度、摘要、类型支持及模型可接受的完整输入容量；签名 URL 过期时重新鉴权解析，不视作原件丢失。预检失败不创建成功后继，也不冻结来源会话。
2. 预检与写入待激活尝试之间再锁定来源 Session，核对没有活动 Run、待确认写操作或已经开始的升级，并比较预检时的消息序号/摘要。提交 `READY_FOR_FIRST_MESSAGE` 后来源暂停新 Run。30 分钟内无首条新版消息的尝试在加锁核验仍为空后转 `EXPIRED`，恢复来源；已有消息或 Run 的尝试不能由此任务删除。
3. 首条新版消息创建目标 `PENDING_ACTIVATION` Session、正式输入及首次 Run；模型实际收到第 1 步的完整前序链和该条新输入。失败保留候选会话及其消息、Run，供本人和固定管理员查看或重试。显式放弃将尝试与候选会话转为 `ABANDONED`，来源恢复可运行；后续新升级建立新尝试。
4. 首次新版 Run 成功、消息和状态均可恢复后，在一个平台事务内把尝试标为 `SUCCEEDED`、目标设为 `ACTIVE`、直接来源设为 `READ_ONLY`；唯一约束阻止多个成功后继。失败候选不进入成功版本链；若激活事务结果未知，先核对这三处事实，不重新调用模型。

### 4.4 确认、工具操作及管理员查看

1. 先保存固定目标、绑定版本、身份、策略与参数的通用提案；授权查询可按策略跳过确认，会议预约和取消必须确认。确认绑定参数及完整操作摘要，十分钟一次性；当前账号、授权、安全和身份版本必须一致。消费与转待发送同事务，发送前再次鉴权、原子领取并落盘发送意图。未知写结果按 Adapter 的实际上游能力核对，不用新 ID 自动重发。
2. 固定管理员查看用户正式消息、图片、Run 过程或完整会议操作时，服务端检查固定管理员身份并在返回内容前写入访问审计。审计写入失败时本次不返回内容；查看事件记录人、目标用户、目标 Session/操作、入口和时间，不复制正文或图片。查看不改变消息所有者、Run 调用人或会议 MCP 的签名操作者。
3. 无物理外键意味着还需巡检：Session 所属用户、消息与 Session、Run 与输入消息、块与媒体、升级链与唯一成功后继、状态槽、会议操作与确认，以及审计目标引用均须核对。发现异常时阻断受影响 Session 的新敏感操作并告警。

## 5. 未来渠道的最小预留

核心 Session 使用平台生成的稳定主键，并保留入口类型；正式消息、Run 与其引用不使用 Web 登录会话 ID、手机号或渠道 peer/sender ID。外部渠道到来时再增加可信绑定、聊天位置、入站去重和出站投递表，并通过业务 SessionId 接入相同的消息与 Run 主线。一期不选定具体渠道键、回执语义、重试窗口或改绑规则，也不提前创建空表。

## 6. 后续建表与运行验收场景

以下是设计的验收标准，不代表当前已经执行。身份表已完成的本地验收不能替代这些场景。

| 场景 | 必须观察到的数据库及用户行为 |
| --- | --- |
| 首次普通输入、图片上传失败 | 先完成全部原件上传；成功时 Session、素材元数据、内容块、正式用户消息和 Run 在 SQL 一并提交；失败不产生半条正式历史，未引用对象按租约/核对规则延迟清理，不能承诺跨存储原子提交。 |
| 同一提交重发、改内容重发 | 同键同内容得到同一 Session/消息/Run；同键改内容报冲突；新键但正文相同产生新消息。 |
| 同会话并发输入与重试 | 活动 Run 只保留一个，普通新输入被拒绝；终态失败后重试引用同一用户消息，新 Run 独立可追查。 |
| 流式输出中断与重启 | 已落盘的过程输出可查但不形成正式员工消息；重启后待核对且不自动重放模型或会议写操作。 |
| 状态保存与业务提交错开失败 | Run 不能误标 `SUCCEEDED`；消息与 AgentScope 状态不一致时暂停新 Run，按状态版本、候选结果和事件核对。 |
| V1→V2→V3 | V3 首轮实际输入包含 V1、V2 全部正式消息及可读图片；原消息归属不变，只有成功链展示为版本历史。 |
| 升级超限、素材缺失、空闲过期与失败放弃 | 前两者不锁旧会话；无首条消息满 30 分钟解冻；已接纳的失败目标保留可查且不进入成功链；重复操作只得一个成功后继。 |
| 确认过期、重复消费、号码或授权变化 | 旧确认不能发出会议写操作；已发出操作按原 `requestId` 核对，结果不明不换 ID 自动重写。 |
| 固定管理员查看 | 正文、图片、过程和操作参数完整展示；每次成功或拒绝查看均有不含正文副本的访问审计，查看不能变成代用户操作。 |
| 建表规约及孤儿巡检 | 每表主键/时间/中文注释、唯一索引、状态约束均在真实 MySQL 检验；无物理外键；跨表归属异常由巡检发现。 |
