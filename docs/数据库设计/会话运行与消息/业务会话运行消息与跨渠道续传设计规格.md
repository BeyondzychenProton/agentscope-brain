# 业务会话、运行、消息与跨渠道续传设计规格

> 状态：业务规则于 2026-10-18 确认，固定管理员查看范围、对象存储及通用操作模型于 2026-10-19 调整；本文是设计规格，不代表应用、数据库或外部渠道已经实现。  
> 范围：一期 Web 对话及为将来外部渠道预留的业务边界。本文不制定物理表结构，不执行建表、代码开发或联调。  
> 身份基线：[一期用户与管理员数据模型](../用户与管理员/用户与管理员数据模型.md)；总体边界：[一期总体设计](../../一期总体设计.md)；术语：[平台术语](../../../GLOSSARY.md)。

## 1. 问题陈述（Problem Statement）

用户需要与数字员工持续对话，能够在断线、服务重启和员工发布新版后找回可信的历史、Run 结果和未完成事项。平台还要区分 Web 登录会话、业务会话、每轮 Run、原始消息及 AgentScope 的工作状态，避免将某一层的记录误作另一层的事实。

将来接入外部消息渠道时，同一用户的身份、授权和消息投递需要跨入口保持一致；各渠道的对话仍各自独立。用户可以明确选择把 Web 中的部分信息续传到外部渠道，但不能因此让外部渠道自动获得整段 Web 历史。数字员工定义升级又是另一种动作：新版首次继续时要求模型收到旧会话的完整原始对话，而旧版历史的归属不能被改写。

## 2. 方案（Solution）

平台以稳定 `UserId` 为会话所有者，为每段**业务会话**固定数字员工和不可变的发布版本；每次用户输入产生受平台管理的 **Run**。平台在 SQL 中长期保留业务会话、原始消息、多模态素材所需信息、Run、确认、投递和审计事实。AgentScope `AgentState`、Memory、Workspace 是运行资料，按用户、员工和会话等边界寻址，不替代平台原始消息或 Run 记录。素材原件保存在平台控制的私有对象存储，SQL 保存归属、稳定对象定位和完整性元数据；执行与确认使用跨业务通用记录，具体见[通用素材与工具操作设计](通用素材与工具操作设计.md)。

一期仅开放 Web，用户可有多段独立会话。未来已可信绑定的外部发送人进入同一身份与授权链，但目标渠道维护自己的业务会话。用户选择续传时，仅把选定且已完成的 Web 内容送往目标渠道；送达并核对后，该内容成为目标渠道可见历史和后续对话上下文。数字员工升级则由用户在某条旧会话中明确发起，创建关联到旧会话的新版本会话，严格全量导入原始对话消息供新版模型首次使用；成功后仅该条旧会话只读。

下列较早讨论已被后续决定替代，以本文为准：

| 较早表述 | 最终规则 |
| --- | --- |
| 跨渠道在同一个业务 Session 中续接 | Web 与外部渠道使用独立业务会话，只续传用户选定的信息。 |
| 原会话有未完成 Run 时一律不能跨渠道续接 | 不搬迁原会话；可续传此前已完成的正式消息和素材，正在生成的部分回答、待确认操作不得续传。 |
| 一期只验收文字 | 一期端到端验收文字和图片；音频、视频及通用文件纳入能力核对，具体上线范围后定。 |
| 图片原件以 BLOB 保存到 MySQL | 所有素材原件使用私有对象存储，SQL 保存归属、对象定位、MIME、长度及摘要。 |
| 为会议建立专用操作和确认模型 | 使用通用工具操作和独立操作确认，会议预约/取消继续执行已确认的业务规则。 |

## 3. 用户故事（User Stories）

1. 作为已登录用户，我希望开启多段互不混淆的业务会话，以便分别处理不同话题。
2. 作为已登录用户，我希望每段会话明确对应数字员工和发布版本，以便知道当前由哪个版本回应。
3. 作为已登录用户，我希望新版本发布后旧会话仍可按原版本继续，以便尚未完成的工作不中断；旧版本被停用时则能查看历史但不能新建 Run。
4. 作为已登录用户，我希望在一段会话中同一时间只有一个正在执行或等待确认的 Run，以便新输入不会插入正在处理的事务。
5. 作为已登录用户，我希望确认或取消仍作用于当前 Run，以便不会误触发下一轮对话。
6. 作为已登录用户，我希望关闭页面后服务端继续处理已开始的 Run，以便重新打开页面时能查看累计回答、关键进度和最终状态。
7. 作为已登录用户，我希望主动取消后看见“正在取消”和最终核对结果，以便知道外部写操作是否已经发生。
8. 作为已登录用户，我希望中断的部分回答仍可查看且明确标为中断，以便不把未完成内容误认为最终答复。
9. 作为已登录用户，我希望服务重启后能看见未完成 Run 的待核对状态，以便决定后续继续或重试，而不是遭遇自动重放。
10. 作为已登录用户，我希望框架状态丢失时会话暂停新 Run 并说明原因，以便不会在空白上下文中悄悄继续。
11. 作为已登录用户，我希望归档会话后能从列表隐藏，并在发布版本仍可运行时恢复和继续，以便整理会话而不丢失历史。
12. 作为已登录用户，我希望通过新消息更正旧内容，以便保留原始消息及更正经过，而不是原地修改历史。
13. 作为已登录用户，我希望文字和图片在一期能够输入、保存、查看和供数字员工使用，以便多模态对话真正可用。
14. 作为已登录用户，我希望数字员工升级时只针对自己选定的旧会话“在新版继续”，以便其他旧会话不受影响。
15. 作为已登录用户，我希望新版模型首次收到旧会话全部用户与员工对话消息及所需素材，以便直接接上原话题；旧版内部指令、工具调用和工具结果不作为对话导入。
16. 作为已登录用户，我希望完整历史超出新版模型上下文，或必需素材不可读取时得到明确提示且不因切换失败锁定旧会话，以便不在不知情时接受截断或摘要；旧会话能否继续运行仍按原版本和当前授权判断。
17. 作为已登录用户，我希望升级成功后从新版会话查看完整的前序版本链（例如 V1、V2、V3），而不是只看到最早的 V1，以便追溯每次升级前的消息和版本。
18. 作为已登录用户，我希望个人偏好在同一数字员工的不同会话和发布版本间沿用，以便重复信息不用重说；更正或删除后旧偏好不再恢复。
19. 作为已登录用户，我希望会议预约或取消确认只对应本次展示的操作与参数，并且十分钟内只能使用一次，以便过时或变化的确认不能再次执行写操作。
20. 作为失去某数字员工授权的用户，我希望仍能查看自己过去的会话，但不能继续发起 Run，以便历史归属与当前使用权分开。
21. 作为固定管理员，我希望能直接查看普通用户的完整聊天正文、图片、历史会话、Run 过程输出和会议写操作记录，以便核对对话与操作经过；查看权限不改变原会话所有者或会议工具操作者，查看行为留访问审计。
22. 作为将来已绑定的外部渠道用户，我希望首次私聊某数字员工时建立该渠道会话，此后同一聊天位置默认继续最近仍可运行的会话，以便自然续聊。
23. 作为 Web 用户，我希望明确选择要续传的已完成消息和素材及目标聊天位置，以便外部渠道只收到我选择的信息。
24. 作为外部渠道用户，我希望收到的选定信息显示在该渠道会话中，并可供之后的数字员工对话使用，以便在该渠道继续处理相应话题。
25. 作为 Web 用户，我希望转送失败或送达结果不明时看到真实状态，并能安全重试，以便不会误以为目标渠道已经收到或收到多份。
26. 作为解绑外部渠道的用户，我希望该渠道立即停止创建新 Run 与尚未发出的投递，以便旧绑定不再授予新操作；历史和已经在途的投递仍可核对。
27. 作为尚未绑定的外部发送人，我希望只收到绑定引导，以便我的渠道标识不会被误当作平台用户身份。
28. 作为平台运营者，我希望能区分 Run 完成与渠道回复是否送达，以便发送失败时只重试原回复，不重新执行数字员工或会议操作。
29. 作为群聊参与者，我希望平台在群聊能力正式设计前不把个人记忆或会议工具结果发到群里，以免信息被错误共享。

## 4. 设计决定（Implementation Decisions）

### 4.1 名称、关系与事实归属

| 概念 | 必须承载的业务事实 | 归属与约束 |
| --- | --- | --- |
| Web 登录会话 | 当前登录人及认证有效性 | 由认证基础设施管理；与业务会话分开，过期或撤销不删除历史对话。 |
| 业务会话（Session） | 稳定所有者 `UserId`、数字员工、创建时固定的发布版本、入口渠道、会话归档/只读情况、可选来源旧会话 | 同一用户可有多段；不同渠道独立；不能从渠道聊天 ID 或 AgentScope 状态反推会话归属。 |
| Run | 一轮请求的调用者、来源会话与渠道、固定发布版本、执行状态、结果和关键事件 | 同一会话不得并行执行两轮普通输入；确认、取消和外部写操作核对归属于原 Run。 |
| 业务消息 | 所属会话、发送方、顺序、原始内容及多模态素材、来源/转送关联 | 已提交的用户消息与已完成的员工回复是正式历史；原地不编辑。部分回答属于 Run 过程。 |
| 消息素材 | 消息归属、类型、原件稳定定位和完整性信息 | 私有对象存储保留原件；SQL 元数据与对象共同构成可恢复的原始历史，临时 URL 不是原件。 |
| 工具操作与操作确认 | 当前可信操作者、固定执行目标/版本、参数、提案确认、执行和核对结果 | 同一模型支持不同 Skill/业务；确认绑定一次具体提案，外部业务事实仍归各业务系统。 |
| 渠道身份绑定与聊天位置 | 外部发送人到 `UserId` 的可信绑定；渠道实例、私聊/群/线程位置及其会话路由 | 发送人、接收位置和平台用户分别识别；未绑定发送人不能获得业务会话或 Run。 |
| 选定续传与投递 | 选定的来源消息、目标渠道会话、投递意图、去重身份、回执及最终状态 | 来源和目标会话独立；只在确认送达后把选定内容作为目标可见历史和后续模型上下文。 |
| AgentScope 状态、记忆和工作区 | 当前模型上下文、可压缩状态、长期偏好和运行文件 | 使用平台可信 `UserId` 与隔离后的会话/员工标识；运行状态与完整原始业务消息分开。 |

业务 Session、Run、原始消息、确认、投递与审计由平台持有；会议系统仍是预约结果和业务权限的权威来源。平台不能用一次模型输出、渠道 sender ID、手机号或框架自动生成的 Gateway session ID 代替上述业务事实。`UserId` 的稳定性和授权检查沿用已确认的身份模型。

### 4.2 会话与 Run 生命周期

1. 创建会话时固定数字员工发布版本；发布新版本不改写旧 Session，也不改变执行中的 Run。停用某发布版本只阻止其会话发起新 Run，历史仍可查看。归档只改变列表可见性，不改变所有者、发布版本或框架状态归属；恢复后仍须检查版本及当前权限。
2. 创建 Run 前验证账号有效、员工使用授权、会话归属和可运行版本。运行中或等待写操作确认时，普通新消息应被拒绝并提示完成或取消当前 Run；确认与取消仍进入该 Run。授权撤销后，原用户可查看历史但不能创建新 Run；账号停用则不得登录查看。
3. 浏览器断开不取消服务端 Run。重连展示累计回答、关键进度和最终状态，不要求逐字重放流式动画。中断的部分输出保留在 Run 过程记录并明确标识，不充当完整员工消息。
4. 主动取消先呈现取消中，阻止后续模型和工具步骤。若会议写操作已经发出，须核对会议系统结果后再确定最终状态。服务重启后未完成 Run 进入待核对，不自动重放模型调用或会议写操作；结果不明时由用户明确继续或重试。
5. 若业务消息仍可读取但 AgentScope 状态不能恢复，暂停该 Session 的新 Run，向用户说明；修复状态或显式开关联新会话后才继续，不以空状态冒充原会话。
6. 操作确认绑定一次具体提案的目标、版本、可信操作者、身份绑定及展示参数，只能使用一次，十分钟过期；账号、授权、安全版本、身份绑定、执行目标或相关参数变化会使其失效。实际工具调用时仍须重新检查权限与操作者身份。已发出的外部写操作不能因本地取消或授权变化就认定被撤销。
7. Web 同一次消息提交使用稳定提交标识；网络超时后的相同标识重发返回原 Session、消息和 Run，标识相同而内容改变应拒绝。用户明确再次发送相同文字是新的提交。明确失败 Run 的重试沿用已接纳的原用户消息，另记新 Run；结果不明的外部写操作必须先核对。

### 4.3 数字员工定义升级

1. 用户仅能对自己的一条旧版会话选择“在新版继续”。执行中的 Run 和待确认写操作须先完成、取消或核对到终态；其他旧版会话不受本次切换影响。
2. 新版会话使用自己的发布版本及 AgentScope 状态槽，并关联来源旧会话。旧 Session 和旧消息留在原处供历史查看，不改写旧消息归属。新版模型首次输入由旧会话**全部用户与数字员工对话消息**构成，包含相应图片、音频、文件等素材；不导入旧系统指令、工具调用和工具结果。
3. 首次输入坚持严格全量：预先检查完整历史是否能被新版模型接收以及必需素材能否读取。任一条件失败就不完成切换，不将旧会话转只读，并明确提示超限或素材缺失；旧会话继续受原版本可用状态和当前授权约束。不得在切换时静默截断、分段替代或先行摘要。切换成功后，仅这条旧 Session 转为历史只读；重复操作不能产生多个不一致的新版会话。
   点击“在新版继续”并通过预检后，来源旧会话暂不接纳新 Run；用户首条新版消息触发首次新版 Run。若预检后 30 分钟仍未发送首条新版消息，结束空闲尝试并恢复来源会话接收新 Run；已有消息或 Run 的尝试不按此规则自动清除。首次新版 Run 成功且状态持久化后，才激活新会话并将直接来源旧会话转只读。
   若首次新版 Run 失败，已接纳的新版消息与失败 Run 留在待激活目标会话供查看和重试；用户选择放弃后该失败会话仍保留可查，但不进入成功版本链，来源旧会话恢复可运行。以后再次升级须新建尝试，不能复活已放弃的候选会话。
4. 成功续接后的普通对话使用 AgentScope 自带压缩能力；约在模型上下文使用量达到 80% 时触发。这是**触发阈值**，不是压缩后保留 80% 原文。首次新版模型调用不得因普通压缩阈值提前改写全量历史。压缩只改变当前模型上下文，平台原始消息历史仍保留。
5. 长期偏好记忆可在同一 `UserId` 与同一数字员工的会话及发布版本间共享，但不得跨用户或员工串用；更正、删除和格式变化须有可验证的处理规则。记忆不承担预约事实或完整消息台账职责。

### 4.4 渠道、续传和送达

1. 一期 Web 是唯一实际入口。未来外部渠道接入前，用户从已认证 Web 发起绑定，并在渠道侧确认；企业通讯录自动绑定另行评审。未绑定发送人只收到绑定引导，不创建业务 Session/Run。群聊仅预留 peer 与 sender 的不同标识，不启用群共享会话或把个人记忆、会议工具结果直接回复群里。
2. 外部私聊按可信 `UserId`、数字员工、渠道实例及聊天位置选择渠道会话：首次创建；此后默认继续该位置最近仍可运行的会话，用户明确新建时才切换。会话归属和当前授权仍须每次核验。Web 与该渠道绝不共用业务 Session 或 AgentScope 对话状态。
3. Web 用户明确选定已经完成的正式消息及素材，并选择可信绑定到同一 `UserId` 的目标聊天位置，才可发起续传。目标位置已有同一用户与员工的可用渠道会话时复用，否则创建目标渠道会话。未选中的 Web 历史、正在生成的部分回答和待确认操作不进入目标渠道。Web 原 Run 未结束时，用户仍可续传此前已完成的内容。
4. 续传作为独立投递记录原消息来源与目标渠道结果。确认送达后，选定内容在目标渠道会话中可见、可追溯，并进入其后续模型上下文；Web 会话及消息原归属不改变。送达失败或结果不明时，Web 显示失败/待核对状态，目标侧不得把未确认送达内容当作既成上下文。重试同一投递之前先核对可能已有的回执，避免重复发送。
5. 数字员工 Run 完成与渠道回复送达是两种结果：渠道回复失败时只重试同一回复，不重新执行 Run。解除渠道绑定后立即阻止该渠道创建新 Run 和未发出的投递；已在途投递继续核对结果，既有会话与审计仍归原 `UserId`。

### 4.5 消息与多模态边界

正式用户/数字员工消息保持原始顺序、发送方和多模态内容，不提供原地编辑；更正以新消息表达。平台以 SQL 正式消息、有序内容块和素材元数据，加上私有对象存储中的不可变原件，共同保留可供重启查看、审计和严格全量升级的原始对话。文字与素材的顺序保留，素材可表达图片、音频、视频和通用文件；运行时通过 Adapter 转为当前模型支持的 AgentScope `Msg` / `DataBlock`。结构通用不扩大一期文字与图片的验收范围。

原件先上传且校验成功，再以一个 SQL 事务接纳正式消息、素材元数据和 Run；不能假定对象存储与 SQL 原子提交。提交结果不明先核对，未引用上传按租约和清理互斥规则延迟回收。读取前鉴权，管理员原件访问前成功留审计；持久历史保存对象定位而非临时签名 URL。签名过期可重新解析，原件缺失或模型不支持时不能静默跳过。SQL、对象和历史存储配置联合备份与恢复，细节见[通用素材与工具操作设计](通用素材与工具操作设计.md)。

AgentScope SQL `AgentStateStore` 能保存**当前**多模态上下文，但压缩会替换旧上下文；Harness 会话日志也不是完整媒体副本，因此两者不能单独证明平台保留了严格全量的原始历史。该判断基于 Java `v2.0.4` 静态源码；实施前还须做真实 SQL 往返和素材可读性验收。一期 Web 的文字与图片必须端到端可用；音频、视频、通用文件保留在能力核对与后续范围中，不据此承诺一期渠道或模型已支持。

### 4.6 工作台与员工切换

1. 一期只部署会议室数字员工；多员工切换规则为后续扩展边界，原型用示例员工演示。工作台采用对话优先布局：当前消息流和 Run 状态为主要内容，当前数字员工的最近会话列表作为次级导航；版本历史从当前会话入口打开，不在主导航中另设重复的历史按钮。
2. 用户从员工切换入口打开可用数字员工列表。列表只显示当前用户获授权的员工；切换后更新工作区名称、会话列表、当前消息流、Run 状态和新建会话的员工/发布版本上下文。
3. 切换员工时恢复该员工最近查看且仍可访问的会话；若无可恢复会话则显示该员工的空状态。员工间的业务会话、版本链、Run、AgentScope 对话状态互相隔离，不因切换而合并或复制；同一用户与同一员工范围内已确认的长期偏好规则继续适用。
4. 同一业务对话经历多次发布升级时，历史入口展示该会话链上的所有前序版本，并可选择其中任一历史会话只读查看。版本链按来源关联逐级追溯，不把历史折叠成“仅 V1”；当前会话继续显示当前版本和运行状态。成功升级后，新版会话不再显示“在新版继续”操作。
5. 新建会话始终属于当前选中的数字员工，并固定该员工当前可用发布版本；切换员工只改变工作区上下文，不改变旧会话归属、状态或消息。

对话优先布局和员工切换交互参考[会话工作台原型](../../../prototypes/session-ui-prototype.html?variant=B)。原型仅演示已确认的导航与会话边界，不构成生产实现或新的业务状态来源。

## 5. 测试决定（Testing Decisions）

**主验收缝隙**是平台统一业务入口的外部行为：以已认证用户或可信绑定发送人的请求进入，观察用户可见结果以及持久化后的 Session、Run、消息、确认和投递事实，再通过重启后的读取验证。该缝隙同时覆盖平台与 AgentScope 的映射；不以内部方法调用次数、私有状态字段或某一种表拆分作为业务正确性的判据。未来渠道适配器先做验真、归一化和回执契约验证，再通过同一业务入口复用业务场景。

评审和后续验收至少覆盖：

1. 两名用户、同一用户两段会话、两名数字员工之间的所有者、发布版本、状态槽及长期记忆边界。
2. 同一 Session 连续输入、并发新输入、等待确认时输入与当前 Run 的确认/取消；只产生允许的 Run。
3. 浏览器中断与重连、部分回答中断、主动取消、外部写操作在取消前已发出的结果核对。
4. 服务重启后未完成 Run 待核对，不重复模型或会议写操作；AgentScope 状态缺失时暂停新 Run。
5. 确认参数变化、十分钟过期、重复点击和账号/授权变化后，写工具均不能凭旧确认执行。
6. 新版本发布不改变旧会话；旧版本停用、会话归档/恢复和员工授权撤销只改变允许的新操作，不改写历史。
7. 单条旧会话升级成功：旧消息仍在原会话，新会话可查看来源；首次新版模型调用实际包含全部原始对话及可读取素材，旧内部记录不进入。
8. 旧会话有活动 Run、历史超出新版上下文、图片等必需素材失效、模型首次调用失败、用户重复点击时，旧会话不会被错误转只读或出现多个不一致的新会话。
9. 首次新版调用没有提前压缩；其后的普通对话达到约 80% 阈值时使用框架压缩，而平台原始消息仍完整可读。
10. 一期文字与图片从 Web 上传私有对象存储、SQL 接纳、模型运行、重启恢复到历史展示的完整路径；签名过期重新鉴权，原件缺失、版本或摘要错误须识别，不能宣称恢复成功。
11. 未绑定渠道发送人、解除绑定、同一私聊首次/后续输入、群聊 peer 与 sender 分离时的路由与授权边界。
12. Web 在运行中的 Run 旁只选择已完成消息续传；目标渠道已有/没有可用 Session、部分内容未选择、重复投递和结果不明的可见行为。
13. Run 已完成但渠道回复发送失败时，重试不重新执行数字员工或会议写操作；解绑后的在途投递结果仍可核对。
14. 用户更正历史只追加新消息；固定管理员可直接查看完整聊天正文、图片、历史会话、Run 过程输出和会议写操作记录，普通用户不能越权查看他人的会话。管理员查看留访问审计，也不能代用户发起 Run 或会议工具调用。
15. 用户切换数字员工后只看到该员工获授权的会话，并恢复其最近查看会话；员工间历史、Run 和 AgentScope 状态不串用。多次升级的版本历史完整列出所有前序版本，选择历史版本后保持只读查看。

身份与会话表的结构验收分别见各自建表记录；旧版结构证据不替代通用化后重验，它们均不构成 Session/Run、对象存储或工具执行行为已经通过的证据。AgentScope 多模态 SQL 往返、压缩触发、模型上下文估算与首次升级调用、未来渠道实际回执语义均需各自运行验收。本次仅产出规格，未运行上述验收。

## 6. 范围外（Out of Scope）

- 本文只规定业务规则；Session/Run/消息与操作的初建 DDL 由关联建表规格定义，不在本次实现应用接口、未来投递表或既有数据迁移，也不变更已有身份表。
- 已确定素材原件使用私有对象存储、SQL 保存元数据；对象存储产品、限额、租约/清理互斥和访问方式须在实施时配置及验收，不能把“框架可序列化”或建表成功当成方案已落地。
- 一期不实现钉钉、飞书、企业微信等外部渠道、群共享会话、自动企业通讯录绑定，也不承诺外部渠道的图片/音频/视频/文件可收发。
- 一期不提供永久删除会话按钮。2026-10-23 用户明确一期暂不考虑数据保留策略，留存期限、自动过期及彻底删除规则延后，不作为一期验收前置。
- 不提供管理员代普通用户发送消息、确认写操作或调用会议工具的入口。
- 不自研对话压缩算法，也不以长期记忆替代原始消息或会议系统事实。
