## 1. 已确认的行为与本稿范围

| 本轮决定 | 物理设计中的表达 |
| --- | --- |
| Q2：允许保存不完整草稿 | 草稿按修订保存；结构、权限和容量先校验，完整必填和有效引用在发布前校验。未就绪草稿不能发布。 |
| Q3：与当前版本有效内容相同不造空版本 | 返回当前版本，只追加 `NO_CHANGE` 发布收据，不分配发布号，不插入版本或 Skill 快照。 |
| Q3：A→B→A 形成新发布 | 内容相等只与当前版本比较；历史内容摘要不设唯一索引，改回 A 后正常生成新版。 |
| Q4：仅版本级可用／停用，可重新启用 | 版本配置不可变；可用性单独更新并审计。恢复旧版不改变员工当前版本指针，不增加员工整体启停开关。 |
| Q5：补齐身份审计中的授权对象 | 既有 `identity_audit_event` 扩展员工、授权记录、授权版本前后值四列；授权事实不另存第二套审计。 |
| Q6：停用版本的同内容发布仍保持停用 | 返回原版并明确其仍停用；恢复必须走显式重新启用操作。 |

继续沿用：一个会议室员工、Web 唯一入口、每员工一份草稿、员工统一发布、Session 固定版本、Run 继承 Session 版本、用户×员工授权、固定管理员仅免此层显式授权。发布版本停用只阻止相关新 Run，不改写历史或取消在途 Run。无审批、强制测试门槛、独立 Skill 发布或回滚入口。

## 2. 通用物理约定

- 新八表使用 InnoDB、MySQL 8.0.16+，默认 `utf8mb4_0900_ai_ci`；与[现有 MySQL 规约](../用户与管理员/阿里巴巴MySQL规约核对.md)一致，不建物理外键、级联、触发器或存储过程。
- 每表包含 `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`、`gmt_create DATETIME(6)`、`gmt_modified DATETIME(6)`，三列均非空。下列字段表不重复它们。全部业务时间由应用按 UTC 写入，每表每列有中文注释。
- 下文 `ID/REV` 均为 `BIGINT UNSIGNED`；引用 ID、修订与版本值有值时必须大于 0，只有明确允许的计数可以为 0。索引名使用 `uk_`、`idx_`，约束名使用 `chk_`；VARCHAR 索引明确写全长，不能用缩短前缀放宽业务唯一性。
- `ASCII(n)` 表示 `VARCHAR(n) CHARACTER SET ascii COLLATE ascii_bin`；代码、请求标识和英文状态按此比较。`SHA` 表示 `BINARY(32)`；对外展示时才转为 64 位十六进制。
- JSON 列只负责存合法 JSON；顶层对象由 `CHECK(JSON_TYPE(...)='OBJECT')` 限制。配置 Schema、未知字段、引用、字段间语义及敏感值检查由应用完成，不能把 JSON 类型当作配置有效性证明。
- 所有不可变内容采用只追加的服务接口与数据库权限；普通 `CHECK` 不能阻止管理员直接 UPDATE，也不能验证摘要是否由真实内容计算。

## 3. 八张表的字段与约束

### 3.1 `digital_employee`：稳定员工身份

| 字段 | 类型／可空／初值 | 含义 |
| --- | --- | --- |
| `employee_code` | `ASCII(64)`，非空 | 稳定业务代码，服务校验小写英文、数字和连字符；创建后不改派。 |
| `display_name` | `VARCHAR(100)`，非空 | 展示名称，去除两端空白后不得为空。 |
| `description` | `VARCHAR(1000)`，非空，空串 | 展示说明，不承担配置正文。 |
| `current_release_id` | `ID`，可空 | 后续新会话选择的发布版本；未发布时为空，可指向已停用版本，但此时不得新建可运行会话。 |
| `last_release_no` | `REV`，非空，0 | 本员工已分配的最大发布号；只有实际创建发布版本才加一。 |
| `row_version` | `REV`，非空，1 | 员工元数据和版本指针的并发观察值，不替代草稿修订或发布可用性修订。 |

唯一键：`uk_employee_code(employee_code(64))`。CHECK：代码／名称非空，`row_version>0`，当前发布 ID 有值则为正；尚无发布时允许 `last_release_no=0`。服务和巡检保证当前版本属于本员工，且最大发布号与真实发布记录一致。此表不增加 `employee_status` 或删除标记。

### 3.2 `employee_draft`：唯一可变草稿

| 字段 | 类型／可空／初值 | 含义 |
| --- | --- | --- |
| `employee_id` | `ID`，非空 | 所属员工。 |
| `draft_revision` | `REV`，非空，1 | 每次成功保存加一；客户端携带期望修订防覆盖。 |
| `config_schema_version` | `INT UNSIGNED`，非空，1 | 草稿结构及其规范编码版本。 |
| `config_json` | `JSON`，非空 | 完整草稿文本包，可暂缺模型、指令等必填内容；不是运行时配置来源。 |
| `dependency_sha256` | `SHA`，可空 | 本修订保存时解析到的模型、工具接入和平台静态规则的有效依赖指纹；无法完整解析时为空。 |
| `saved_by` | `ID`，可空 | 最近一次人工保存的固定管理员；仅未人工保存的初始化草稿允许为空。 |

唯一键：`uk_employee_id(employee_id)`。CHECK：员工 ID、修订、Schema 版本为正，JSON 为对象，`saved_by` 有值则为正。保存事务、草稿修订提升及保存审计一起提交。

初始化草稿可以是结构正确的空配置；不自动形成发布。`dependency_sha256=NULL` 不表示任意依赖均可使用，而表示未具备发布条件。保存时平台在锁外准备依赖快照，提交前复核配置目录观察值；内容或依赖变化必须保存出新修订。发布不得首次从“今天的最新配置”补全某个旧修订的空指纹。

### 3.3 `employee_release`：不可变配置与独立可用性

| 字段 | 类型／可空／初值 | 含义 |
| --- | --- | --- |
| `employee_id` | `ID`，非空 | 所属员工。 |
| `release_no` | `REV`，非空 | 员工内从 1 起的发布号。 |
| `source_draft_revision` | `REV`，非空 | 真正创建本版的草稿修订；不会随草稿继续修改或无变化发布而改写。 |
| `config_schema_version` | `INT UNSIGNED`，非空 | 发布清单结构与有效配置编码版本。 |
| `config_json` | `JSON`，非空 | 已解析的模型配置、指令、Skill 快照引用、工具绑定版本及平台静态约定。 |
| `dependency_sha256` | `SHA`，非空 | 创建本版时固定的有效依赖指纹。 |
| `config_sha256` | `SHA`，非空 | 不包含生成 ID 等字段的有效配置摘要，定义见第 5 章。 |
| `manifest_sha256` | `SHA`，非空 | 包含真实快照引用的最终 `config_json` 清单摘要。 |
| `published_by` | `ID`，非空 | 发布管理员。 |
| `published_at` | `DATETIME(6)`，非空 | 正式发布提交时的业务时间。 |
| `availability_status` | `ASCII(16)`，非空，`AVAILABLE` | `AVAILABLE` 或 `DISABLED`。 |
| `availability_revision` | `REV`，非空，1 | 可用性变更的并发修订；每次真实状态变化加一。 |
| `availability_changed_by` | `ID`，非空 | 最近一次可用性状态的设置人，初值为发布人。 |
| `availability_changed_at` | `DATETIME(6)`，非空 | 初值为发布时间。 |

唯一键：`uk_employee_release_no(employee_id,release_no)`、`uk_employee_source_draft_revision(employee_id,source_draft_revision)`。普通索引：`idx_employee_config_sha256(employee_id,config_sha256)`、`idx_employee_availability(employee_id,availability_status(16))`。

CHECK：数值引用和版本为正，JSON 为对象，可用性仅两态。配置、来源、摘要、发布人和发布时间不可改写；只有可用性相关四列及 `gmt_modified` 可受控更新。**不建立 `(employee_id,config_sha256)` 唯一键。** 无变化发布产生零条新版本，符合“每个来源修订最多一版”，不要求每修订都产生版本。

不可变性以成功提交为界：构造新版本的同一未提交事务内，可以先取得版本／Skill 主键再回填完整清单和摘要；提交前必须检查全部字段完整，任何占位材料都不得单独提交或对外可见。之后不能为补资源或修清单原地改写已发布内容。

| 字段 | 类型／可空 | 含义 |
| --- | --- | --- |
| `tool_binding_version` | `ASCII(64)`，非空 | 不改派的绑定标识，兼容既有 `tool_operation`；新标识由服务端生成。 |
| `provider_key` | `ASCII(64)`，非空 | 受控服务提供方。 |
| `tool_name` | `ASCII(128)`，非空 | MCP 工具名称。 |
| `binding_schema_version` | `INT UNSIGNED`，非空 | 绑定 JSON 与摘要的编码版本。 |
| `binding_json` | `JSON`，非空 | 固定目标、传输、非敏感参数、凭证引用、输入契约、参数规则、Adapter、身份注入、确认、幂等及核对能力。 |
| `binding_sha256` | `SHA`，非空 | 完整绑定内容的规范摘要，不含秘密值。 |

相同摘要只用于查找候选，核对规范内容后可复用；不要求绑定摘要全局唯一，不假定哈希命中自动证明内容相等。发布清单直接保存选择的绑定版本，不另建第九张发布工具连接表。后端改地址、契约、身份或 Adapter 不能覆盖旧绑定；秘密值轮换保持凭证引用及原目标／身份语义。

### 3.5 `employee_use_grant`：当前授权关系

| 字段 | 类型／可空 | 含义 |
| --- | --- | --- |
| `user_id`、`employee_id` | `ID`，非空 | 被授权用户与员工。 |
| `grant_status` | `ASCII(16)`，非空 | `ACTIVE` 或 `REVOKED`。 |
| `granted_by`、`granted_at` | `ID`／`DATETIME(6)`，非空 | 最近一次真实授予或再授予。 |
| `revoked_by`、`revoked_at` | `ID`／`DATETIME(6)`，可空 | 当前处于撤销状态时的操作者与时间；再授予后清空，历史由身份审计保存。 |

唯一键：`uk_user_employee(user_id,employee_id)`。普通索引：`idx_employee_grant_status(employee_id,grant_status(16))`。CHECK：引用为正；`ACTIVE` 时撤销两列均空，`REVOKED` 时两列均非空。没有关系行即未授权，撤销从未授权的关系不虚构一次授予。

真实授予、撤销、再授予与 `platform_user.authorization_version+1`、身份审计在同一 SQL 事务提交。重复授予 ACTIVE、重复撤销 REVOKED／不存在关系属于无变化，不提升版本；固定管理员免此层显式授权，不通过创建虚假 grant 表达角色权限。

### 3.6 `employee_configuration_audit_event`：配置审计与成功收据

| 字段 | 类型／可空 | 含义 |
| --- | --- | --- |
| `actor_user_id`、`employee_id` | `ID`，非空 | 可信管理员与已定位的员工；无法定位对象的拒绝记入口日志，不能造孤儿引用。 |
| `action_code` | `ASCII(32)`，非空 | `DRAFT_SAVE`、`EMPLOYEE_PUBLISH`、`RELEASE_DISABLE`、`RELEASE_ENABLE`。 |
| `outcome` | `CHAR(7) CHARACTER SET ascii COLLATE ascii_bin`，非空 | `SUCCESS` 或 `FAILURE`。 |
| `result_code`、`reason_code` | `ASCII(32)`／`ASCII(64)`，可空 | 成功结果如 `SAVED/CREATED/NO_CHANGE/DISABLED/ENABLED`；失败记录受控原因。 |
| `draft_revision` | `REV`，可空 | 保存成功后的修订，或发布请求使用的草稿修订；不是所有事件都必填。 |
| `employee_release_id` | `ID`，可空 | 发布实际返回版本或可用性操作的目标版本。 |
| `request_id` | `ASCII(128)`，非空 | 一次管理命令的稳定请求键，接口校验长度与字符集。 |
| `request_sha256` | `SHA`，非空 | 操作者、员工、动作、期望修订及请求输入的稳定指纹。 |
| `success_request_id` | `ASCII(128)`，可空生成列 | 仅 `outcome='SUCCESS'` 时取 `request_id`，否则为 NULL。 |
| `change_summary` | `JSON`，可空 | 受控字段名、是否变化、前后修订等脱敏摘要，不放指令、Skill 全文、密钥或任意请求副本。 |
| `occurred_at` | `DATETIME(6)`，非空 | 事件时间。 |

唯一键提案：`uk_actor_success_request(actor_user_id,success_request_id(128))`；成功请求在同一管理员范围内不能用于其他动作／员工。普通索引：员工＋时间、发布 ID、请求 ID。失败行生成 NULL，允许同一请求的多次失败尝试各自留记录；不得把整表的 `request_id` 简单设为全局唯一。

CHECK 仅约束动作／结果集合、正数引用、JSON 顶层对象及成功结果／失败原因的基本配对。各动作必填哪些修订和结果引用由应用定义。`NO_CHANGE` 的请求修订可以不同于结果版本的真实来源修订，不能错误要求相等。审计是追加事实，成功收据和实际变更同事务提交；重复请求不更新旧审计。

## 4. 配置结构与文本包的具体提案

草稿与发布各用一份严格的 Schema v1：

| 分组 | 草稿 | 正式发布 |
| --- | --- | --- |
| `configSchemaVersion` | 固定为 1，与列值一致 | 固定为 1，与列值一致 |
| `model` | 平台模型引用及参数，可以未填写完整 | 已解析的配置引用、实际模型 ID、非敏感连接／凭证引用、参数与必要修订 |
| `instructions` | 文本，可为空 | 完整员工指令，必须非空 |
| `skills` | 入口原文与 `resources[{path,text}]`；不完整文本可存，解析问题作为未就绪提示 | `[{name,snapshotId,packageSha256}]`，内容在正式明细表 |
| `tools` | 已接入服务和子工具选择 | `[{providerKey,toolName,toolBindingVersion,bindingSha256}]` |
| `workspace`、`memory` | 平台统一静态规则引用，不能编辑成运行资料 | 固定模板／策略及必要修订，不含任何用户记忆或文件正文 |

这些是顶层字段清单；具体模型参数仅接受该平台模型适配器声明的白名单，工具契约与参数 Schema 由绑定快照给出。草稿可以留空，但不能引入任意未知顶层字段、密钥或执行脚本。正式包先经固定版本解析器校验，未支持的 metadata 表达拒绝发布并说明原因，不截断为“只有名称描述”。

路径提案：使用 `/` 分段、Unicode NFC 文本，拒绝绝对路径、盘符、反斜线、空段、`.`、`..`、控制字符、尾部空格和等价冲突；拒绝把 `SKILL.md` 当作额外资源重复保存。**不靠静默重命名修复冲突**，原文引用的路径必须可解析到本包中的实际资源。默认排序规则还会将部分重音差异视为相等，这是本提案的保守去冲突规则；在不启用 shell 的真实读取验收中复核。

正文和资源使用严格 UTF-8 解码，入口 BOM 在导入时明确提示处理；文本一经保存不静默改换行、空白或内容，不把 LF 与 CRLF 不同的文本声称为字节相同。数据库往返须验证中文与换行原样保留。

建议的可配置初始限额：每员工最多 10 个 Skill；每 Skill 最多 100 份资源；入口 256 KiB、单份资源 1 MiB、单包 8 MiB、草稿／整次发布准备材料 16 MiB。全部按 UTF-8 字节计，不是框架硬限制，也不是模型上下文承诺；只约束新保存／发布，调低限额不能使合法历史版本被重新解释为可变内容。正式接入时联合校准 HTTP、JDBC 包大小和模型工具读取限制。

## 5. 内容相等与完整性摘要

为避免生成不同的快照 ID 就被判成不同配置，明确使用两种摘要：

1. **`config_sha256`：有效内容摘要。**涵盖实际模型请求配置、员工指令、Skill 名称与完整包摘要、工具绑定完整内容摘要、Workspace／Memory 静态约定。排除发布主键／序号、Skill 快照 ID、来源草稿修订、操作者、请求号、时间、可用性状态和可用性修订。
2. **`manifest_sha256`：最终清单摘要。**对已经写入真实快照 ID、工具绑定版本等引用的最终 `config_json` 规范字节计算。读取时还须验证引用归属、全部正文和资源摘要，不能只校验这一个摘要。

Schema v1 的规范编码提案：拒绝重复 JSON 键，按 Unicode 码点顺序排列对象键，列表保留业务顺序；作为集合的 Skills、工具和资源清单先按稳定名称／路径排序并拒绝重复。数字按精确十进制去除无意义尾零，不用浮点近似改写；字符串采用确定的 JSON 转义和 UTF-8，不归一化正文。具体实现应使用跨端测试向量，不依赖 MySQL JSON 返回顺序或默认 `Map.toString()`。

Skill 包编码使用带版本标识和长度的结构：入口原文字节、完整 metadata 的规范字节、按路径排序的每份资源路径／字节长度／内容摘要。工具摘要同样涵盖绑定 Schema 版本和完整语义，不含创建人、时间、标识本身或秘密值。摘要只作候选筛选，决定复用或 `NO_CHANGE` 前仍校验实际规范内容及引用完整性。

## 6. 请求重试、发布和可用性事务

### 6.1 成功收据先于重新执行

配置管理请求携带稳定 `request_id` 和期望修订；先验证当前固定管理员资格，再查该管理员的成功收据。同键同请求返回原处理结果；同键不同动作／对象／参数拒绝。返回收据同时区分“当时处理结果”和“今天的当前版本／可用性”，不把旧收据当作当前状态。

没有成功收据的新请求才执行当前修订检查。保存失败或发布失败不能留下伪成功收据；失败审计允许单独追加。提交结果不明时先在新连接核对已提交收据，仍无法判定则返回待核对，不分配新请求号继续发布。

### 6.2 保存与发布

1. 保存允许不完整配置；在锁外准备依赖指纹，在管理员用户→员工→草稿锁下核对期望修订及依赖观察值，保存新修订并写审计。
2. 发布只能引用已保存的当前草稿修订。依赖指纹必须非空，准备时与当前受控配置目录相符；依赖已变则要求先重新保存出新修订。准备前后仍需再检查，不能只防本次准备期间变化。
3. 在锁外解析并验证完整 Skill、模型引用与工具绑定；SQL 事务内重新按管理员用户→员工→草稿加锁，复核修订与依赖。本期文本 Skill 的正式内容与版本统一进 SQL，不在持有行锁时做外部模型／MCP 网络调用。
4. 与当前版的有效内容比较。相同则只插 `SUCCESS/NO_CHANGE` 审计并返回其 ID／当前可用性，不增发布号、不写快照、不切指针、不改变停用状态。
5. 内容不同则在员工锁下分配下一发布号，插入／复用不可变绑定、插入版本及全部 Skill 明细、计算最终清单摘要、追加成功收据并切换当前指针；一起提交。A→B→A 只比较当前 B，因此创建新 A。

“同一修订最多一版”的唯一键只约束真实版本；草稿的依赖指纹补上 `NO_CHANGE` 没有版本行时的缺口。无变化收据中的请求修订与结果版本的真实来源修订可以不同，两者不能互相覆盖。

### 6.3 可用性变更

按管理员用户→员工→目标发布版本加锁，核对目标归属和期望 `availability_revision`，再改变状态、增加修订并追加审计。重复设置同一状态无额外状态变化；恢复 V1 不切换当前 V2。新 Run 与版本停用通过员工行锁排序：停用先提交则新 Run 被拒绝；Run 已接纳则不追溯取消它，工具调用仍执行原有实时身份和授权检查。

停用、恢复和新发布不能原地修改配置；默认版本停用时不猜选旧版。涉及批量用户或多个员工不在本轮范围内。

## 7. 身份审计四列扩展与授权事务

在既有 `identity_audit_event` 设计上增加：

| 字段 | 类型／可空 | 用途 |
| --- | --- | --- |
| `employee_id` | `ID`，可空 | 授权目标员工。 |
| `grant_id` | `ID`，可空 | 已存在的授权关系；首次授权失败或撤销从未授权关系时允许为空。 |
| `authorization_version_before` | `REV`，可空 | 真实变更前或无变化观察到的用户级授权版本。 |
| `authorization_version_after` | `REV`，可空 | 真实变更后版本；无变化时等于 before。 |

增加普通索引提案：`idx_target_employee_occurred(target_user_id,employee_id,occurred_at)`、`idx_grant_id(grant_id)`。通用 CHECK：版本前后同空同非空；有授权关系或版本时员工非空；有值均为正；after 不小于 before。不依靠一条条件含糊的 CHECK 强迫所有失败／无变化也增加版本。原有非授权审计四列全空仍可写。

动作语义由服务统一约束：真实 `EMPLOYEE_GRANT/EMPLOYEE_REVOKE` 成功时四列完整、`after=before+1`；无变化返回 `NO_CHANGE`，版本前后相同且不影响记忆任务；失败不伪造成功后版本或不存在的 grant。审计中 grant 必须属于同一目标用户和员工，历史版本值不要求永久等于用户当前值。

授权命令携带 `expectedAuthorizationVersion`。事务内按管理员用户和目标用户 ID 升序取得用户锁，再锁员工／关系；**先校验期望版本，再判断是否无变化**。真实变化、版本提升和审计同事务提交。旧授权请求即使 `request_id` 相同，也不能在撤销／再授予后复活旧命令。

既有身份审计的 `request_id` 仍是可空、非唯一的关联标识，不冒充配置审计的成功收据键；本稿不为它新增另一套授权幂等字段。授权版本冲突返回重新加载，由当前关系确定新操作。固定管理员按角色免此层授权，不通过 grant 行表达或改变其使用权。
