## 1. 范围与已确认决策

沿用一期单企业、Web、一个会议室数字员工、单节点低并发边界。会话、Run、消息、发布、工具确认等既有规则分别以[会话规格](../会话运行与消息/业务会话运行消息与跨渠道续传设计规格.md)、[会话建表规格](../会话运行与消息/一期会话运行消息建表规格.md)、[配置与发布决策](../数字员工配置与发布/一期配置与发布决策.md)和[Skills 版本装载设计](../数字员工配置与发布/Skills_MySQL管理与版本装载设计.md)为准。

| 问题 | 用户确认的决定 |
| --- | --- |
| Q1 | “我的记忆”显示当前用户、当前员工的一份完整偏好文档，支持查看、整份修改、保存和清空。 |
| Q2 | 不同 Session 可以并行；同 Session 仍最多一个活动 Run，等待确认只占本 Session。共享记忆写入另行协调。 |
| Q3 | 临时计划、处理中间文件和生成资料默认只供所属会话；跨会话须显式引用。 |
| Q4 | 清空当前记忆后可从之后的新输入重新学习；旧日记、摘要和排队任务不能恢复被清空的偏好。原始聊天不随之删除。 |
| Q5 | 只从已成功 Run 的正式对话提炼长期个人偏好；失败、取消、待核对轮次和工具日志不作为自动学习输入。 |
| Q6 | 用户手工更正优先；历史和推断不能覆盖手工内容，之后新消息明确表达变化时才可相应更新。 |
| Q7 | 正在执行的 Run 可用启动时记忆快照完成；修改从下一次新 Run 生效，旧任务不得回写被更正或清空的内容。 |
| Q8 | 记忆更新异步执行、独立记录状态和重试；其失败不推翻已完成回答，也不重新执行会议操作。 |
| Q9 | AgentState 使用独立 MySQL 框架后端；长期记忆正文与日记默认通过 Workspace 保存到框架 JDBC KV，文本运行资料优先复用该文件存储能力；平台另保留必要控制元数据；文件原件用私有对象存储与 SQL 索引，本地仅缓存。 |
| Q10 | 每次手工保存或清空开启新记忆代次；旧日记、未完成旧任务立即退出有效范围，即使因此舍弃尚未汇总的旧偏好。物理销毁和备份期限由 #10 确定。 |
| Q11 | 同一用户、同一员工跨会话显式引用资料时固定当时内容快照，保留来源；来源后续修改不改变已引用内容。 |
| Q12 | 明确偏好冲突按用户输入的服务端接纳顺序判定，较晚表述优先；无法判定时保留现值并请用户澄清。 |
| Q13 | 固定管理员成功留访问审计后可读记忆、日记和会话运行资料，不能代用户修改或清空记忆；审计失败不返回内容。 |
| Q14 | 员工使用授权撤销后，账号仍有效的本人可查看、更正、清空已有记忆；停止新自动学习。再授权不重放撤销期间旧任务；停用账号不能登录。 |
| Q15 | 重启后重新查权、去重，恢复成功 Run 对应的有效代次待处理记忆任务；不重放业务 Run 或会议操作。必需会话状态或资料不能核验时暂停该会话。 |

“清空”“旧代次失效”在本文表示退出在线有效读取、检索和自动学习范围；不表示备份、审计及所有底层副本已经物理销毁。2026-10-23 用户明确一期暂不考虑数据保留策略，[#10](https://github.com/BeyondzychenProton/agentscope-brain/issues/10) 的留存期限及物理销毁规则延后，不作为一期前置；在线清空、旧代次隔离及恢复时核验有效代次的规则继续适用。

2026-10-21 的实现取舍是：框架优先承担内容保存、提取、合并和检索；平台集中落实可信身份、成功来源、用户更正/清空、任务恢复及审计。原有 Q1～Q15 的用户可见规则继续有效，不能用原生 hooks 的默认行为替代这些规则。逻辑记录不直接等同于新增物理表，具体映射见第 3 节及第 9 节。

## 2. 数据面、隔离键与权威存储

| 数据面 | 逻辑归属与隔离键 | 权威存储及规则 |
| --- | --- | --- |
| 平台业务事实 | UserId、employeeId、Session、Run 及固定 releaseId | 既有平台 MySQL 表；正式消息和工具操作不由框架状态或记忆代替。 |
| AgentState | 可信 UserId + 服务端 state_session_key | 独立 MySQL 框架状态后端。Session 固定员工和发布版本，状态槽不复用。 |
| 长期偏好、提炼日记 | UserId + employeeId + 有效 memory_generation | 默认复用框架 JDBC KV（默认表名 `agentscope_store`，可配置）保存逻辑 `MEMORY.md` 与 `memory/` 日记。同一用户、员工跨 Session 和发布版本共享；检索仅访问当前有效代次，不另存一份可独立修改的记忆正文。 |
| 会话运行资料 | UserId + employeeId + business_session_id；记录来源 run_id | 文本优先通过 Workspace 复用框架 JDBC KV，文件原件在私有对象存储，平台维护必要归属与引用元数据；计划、任务、中间资料、框架日志不因同用户而跨会话可见。 |
| 只读定义资产 | employeeId + employee_release_id | 已确认的发布配置和 Skill MySQL 快照。用户记忆及运行文件不进入发布。 |
| 运行目录与缓存 | 完整绑定、内容修订和摘要 | 可重建本地缓存。缓存丢失不能改变内容权威、清空结果或隔离范围。 |

### 2.1 AgentState 绑定

沿用既有映射：从可信业务 Session 取得 `state_session_key`，原样传入框架逻辑 `sessionId`；可信 `platform_user.id` 转为框架 `userId`。MySQL 状态实现内部才编码 `userId:sessionId`，平台不能重复预拼。状态槽采用服务端生成、不复用的 32 位小写十六进制随机值，浏览器与模型均不能指定。

业务 Session 保存 owner、员工、固定发布版本和状态槽；Run 继承。`state_version_before/after` 的可空观察约束保持不变，直到真实集成证明版本能力。首次尚无状态与已运行 Session 状态异常缺失必须区分。

### 2.2 Workspace 路由

下列为逻辑 namespace 示例，不是已实现的表名或文件系统路径：

```text
memory:   [employees, employeeId, users, UserId, generations, generation]
runtime:  [employees, employeeId, users, UserId, sessions, businessSessionId]
release:  [employees, employeeId, releases, releaseId]
```

会话运行 namespace 不需要再靠发布版本分槽，因为 Session 已固定发布版本；内容元数据仍记录该版本便于核对。共享记忆不把发布版本作为隔离键，记忆格式版本也不能冒充员工发布版本。

框架 `MEMORY.md` 和 `memory/` 接受控共享记忆后端；会话日志、任务、计划及其他可写资料接会话后端；定义资产从固定发布来源只读装载。路径名仅用于路由，不能成为授权依据。所有者、Session、Run、发布版本和记忆代次都从服务端绑定取得，不能接受前端路径中的身份作为可信身份。

真实隔离须覆盖读、写、追加、枚举、全文检索、下载和路径规范化，不能只验证 `read`。用户和模型不能借本地模板、其他 Skill 来源或缓存覆盖固定发布内容；空记忆必须显式表示为“有效且为空”，不能回退到旧本地 `MEMORY.md`。

## 3. 逻辑实体与 MySQL 元数据

记忆代次 `generation` 标识一次手工保存/清空后建立的有效范围，不复用；文档修订 `document_revision` 标识该代次内的内容变化，每次有效自动写入也推进修订。读写使用二者组成的版本，不能只比较其中一个。文档修订优先评估映射到框架 KV 记录的 `version`，不平行维护两套可独立变化的修订计数；#9 必须证明所有写入口、同内容重试及快照读取均满足本协议，不能直接把默认 `put` 当作条件提交。记忆更新任务只更新偏好及日记，不是新的业务 Run。

以下逻辑记录用于落实协议，不意味着已经增加同名物理表。[#9 完整实体评审](https://github.com/BeyondzychenProton/agentscope-brain/issues/9)负责表拆分、类型、索引、唯一约束、事务实现和最终 DDL。物理设计默认复用框架 KV 保存正文及日记，取消“为 `memory_document` 单独建正文表”的默认假设；平台控制记录只保留框架未表达的业务事实，审计优先复用现有机制。本轮不确定新增表数，不修改 SQL。

| 逻辑记录 | 必需元数据 | 约束 |
| --- | --- | --- |
| 记忆控制记录 `memory_profile` | id、user_id、employee_id、generation、有效文档 KV 定位及文档修订映射、memory_schema_version、policy_version、输入顺序分配/截止信息、更新时间 | 用户与员工唯一；只保存必要控制元数据，不复制正文。有效代次和修订由受控协议推进；不存在的首次初始化与已有记录异常缺失分开处理。 |
| 记忆文档/日记 `memory_document`（逻辑概念） | 框架 KV 中的文档内容，以及归属、generation、逻辑路径、修订、摘要、来源索引和更新时间的映射 | 默认由框架 KV 承载，不另建同义正文表；元数据可存于受控 KV 内容或平台关联记录，由 #9 明确唯一权威位置。当前整份偏好文档只有一个有效修订；日记有任务/来源去重标识；清空是有效空文档，不触发默认初始化。 |
| 记忆更新任务 `memory_update_job` | job_id、user_id、employee_id、source_session_id、source_run_id、源正式消息引用与校验信息、用户输入顺序、generation、基线文档修订、来源及任务创建时的授权版本/授权生命周期凭据、策略/格式版本、候选结果定位/摘要及来源证据、状态、尝试次数、失败原因、领取信息 | 同一来源 Run、代次和任务种类幂等；只处理平台已确认成功的来源。复用既有正式消息，不复制完整聊天；候选不成为另一份权威正文。任务存在不代表内容已提交。 |
| 会话运行资料 `workspace_entry` | entry_id、user_id、employee_id、session_id、来源 run_id、release_id、逻辑路径、资料类型、内容修订、文本 KV 定位或对象定位、类型/长度/摘要 | 文本优先复用框架 KV；平台只维护必要归属/引用，所有者与 Session 一致，不重复存一份可独立修改的全文。持久对象位置不保存临时签名 URL。 |
| 资料快照引用 `workspace_snapshot_reference` | source_entry_id、固定源修订和摘要、源 Session/Run、target_session_id、归属、目标快照/对象定位、创建人及时间 | 来源、目标均属当前用户与同一员工；固定内容，不读取来源“最新版本”。目标保留可恢复快照与来源信息。 |
| 记忆与资料审计 | request_id、actor_user_id、操作类型、subject_user_id、employee_id、必要的 Session/Run/任务、代次与修订前后值、摘要、结果和时间 | 优先复用现有审计机制，按需补动作码与关联字段；追加记录，不复制完整旧偏好文档。内容访问审计必须先成功，才能返回管理员可读内容。 |

Run 还需可核对地关联启动时的 `memory_profile_id`、`memory_generation_at_start`、`memory_document_revision_at_start` 和所用格式/策略版本。字段落在 Run 扩展还是独立绑定记录，由 #9 决定；不能只存于进程变量。用户在一轮期间修改记忆，不篡改该轮已经读取的快照。

来源索引用于说明某段偏好来自手工基线还是哪条用户输入，并支持冲突核对。内部来源信息不要求用户按条目编辑：界面仍是一份完整文档。只有模型输出、没有可验证正式输入来源的“明确偏好”不能被当作用户的新表述。

## 4. 一次 Run 的记忆与资料绑定

1. 沿既有顺序检查账号、员工使用权、Session 归属和固定发布版本；同 Session 的活动 Run 约束保持不变，不增加用户与员工范围的全局 Run 占位。
2. 在接纳用户输入时，为该用户与员工范围内的正式用户输入确定可比较、唯一且持久的服务端接纳顺序。不得用后台任务完成时间、模型响应时间或客户端时钟替代；并发分配和同序冲突由 #9 落实。
3. 创建 Run 时固定当前有效记忆代次、文档修订及内容快照，绑定当前 Session 运行 namespace；如果与手工编辑并发，事务/版本检查保证取到一致的前版或后版，不能拼接两版内容。
4. 按 Session 固定发布版本装载只读配置与 Skill。运行读取当前有效偏好，旧对话中的偏好属于历史陈述，不自动恢复为现行偏好；下一新 Run 须更新其有效记忆视图，不沿用缓存的过代文档。
5. Run 仍按既有 AgentState 与正式消息规则完成。记忆任务不参与判断该业务 Run 是否成功；一笔会议是否成功仍由会议系统及结构化操作记录核对。

可以缓存只读发布资料和经确认可并发使用的存储组件；带当前 AgentState、上下文或任务进度的可变对象不能直接跨并行 Run 共享。具体 Harness 实例复用方式须证明会话隔离及并发行为，不能因属于同一用户就假定有状态实例可安全复用。

原始对话的保留及跨版本严格全量导入规则不变。清空偏好不是从既有聊天正文中抹除那句话；平台必须将“历史说过什么”与“当前有效偏好”分开呈现和输入，自动学习更不能从旧上下文重建已清空内容。模型是否正确遵守最新偏好仍需实际行为验收，不能仅凭提示词或 namespace 宣称已经保证。

## 5. 手工保存、清空与禁止复活

### 5.1 手工操作

1. 本人带读取时的代次、文档修订和本次操作标识提交整份保存或清空。服务端重新认证和查所有者；撤销员工使用授权但账号仍有效的本人保留这项数据管理权。同一请求重试先按操作标识与内容摘要核对已有结果，重复点击不再换代，相同标识携带不同内容须拒绝。
2. 以当前代次和修订作条件更新。修订已变则提示重载或比较差异，不静默覆盖另一浏览器或自动学习刚提交的内容。
3. 通过受控提交协议，保存新代次的完整文档（清空则为显式空文档），建立手工基线与输入截止信息，并一致地激活新代次、登记操作结果和追加变更审计。只有文档可核验且激活成功后，才向用户确认已保存。正文默认复用框架 KV，不能假设其独立 JDBC 连接自动加入平台 SQL 事务；#9 需落实同事务 Adapter，或“先准备不可见候选，再原子激活控制记录及审计”的可核验协议。准备失败保持原有效文档，提交结果不明先核对；协议未验证前不得开放该写入口。
4. 新代次不可再次读取、检索或合并旧日记。旧候选、队列任务及缓存即使尚未物理回收，也不能作为有效输入或写入者。隔离代次是正确性边界，异步清理状态不决定是否失效。
5. 新文档成为唯一手工起点；旧代次未汇总内容不带入。后续新 Run 使用新代次；旧在途 Run 可按原快照完成，但不把旧代次提炼结果晋升到新代次。

每次保存都换代，包含只更正部分文字的保存。新代次应保留这次提交的完整文档及新来源基线；不能清空用户没有删除的其他已显示内容。

### 5.2 后台提交校验

记忆内容写入必须统一经过平台受控提交点，校验当前账号/授权、generation、基线 document_revision、来源资格和输入顺序。任何旧代次提交均拒绝；不能遇到冲突后改用“最新代次”重发旧候选。

同代次自动任务竞争时，以条件更新提交正文、来源索引、任务应用标记及必要审计。基线修订冲突则重新读取当前文档，重新核对/生成候选，不能直接无条件覆盖。模型调用在事务外；事务只负责校验和短时提交，避免在模型等待期间锁住并行会话。

所有写入口都受此协议约束，包括日记追加、整份合并、记忆保存工具、维护任务和压缩相关提炼。只在 Web 编辑接口增加校验不够。若某条框架写入链路无法受控，正式接入前须关闭或替换该链路，不能让它旁路写当前代次。

## 6. 自动学习、来源顺序与任务恢复

### 6.1 输入资格与偏好优先级

- 只有平台 `SUCCEEDED` 的 Run 对应正式对话可成为自动提炼来源。任务来源是平台保存的、可核对的正式内容，不能在执行任务时任意读取 AgentState 的最新整段上下文。
- 只提炼常用会议室、时段、合作人员等长期个人偏好。预约编号、预约/取消状态、授权和完整聊天均不转交记忆作为权威事实。
- 用户本人的新明确表述才能改变已有手工偏好；员工回复、工具结果或旧摘要中复述某项偏好不能制造“新用户表述”。推断可提出补充，但不能覆盖手工更正或有更新明确来源的现值。
- 比较明确表述时按正式用户输入的服务端接纳顺序，不按 Run、提炼或合并完成时间。旧任务可提出不冲突的补充，不能覆盖来源更新的偏好；无法证明冲突如何解决时保留现值并请求澄清。
- 用户保存/清空之后，只允许新代次后续新输入触发新学习。版本升级导入的旧历史、旧员工回复和旧内部摘要都不能伪装成新输入；导入内容的来源链须保留。

语义匹配和偏好提炼本身可能出错。候选须保存来源证据和基线修订；不能只给整份模型输出而无来源比较信息，就声称实现 Q6、Q12。完整来源索引结构、冲突证据和交互呈现由实体评审与真实用例验证落实。

### 6.2 持久任务与状态

成功 Run 与记忆任务创建之间不能留下不可恢复的进程内窗口：可在成功事务中登记待处理意图，或用唯一来源约束和可重复扫描补齐。是否生成任务还需检查该 Run 捕获的代次仍有效、账号和员工使用授权仍允许；不能给已过代 Run 换代补学。

建议逻辑任务状态为 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`STALE`、`CANCELLED`：前两者待处理/处理中，`FAILED` 保留失败原因供受控重试，`STALE` 表示过时代次，`CANCELLED` 表示授权等条件阻止。最终状态命名和重试配置由 #9 统一；本节确定的是外部行为和恢复责任。

任务领取、结果应用及日记追加均有持久去重标识。进程中断或提交结果不明时先核对是否已应用；不能因租约过期就直接重复追加。合法重试只执行记忆提炼/合并，不调用原业务 Run、会议写工具或重复插入原正式消息。

界面可在记忆入口或来源 Run 附近显示待更新、已更新、更新失败与原因；失败重试入口重新检查资格。更新失败不把 `SUCCEEDED` 业务 Run 改成失败，不撤回已经保存的正式回复。

### 6.3 重启、授权与缓存

重启后读取持久任务，重新核对成功来源、原代次、当前代次、格式/策略版本、账号与员工使用权，以及是否已经应用。有效任务可恢复；旧代次作废，授权撤销期间搁置的任务不因再授权复活。再授权后的新成功 Run 才产生新的合格来源。

撤销或再授予与任务提交并发时，使用既有授权版本或等价持久条件校验；仅查询当前“已授权”布尔值不足以识别撤销后再授予的旧任务。账号停用同样阻止新自动学习；本人数据管理仍受有效登录约束。

缓存键至少包含用户、员工、代次和文档修订；会话资料缓存包含 Session 及内容修订。失效通知只能加速刷新，不能替代提交时版本检查。首次初始化、有效空文档、已有数据读取失败是不同状态，不能把后两者变成新建默认记忆。

## 7. 会话资料、快照引用与发布版本

会话运行资料归当前用户、员工和 Session，Run 提供来源。单一可变路径可产生内容修订；被正式消息、快照或历史引用的内容版本必须可恢复，不因后续覆盖该路径而改变。需要长期保存的文本在 MySQL，文件原件在私有对象存储；本地副本可从权威内容重建。对象完整性、临时链接重签、上传与 SQL 错开、未引用对象清理沿用[通用素材设计](../会话运行与消息/通用素材与工具操作设计.md)。

显式跨会话引用先验证来源和目标均属当前用户与同一员工，并核对当前权限、固定源修订、摘要和目标能力。目标保存固定快照及来源，不挂接可变的源路径；SQL 与对象未完整就绪时不能声称引用成功。原消息素材的独立归属及不复用可覆盖对象键规则继续有效。

发布新版不自动复制或合并旧会话的计划、任务、工具内部记录和临时文件。用户“在新版继续”仍通过新 Session/新 AgentState 槽，导入完整成功版本链的正式对话和素材；正式内容引用的资料必须可恢复，隐藏运行资料不作为正式历史导入。其他运行资料仍需按显式快照引用处理。

同用户与员工的新旧发布版本读当前有效偏好。记忆的 `memory_schema_version`、策略版本用于平台读写兼容性与来源核对，不随一次员工发布自动换代或迁移。以后需要改变格式时，须有明确迁移、校验、切换和失败保持原有效内容的方案；旧格式无法读取时暂停依赖它的运行，不能以空文档冒充成功迁移。

定义快照继续只读；Workspace 中的可写资料不能成为 Skill 覆盖来源。资料通用结构不扩大一期媒体能力，文字与图片以外能力仍待原有范围和实际模型/Adapter 验收。

## 8. 权限、审计与恢复边界

普通用户只能读取本人数据；用户数据管理权与数字员工运行使用权分开判定。撤销员工授权后仍可管理已有记忆，停止新自动学习和新 Run；账号停用则禁止登录和受保护读取。改手机号不改变稳定 UserId，也不转移原记忆所有权。

固定管理员读取记忆正文、日记或运行资料前，须成功写访问审计；失败不返回正文、检索片段或下载链接。管理员的内容访问不赋予代用户保存/清空记忆、发送 Run 或确认会议操作的权利。本人更正、清空及自动内容应用记录主体、代次/修订、来源和结果；底层管理员运维访问不冒充应用已授权的数据编辑功能。

| 故障或恢复情形 | 应有处理 |
| --- | --- |
| 框架 AgentState 已有 Session 中异常缺失 | 暂停该 Session 新 Run，按既有核对流程修复；不自动以空 AgentState 重放会议动作。 |
| 记忆控制记录、当前文档或必需资料缺失/摘要不符 | 区分正常首次初始化，标识不可用并暂停依赖它的运行；不能用缓存或空内容悄悄顶替。 |
| 记忆任务失败，但业务 Run 已成功 | 保留正式回复及成功 Run；记忆任务单独记录失败和重试。 |
| 手工 SQL 提交结果不明 | 按操作标识和代次/修订核对，不向用户保证保存成功，也不盲目再换一代。 |
| 框架状态与平台 SQL 提交错开 | 沿用既有 Run `RECONCILING` 与 Session 暂停；共用 MySQL 不代表同事务。 |
| 对象与 SQL 引用不完整 | 保持未完成并核对；阻断依赖原件的读取/续接，不能删除仍可能被已提交记录引用的对象。 |
| 从备份恢复 | 联合恢复 SQL、对象及存储配置，并核验状态槽、代次、任务应用记录和引用。#10 仍需明确删除记录与旧备份恢复的衔接，不能宣称已证明所有备份中的遗忘。 |

## 9. 框架复用与实施约束

### 9.1 框架优先的复用决定

默认采用下列 Implementation 分工，优先配置和组合现有能力。只有固定版本能力确实不能表达本项目协议时，才增加必要的 Adapter；不自行重写记忆提取器、合并器、通用文件存储或同义检索层。

| 能力 | 默认复用 | 平台负责的内容 |
| --- | --- | --- |
| 文档与日记格式 | `MEMORY.md`、`memory/YYYY-MM-DD.md` | 可信用户/员工归属、有效代次及来源映射。 |
| 正文持久化 | `WorkspaceManager`、`AbstractFilesystem`、`BaseStore` / `JdbcStore`；默认表名 `agentscope_store`，名称可配置 | 控制记录、有效内容定位、版本条件提交及一致激活，不复制另一份可独立修改的正文。 |
| 自动提取 | 原生 `MemoryFlushManager`，显式传入模型及提取提示 | 只传入成功 Run 的合格正式来源；限定个人偏好，保留来源与输入顺序，排除工具日志与旧历史再学习。 |
| 合并整理 | 原生 `MemoryConsolidator` 及合并提示/篇幅配置 | 按当前用户、员工、代次限定日记与水位；控制提交，防止覆盖手工更正或更新来源。 |
| 读取与检索 | Workspace 读取、原生 `memory_search` / `memory_get` | 仅暴露当前有效范围；统一覆盖读、枚举、搜索和下载的身份/代次检查。 |
| 框架状态 | 原生 `AgentStateStore` 的 MySQL 后端 | 沿用业务 Session 与状态槽绑定，保留正式消息、Run 和审计的独立权威。 |
| 模型、提示和节流配置 | `MemoryConfig` 可表达的配置及相应类的构造参数 | 统一维护配置；逐条核对调用后提取、压缩前提取和紧急压缩的实际生效路径。 |

正文存储、提取和合并按上述决定复用；任务持久化、来源资格、手工更正优先及清空不复活仍是平台需实现和验收的协议，不能因选用原生类而声明自动具备。源码依据见[长期记忆调研](../../调研/状态与持久化/AgentScope长期记忆机制与自动提取调研.md)。

### 9.2 长期记忆 Module 与 Interface

将既有记忆控制集中到一个长期记忆 Module。对外的 Interface 只表达三类行为；以下是行为约定，不固定 Java 方法签名或新增类名：

| 操作 | 调用方需要知道的约定 |
| --- | --- |
| 读取有效记忆 | 身份和员工来自服务端可信上下文；返回完整文档、代次和文档修订。业务 Run 通过同一 Module 固定一致启动快照；无有效记录、有效空文档及数据读取异常分别返回，不以空文档掩盖异常。 |
| 替换记忆 | 提交完整文档、读取时的代次/修订和操作标识；空文档表达清空。重新查权，旧修订返回冲突；成功返回可核对的新代次与修订，结果不明进入核对。保留第 5 节的手工基线、幂等与一致激活规则。 |
| 登记成功 Run 的学习 | 调用方提供既有 Run 引用，Module 内检查成功状态、正式来源、代次和当前授权并幂等登记；返回可查询的任务标识/状态。该操作不等待提取模型完成，不能把“已登记”报告为“记忆已更新”。 |

Interface 包含上述版本、权限、错误与异步完成约定。调用方不分别操作正文、日记、KV、控制记录和任务来维持正确性；Implementation 在 Module 内协调这些步骤，避免相同规则分散到页面、Run 完成处理和后台任务中。

### 9.3 受控写入 Seam 与 Adapter

在框架已有 `AbstractFilesystem` / `BaseStore` 扩展位置设置内部 Seam。必要的 Adapter 集中处理可信归属、当前代次、文档条件提交及受控路径；模型、提取器、合并器和 JDBC 依赖由外部注入，直接复用现有 Interface，不再包一套仅透传的同义抽象。

共享记忆、会话资料和固定发布资产分别映射到各自 namespace。一个 `RemoteFilesystemSpec` 的默认路由共用同一 scope，只将其改为 `SESSION` 会把 Memory 也按 Session 分开，不能满足本文。合并水位、任务去重及节流同样必须核对归属与代次，不能只隔离正文路径。

受控写入必须覆盖日记追加、MEMORY.md 合并、用户保存/清空、模型保存工具、正常压缩及紧急压缩等入口。原生 `memory_save` 直接追加两份文件，不应未经来源和版本控制直接开放。优先保留可安全复用的原生读取工具；写入口无法接管时关闭或受控替代，不让默认 hooks 与平台流程各自写一份权威内容。

### 9.4 自动学习与合并流程

```text
业务 Run 成功并形成正式消息
  → 长期记忆 Module 幂等登记合格来源与原代次
  → 后台任务重新查权、查代次、核对来源与是否已应用
  → 调用原生 MemoryFlushManager，显式传入受控正式消息
  → 经受控写入 Seam 追加当前有效日记，保存可核对的来源/任务标识
  → 在合并机会中复用原生 MemoryConsolidator
  → 经同一受控 Seam 校验基线修订并提交到框架 JDBC KV
  → 核对持久内容与任务结果，后续新 Run 读取有效文档
```

上图表达受控学习协议，不表示一轮 Run 返回前必须同步合并，也不表示两个原生异步中间件已经保证这些步骤有序完成。合并冲突、模型失败和提交不明按第 5～6 节处理；重试仅作用于记忆任务。

原生提取器、合并器的模型与提示优先从统一 `MemoryConfig` 选择并显式传入；提取、合并分别定制范围和语言。业务限定和来源顺序仍须代码校验与来源证据，不能只靠提示词实现。框架默认篇幅与维护间隔可作为接入验证起点；默认日记归档/日志清理天数不替代 #10 的平台留存决策。

### 9.5 固定版本限制与一致提交

以下限制必须进入接入清单，具体源码见[接入点调研](../../调研/状态与持久化/共享记忆与会话工作区接入点调研.md)与[长期记忆调研](../../调研/状态与持久化/AgentScope长期记忆机制与自动提取调研.md)：

- 原生调用后 Flush 在后台执行时读取 AgentState 当前上下文，不等于本项目已经冻结并核验的成功 Run 来源。
- 普通压缩前提取没有接入 `MemoryConfig.flushPrompt`；紧急压缩还有独立路径。关闭调用后 hooks 不保证压缩路径不再提取，需逐条接管或阻断。
- Workspace 追加/覆盖并不自动使用正文 CAS；`BaseStore.putIfVersion` 的存在不证明所有写入口已按预期版本提交。合并水位 CAS 也不等于正文版本保护。
- `JdbcStore` 各操作自行取得连接，不能假定与平台 Spring 事务共享；正文、有效代次、来源应用记录、任务及审计的一致关系必须由 #9 落实。复用表不降低第 5 节的一致激活要求。
- 空内容、本地模板及 overlay 回退必须满足清空语义；有效空文档不能回退成历史内容。

### 9.6 JDBC 建表与本轮范围

固定版本 `JdbcDistributedStore.create(dataSource)` 的默认方言装配会初始化框架表，底层 `JdbcStore` 也有 `initializeSchema` 开关。框架创建的是通用 KV、状态等框架存储，不会生成本文的平台代次、来源、任务或业务审计记录。相关源码：[一体化 JDBC 装配](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-extensions/agentscope-extensions-jdbc/src/main/java/io/agentscope/extensions/jdbc/JdbcDistributedStore.java#L81-L133)、[方言建表开关](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-extensions/agentscope-extensions-jdbc/src/main/java/io/agentscope/extensions/jdbc/dialect/AbstractJdbcDialectBuilder.java#L61-L116)、[KV 初始化](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-extensions/agentscope-extensions-jdbc/src/main/java/io/agentscope/extensions/jdbc/store/JdbcStore.java#L59-L81)。

本次仅将设计回填正式规格，不修改或执行现有 SQL，不触发框架自动建表，不实现 Adapter、Module 或 Java 配置。后续 #9 分别评审框架固定 DDL 与最少平台控制记录，确定实际连接/方言、初始化方式、已有表升级策略及一致提交协议；不按本节直接迁移有数据的库。

## 10. 后续验收场景

主验收从已认证业务入口、正式消息、Run/任务状态及持久内容观察；不能仅检查内部方法被调用或某个路径包含用户 ID。

| 场景 | 必须观察的结果 |
| --- | --- |
| 两用户、两员工、同用户两 Session | AgentState/资料互不串用；仅同用户同员工的有效记忆共享；读、写、检索、枚举、下载都守边界。 |
| A 等确认，B 正常提问 | B 可运行；A 仍只有自己的活动 Run，确认/取消不会作用于 B。 |
| 手工更正与旧 Flush/合并交错 | 新代次文档保持；旧任务拒绝提交，旧日记和搜索片段不再出现。 |
| 清空与空内容回退 | 页面、模型有效偏好和记忆工具均读空；本地模板、缓存及旧对象不复活。 |
| 在途 Run 期间修改记忆 | 该 Run 保留原快照；下一新 Run 使用新代次；原 Run 成功后不能补学旧代次。 |
| 两浏览器编辑同一文档 | 旧修订保存被拒绝并提示重载，不静默覆盖。 |
| 较早输入的任务较晚完成 | 不覆盖较晚明确偏好；冲突不明时保持现值并产生澄清提示。 |
| 新消息/旧历史/员工复述混合 | 仅合格新来源可重新学习；导入历史和员工复述不能冒充新明确表述。 |
| Run 失败、取消、待核对 | 不产生可应用的自动记忆提炼；正式用户消息仍按既有规则保留。 |
| Run 成功与任务登记间崩溃 | 重启补齐一次任务意图，不遗漏、不重复学习。 |
| 任务模型失败、提交不明、应用后崩溃 | 原业务成功不变；核对/重试只作用于记忆，日记与内容应用不重复。 |
| 撤销后再授予并发旧任务 | 撤销期任务不因当前又有权限而复活；本人管理仍有效，停用账号被拒绝。 |
