# 一期用户与管理员建表规格

> 状态：基于已确认的[用户与管理员数据模型](用户与管理员数据模型.md)整理的实施规格，物理表按[阿里巴巴 MySQL 规约](阿里巴巴MySQL规约核对.md)修订；本地执行结果以[验收记录](用户与管理员建表验收记录.md)为准。应用功能尚未实施。业务会话、数字员工定义及其授权关系在各自的设计议题中补齐。

## Problem Statement

一期要让企业员工以手机号进入会议室数字员工，让唯一固定管理员能够开通、停用、更正和恢复账号。原有身份表物理方案不符合团队指定的阿里巴巴 MySQL 规约，尤其是必备字段、主键形态、外键与存储过程，因此需要在保留已确认业务规则的同时重建数据库基线。

## Solution

建立符合阿里巴巴规约的 MySQL 身份数据基线，保存稳定平台用户、密码摘要、唯一固定管理员、当前与历史手机号、会议账号检查状态和过程、身份审计。数据库负责可表达的唯一性、状态取值与非空约束；跨表引用完整性、“恰有一个当前手机号”、账号停用后的 Run 阻断、密码哈希算法、MCP 实际鉴权和追加式审计写入由后续平台服务、事务与巡检负责。初次本地专用 schema 的执行是历史验收；2026-10-22 回归使用一次性临时实例。

2026-10-22 已补强三种用户版本为正、PASSED 时 HTTP 状态非空，并在身份审计扩展 `employee_id`、`grant_id`、`authorization_version_before/after` 四列。字段、索引及配对语义见[员工建表规格第 7 章](../数字员工配置与发布/一期员工配置发布授权建表规格.md#7-身份审计四列扩展与授权事务)，当前隔离结果见[全库验收记录](../数字员工配置与发布/员工配置发布授权与全库建表验收记录.md)。

## User Stories

1. 作为平台管理员，我希望在部署时只有一个固定的管理员身份，以便管理员与员工共用账号体系且管理权不会在界面中被任意授予。
2. 作为平台管理员，我希望依据可信员工名册核对手机号归属后手工开通员工，以便平台账号对应正确的人。
3. 作为平台管理员，我希望记录核对来源和时间，以便以后追查手机号归属依据。
4. 作为员工，我希望以手机号登录，以便使用熟悉的登录标识。
5. 作为员工，我希望姓名只作展示且允许重名，以便同名同事不会共用身份或历史数据。
6. 作为员工，我希望拥有不会因改号而变化的 UserId，以便原有会话、审计和个人记忆仍归属于我。
7. 作为员工，我希望首次登录必须改密，以便管理员设置的初始密码不能长期使用。
8. 作为平台管理员，我希望能重置普通用户密码并使旧登录会话失效，以便用户遗忘密码时安全恢复。
9. 作为平台管理员，我希望能停用普通用户而不删除其历史，以便停止新登录与新 Run 且保留审计。
10. 作为平台管理员，我希望能重新启用普通用户并要求其再次改密，以便恢复使用时不沿用停用前的凭据状态。
11. 作为平台管理员，我希望能更正普通用户手机号且保留其 UserId，以便修正录入错误而不拆断历史关系。
12. 作为原号码持有人，我希望旧手机号在改号后默认保留占用，以便它不会直接被分配给另一个平台用户而混淆会议历史权限。
13. 作为平台管理员，我希望跨用户转交旧手机号必须留下受控记录，以便核对号码新归属与会议历史访问权。
14. 作为员工，我希望会议平台检查失败时仍可进入平台，以便会议服务故障不影响非会议功能。
15. 作为员工，我希望会议工具只在当前手机号版本通过会议账号检查后开放，以便旧号码的探测结果不会沿用到新号码。
16. 作为平台管理员，我希望能区分 MCP HTTP 身份失败和工具业务权限不足，以便不把 401 误判为手机号不存在。
17. 作为管理员，我希望查看开通、改号、停用、重置、启用及身份检查的审计记录，以便解释账号状态变化。
18. 作为普通用户，我希望只有被明确授权的数字员工可使用，以便默认权限最小化。
19. 作为固定管理员，我希望默认可使用全部数字员工，同时会议工具仍受本人号码、工具策略、会议权限和写操作确认约束。
20. 作为开发者，我希望每张表都有规范的自增主键、创建时间、修改时间与中文注释，并能在真实 MySQL 上验收关键约束，以便后续实现按同一模型开发。
21. 作为开发者，我希望验收数据可回滚且不影响已有业务 schema，以便重复核查结构而不污染本地环境。
22. 作为运维和开发者，我希望跨表关系由服务事务校验和巡检发现异常，以便遵守不建数据库外键的团队规约，同时避免孤儿身份记录。

## Implementation Decisions

- 一期只落地用户与管理员身份基线。数字员工使用授权在数字员工定义确定后使用同型数值 ID 关联；此阶段不创建占位数字员工表，也不以手机号代替员工主键。
- UserId 对应平台用户表自增的 `BIGINT UNSIGNED id`，创建后不复用，对外标识由服务层封装。手机号保留表是登录号码的唯一来源；每个号码全局只登记一次，当前号码与历史保留号码用状态区分。
- 用户表分别保存账号状态、凭据安全版本、手机号版本和授权版本。密码摘要单独保存；数据库不保存明文、可逆密文或初始密码原文。
- 固定管理员通过只允许一个常量键的单例关系建模。数据库限制最多一个管理员；部署初始化与平台启动检查保证至少一个有效管理员。管理界面不提供管理员变更入口。
- 当前号码的每用户唯一性由数据库唯一约束实现；每个用户必须至少拥有一个当前号码，由开户与改号事务以及平台启动/巡检校验实现。
- 所有表统一包含 `id`、`gmt_create`、`gmt_modified`；表达是/否的列使用 `is_xxx TINYINT UNSIGNED`。表和列名使用小写单数英文，业务唯一索引使用 `uk_` 前缀、普通索引使用 `idx_` 前缀，VARCHAR 索引声明长度。MySQL 主键索引物理名固定为 `PRIMARY`，这是无法改成 `pk_id` 的数据库限制。
- 不创建外键、级联或存储过程。业务服务在同一事务中检查被引用用户/号码是否存在、归属是否匹配，并通过巡检查询发现历史孤儿记录；数据库保留唯一索引和 CHECK 约束。
- 手机号归属核对与会议账号可用性分开保存。后者只保存当前号码版本的检查结果及必要的失败分类，不保存完整 MCP 请求、密钥或原始敏感响应。
- 会议账号检查基于目标 MCP 版本已验证的前提，按标准初始化和 `tools/list` 探测；HTTP 401 统一归类为签名或身份失败，不直接归因于手机号。真实工具请求仍由会议 MCP 每次判权。
- 身份审计使用结构化动作码、操作者、目标用户、结果、时间和内部号码标识；系统初始化允许操作者为空。审计不包含密码或完整手机号副本。
- 身份状态变化应在一个事务中同时维护号码状态、版本和审计；停用、改号、密码重置后撤销登录会话，Run 与工具入口重新检查。数据库结构不声称单独完成运行时授权。
- 建表脚本以 MySQL 8.0 为目标，采用 InnoDB、`utf8mb4`、规范自增主键、唯一约束、检查约束、必要索引以及中文表列注释。时间值由调用方按 UTC 写入。
- 在既有本地 MySQL 服务中新建专用开发 schema；不修改其他 schema，不写入真实员工数据，验收数据在测试结束时回滚。

## Testing Decisions

- **测试入口**：在本地真实 MySQL 上运行建表脚本，并由独立验收器执行可回滚的 SQL 正反场景及结构规约检查；验收不使用数据库存储过程。仓库尚无应用服务或类似自动化测试可复用。
- **成功行为**：可建立两个同名但 UserId 与手机号不同的用户；可写入凭据、唯一管理员、当前号码、会议检查状态和审计；更正手机号后旧号保持保留、UserId 不变，号码版本及安全版本提升。
- **失败行为**：重复手机号、同一用户第二个当前号码、第二个固定管理员、无效状态值和不完整的“检查通过”状态由数据库拒绝。悬空业务关联由未来服务事务与巡检发现并阻止，不声称数据库外键会拒绝。
- **边界行为**：测试数据回滚后不残留；重复应用脚本的策略应明确。跨记录“恰有一个当前号码”、密码哈希质量、会话撤销和 MCP 实际判权需要后续服务与环境集成测试，不能以建表通过代替。

## Out of Scope

- 业务 Session、Run、消息、AgentState、Memory、Workspace 与多渠道消息的物理建表。
- 数字员工定义、发布版本、数字员工使用授权表及工具策略表。
- Web 登录接口、管理页面、Spring Session 基础设施表及真实会议 MCP 联调。
- 批量导入员工、多管理员、自动手机号归属证明及跨企业租户。
- 提交、推送、部署到共享环境。

## Further Notes

本规格依据已确认的身份模型与测试环境 MCP 契约。会议服务是否部署了按手机号鉴权的版本，仍须在目标环境单独验收。已有联调说明含测试凭据，建表脚本、测试和公开议题均不得复制凭据。
