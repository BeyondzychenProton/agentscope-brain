## 4. 第二轮：Q3—Q4 已确认结果

### Q3：Web 与 SSE 实现——采用 Spring MVC

已确认 Spring MVC：处理普通 HTTP 动作和只读 SSE，Agent 由已确认的独立执行器及适配层运行。SSE 读取持久投影，连接断开不直接取消 SDK 执行。异步写出、队列和超时仍须单独设计与验证。

### Q4：MySQL 数据访问实现——用户指定 MyBatis-Plus

- 平台业务数据使用 MyBatis-Plus 访问；当轮 Spring JDBC 应用数据访问推荐未采用，不再作为当前选型。

- 插件选择、精确依赖与实际编译尚未完成，不把选择 MyBatis-Plus 等同于已实现平台事务或自动获得业务幂等。

官方事实和接入限制见[MyBatis-Plus 接入与事务接缝补充核验](../调研/正式Web应用/MyBatis-Plus接入与事务接缝补充核验.md)：普通 CRUD 与自定义 Mapper 可并存；多表业务写入须进入同一 DataSource 的明确 Spring 事务，不能由事务外单次自动提交拼接。

## 5. 第三轮：Q5—Q6 已确认结果

用户回复“推进采用”，承接当轮两项推荐，Q5、Q6 均采用。

### Q5：普通用户登录的具体框架——采用

采用 Spring Security + Spring Session JDBC 落实既定的服务端会话设计：校验数据库预置账号、使用 HttpOnly 登录 Cookie、服务端持久化登录状态，并保留 CSRF 防护。首次改密的受限访问和可信用户／账号状态校验由平台实现；不增加管理员角色或管理功能。登录框架内部 JDBC 不替代 Q4 已定的业务 MyBatis-Plus 路线。

依据：[Spring Security 6.5 认证持久化](https://docs.spring.io/spring-security/reference/6.5/servlet/authentication/persistence.html)、[CSRF 与 SPA](https://docs.spring.io/spring-security/reference/6.5/servlet/exploits/csrf.html)、[Spring Session 3.5 JDBC](https://docs.spring.io/spring-session/reference/3.5/configuration/jdbc.html)。Spring Session JDBC 默认独立事务，不能假设与平台业务提交原子；具体超时、续期和身份更新接缝继续留待下一轮。

### Q6：浏览器访问与部署入口——采用

采用生产环境同一个 HTTPS 入口访问网页、HTTP 接口及 SSE，保持浏览器同源；开发环境由 Vite 代理接口与事件读取到后端。前端工程独立构建，后端路由与静态资源的具体转发配置在后续部署方案中细化。

依据：[Vite 官方 server.proxy](https://vite.dev/config/server-options#server-proxy)明确支持按路径前缀把开发请求代理到目标；同源生产入口是本项目已确认的设计，不是该开发配置自动提供的部署能力。Cookie／CSRF 规则仍独立落实。

## 6. 第四轮：Q7—Q10 已确认结果

用户将 Q7 有效时长调整为 24 小时，Q8、Q9、Q10 均回复“采用”。此前关于登录时长、并行登录政策、图片路径和启动策略的开放项据此收敛。框架事实见[用户登录会话与图片上传接缝补充核验](../调研/正式Web应用/用户登录会话与图片上传接缝补充核验.md)。

### Q7：登录有效期——按用户调整为固定 24 小时

单次登录固定有效 24 小时，覆盖当轮 8 小时推荐；刷新、轮询和 SSE 心跳均不重置期限，暂不提供“记住我”或自动续期。可信登录时刻／绝对到期由服务端记录并检查；Spring Session 空闲上限与该窗口协调，不用默认较短空闲值静默改变产品承诺。退出、账号失效及安全版本变化按既定规则提前终止会话。到期后的 SSE 发送和心跳继续受 #20 查权规则约束。

### Q8：多浏览器登录与退出范围——采用

允许同一账号多浏览器并行登录，互不踢出；同一浏览器的多个标签共享登录 Cookie。普通退出仅使当前登录会话失效，因此共享该会话的标签均失效，其他独立浏览器登录会话继续有效。改密对旧会话的撤销仍遵守既定安全版本规则，不因并行登录而放松。多标签对同一交互的竞争继续由 #19 CAS 和一次提交规则处理。

### Q9：首版图片传输路径——采用

浏览器经同源后端上传图片，由后端验证类型、字节、像素和摘要后写入私有对象存储；历史图片也经后端重新鉴权代理读取。首版由后端承担图片流量，集中落实现有校验和归属规则；对象存储提供方随后由用户明确为 MinIO，限额与连接参数仍待接入时明确。上传票据／暂存与正式 message_media 分开，上传完成不创建 Run，图文仍由用户主动统一发送。

该路径已从原规格允许方案中选定；multipart 仍不自动提供原件校验、恢复或事务保证。暂存 TTL、结构与清理互斥未由本题决定；后续厂商补充为 MinIO。

### Q10：启动校验与外部服务不可用——采用

启动时先校验数据库／必要表结构及预置普通账号、有效授权、固定员工配置的完整性；基础数据缺失或损坏时明确失败，不猜选配置或自动创建替代身份。不把模型／会议 MCP 在线探测成功作为整个应用启动前置：外部服务暂时不可用时保留正常登录和已有历史读取，相关用户操作准确返回不可用或按已有状态核对；不虚报可执行能力，不放行缺少必要配置的执行。

本题不增加管理员初始化、动态发布或通用配置维护能力。具体检查清单、健康状态与错误接口在已确认策略内细化。

## 7. 第五轮：Q11—Q13 已确认结果

用户回复“全部采用”，Q11、Q12、Q13 均采用。结构与官方事实见[上传暂存、提交回查与确认凭据接缝补充核验](../调研/正式Web应用/上传暂存提交回查与确认凭据接缝补充核验.md)。以下机制已确认，不重新确认 #19／#20／#21 已定的业务语义，不表示已修改 DDL。

### Q11：未发送图片的暂存期限——采用

暂存固定 24 小时，从服务端创建上传票据时起算，刷新／上传重试不续期；过期后禁止新绑定，提示用户重新选择或上传。正式接纳前用独立持久暂存记录保存 owner、目标／新建意图、受控 MinIO 对象定位、验证事实、原到期时间和当前状态，不借用必须归属正式消息的 message_media。

图片被正式消息接纳后，转为正式素材引用，不受临时 TTL 清理。删除临时对象前必须按既定协议禁止绑定、排除在途接纳／结果未知，并与接纳互斥；到期不等于立即删除，不能删除已进入正式历史的原件。该 24 小时只用于待发送图片，不把它移植为正式历史保留策略。

### Q12：普通发送的持久提交记录与原键封闭——采用

增加独立普通提交控制记录，以 UserId + submission_key 唯一，固定本次目标、内容语义摘要和暂存引用，保存接纳／核对／已封闭等事实及原 Session／消息／Run 结果。正式消息已有成功唯一键继续保留；FORM 仍沿用独立交互响应协议。

GET 回查仅返回事实，暂时查无记录不能宣布未接纳。确定未接纳须通过明确的受鉴权封闭动作，与原键接纳互斥：接纳先完成则返回原结果；封闭先完成则原键的迟到接纳永久拒绝，之后才能允许用户明确重试。原键不能因暂存 TTL 清理而复活；新接纳与提交结果、暂存绑定、正式消息／Run 和投影共同提交，具体锁序和最小字段仍需收敛。

### Q13：保留随机确认凭据并增加加密恢复副本——采用

继续随机生成确认 token，以现有 SHA-256 摘要验证，另外保存标准认证加密的恢复副本，用于刷新后取回原 token。加密恢复机制已确认，AES-GCM 的具体格式、独立密钥与 keyId／nonce／格式版本在字段设计中细化。密钥独立于数据库保管；同一密钥每次加密的 nonce 唯一性、原 keyId 恢复及完整性验证须落实。

本人在当前有效登录、CSRF、归属／权限／提案／版本检查通过后，通过专用 POST 领取原 token；领取不新建确认、不换 token、不延长原十分钟、不重置消费，也不执行模型或工具。明文／密文不进入投影、消息／草稿、URL 或普通日志。原密钥缺失、密文损坏或摘要不符时保持不可确认，按既定核对／安全终结处理，不能凭摘要恢复或另签替代。

### Q19：前台执行容量与持久等待——采用

前台同时最多 2 条受控业务执行链，普通新任务最多 16 条待执行；这些是执行许可和普通等待容量，不是全系统线程数或所有模型调用总上限。等待用户输入释放执行资源，但原 Session 仍保持活动 Run 占用；已有交互续接优先调度，不抢占或重复已领取调用。

普通等待事实持久化，不用大内存队列承载唯一事实；原 Run 初态沿用 ACCEPTED，不为显示“等待执行”提前假定 RUNNING。新普通输入达到额度时明确不接纳，不生成半条正式消息／Run，提交控制和草稿按原键返回准确结果；同键已接纳请求始终回查原结果，不受当前容量影响。

已接纳 FORM 回答、已消费确认和已有恢复任务不计入“16 条普通新任务”额度，不能因普通队列满而丢弃、改答未保存或重新消费。持久队列不授权启动重放；重启仍按既定核对和明确继续规则，未知写结果不重发。精确接纳／领取／计数并发与控制记录在整体事务矩阵细化。

### Q20：后台记忆独立单 worker 与扫描周期——采用

已确认的默认值不重问：最大领取 5 次、30 秒翻倍退避至最多 15 分钟、±20% 抖动、10 分钟租约；租约到期先查是否已应用，不盲目重做。前台 2 与后台 1 分别计数，不能宣称系统全部模型调用并发总数恰好为 2；实际资源和外部模型限制在实施校准。
