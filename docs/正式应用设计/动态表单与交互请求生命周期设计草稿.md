# 动态表单与交互请求生命周期设计草稿

> 日期：2026-10-23，Asia/Shanghai。  
> 关联议题：[确定动态表单与交互请求生命周期 #19](https://github.com/BeyondzychenProton/agentscope-brain/issues/19)。

## 1. 沿用的边界

- 数字员工提出结构，服务端校验，前端使用受控组件渲染。
- 同一业务 Session 只有一个活动 Run；表单数据收集、人员选择与预约／取消操作确认分开。
- 浏览器断线不等于业务取消；服务重启后先核对，不自动重放模型或会议写操作。
- 前端技术栈、事件投影与传输方案由各自议题确定；具体表单接入方式、接口和数据结构仍需本议题后续确认。

依据：[正式应用设计入口](README.md)、[AgentScope 运行与交互契约核验](../调研/正式Web应用/AgentScope运行与交互契约核验.md)、[动态表单与交互协议复用核验](../调研/正式Web应用/动态表单与交互协议复用核验.md)。

## 2. 第一轮已确认决定

### Q1：交互归属与顺序

- 动态表单、人员选择、候选时间选择均属于原业务 Run；提交响应后继续原任务。
- 同一时刻只保留一个可响应的交互请求；一张表单可以包含多个字段。
- 一次任务可以依次提出多个交互请求，例如先补时长、再选同名参会人、再选时间。
- 单个待响应请求是平台一期主动施加的限制，不是 AgentScope 原生默认保证；不能把一次 SDK 调用结束当作业务 Run 已完成。

### Q2：一期字段与组件范围

支持短文本、长文本、数字、开关、单选、多选、日期、时间、日期时间，以及人员选择；允许字段分组、必填、范围限制和字段错误提示。

复杂联动和可重复子表延后。本轮当时尚未选择 JSON Schema 草案，后由 Q15 确定；组件库、事件协议及表单 renderer 仍由对应议题确定。

### Q3：预填与可信候选

- 允许使用对话中已经明确的信息预填，预填值必须展示，用户可修改后统一提交。
- 通讯录查询得到多个同名人员时，保持待选，不静默代选。
- 人员、会议室等真实对象由服务端提供并校验。
- 表单提交仅补充数据；预约／取消仍要求独立的具体操作确认。

## 3. 第二轮已确认决定

### Q4：等待输入期间的普通文字

- 一期通过当前交互卡回答，不增加自然语言直接修改待填表单的能力。
- 等待期间输入的普通文字保留为聊天输入框草稿，提示先完成或取消当前任务，不作为本次交互响应或普通新 Run 接纳。
- 聊天输入框草稿与交互表单草稿分开；本轮没有决定聊天输入框草稿是否持久化。

### Q5：取消与视图变化

- 用户不继续填写时，提供明确的“取消当前任务”，进入原 Run 的取消流程。
- 收起卡片、切换会话、关闭页面保留等待，不自动取消任务。
- 已发出的写操作继续沿用既有结果核对规则；取消不等于外部写操作已经撤销。

### Q6：未提交的交互草稿

- 自动保存服务端草稿，并绑定当前交互请求版本。
- 刷新或重新登录后恢复最近成功保存的内容；必填项未完成也能保存。
- 保存草稿不代表提交，不触发模型；明确提交才续接任务。
- 多标签页的草稿并发、修订冲突和提交去重规则见第三轮 Q10。

### Q7：有效期与业务条件变化

- 普通表单不设统一倒计时，保持等待，直到提交、取消或因权限等条件变化失效。
- 提交时重新检查人员、时间、会议室等业务条件；信息过时则提示修改。
- 预约／取消的具体操作确认仍采用既有十分钟期限。
- 普通表单无统一倒计时不构成数据保留、自动销毁或备份淘汰策略；这些议题继续延后。

## 4. 第三轮已确认决定

### Q8：模型提出的结构不合法

- 服务端拒绝展示不合法的表单结构，允许模型根据错误自动修正一次。
- 仍失败则停止后续步骤，明确报错；已经发生的工具操作保留其真实状态。
- 修正不代表接纳任何用户回答；具体框架接入和挂起状态处理由第四轮 Q12—Q13 补齐。

### Q9：用户输入校验失败

- 一次返回所有能确定的字段错误，保留已填内容，留在原表单修改。
- 校验通过前不接纳回答、不续接模型。
- 候选信息过时明确提示修改，不自动换人或换时间。

### Q10：版本、并发与重复提交

- 已展示的结构固定；确需变更时明确换新版，旧版失效，兼容的已填值可带入新版。
- 草稿保存发生版本冲突时保留本地输入并提示处理，不静默覆盖。
- 一个交互请求只接纳一次有效提交；同一次提交因网络重试而重发，返回原结果。
- 另一标签页已经提交后，旧页面展示“已提交”，不能覆盖答案。

### Q11：已接纳回答与正式历史

- 保存结构化原始回答及可读内容，作为原 Run 下的正式用户消息，不为该回答另建 Run。
- 后续执行失败也保留已接纳回答。
- 草稿和校验失败的提交不进入正式消息。

## 5. 第四轮已确认决定

### Q12：受控输入工具与原生挂起

- 采用普通受控输入工具，服务端校验结构、保存交互候选后主动挂起。
- 平台交互记录和框架 pending 均持久保存且一致后，才开放回答提交。
- 服务端把合法回答重建为匹配原工具调用的结果，续接原 Run。
- 多个输入请求或输入请求与其他工具混合的批次，在执行前整体拒绝，纳入已定的一次修正预算。

### Q13：回答接纳、续接与恢复

- 区分“回答已接纳”和“任务已继续”；先在一个 SQL 事务中保存回答、正式用户消息和待续接记录，再调用框架。
- 续接结果不明保留回答并进入待核对；重启后，确认尚未开始续接的回答提供“继续处理”，不能判断是否已消费的先核对。
- 未提交表单核实有效后恢复草稿，用户提交即表示明确继续。

### Q14：操作确认共用外壳、保持独立授权

- 普通表单和操作确认共用待办展示、版本检查和一次响应机制；同一 Run 同时只有一个待响应请求。
- 表单回答按 Q11 进入正式消息；预约／取消授权仍以既有操作、一次性确认和审计记录为准。
- 操作确认类型只能由服务端根据固定提案建立，不能由模型或普通表单指定。

### Q15：版本化表单契约

- 采用受控 JSON Schema draft-07 子集描述字段约束，单独描述字段顺序、分组和可信候选引用。
- 前后端使用同一套规则校验。
- 组件库和 Vue／React 由 #21 确定，事件及传输由 #20 确定。
