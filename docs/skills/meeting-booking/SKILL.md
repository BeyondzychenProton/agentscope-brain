# Meeting Booking

## 1. 概述与边界

本 Skill 编排会议 MCP 工具，完成企业内部会议相关请求。实际动作由已授权的 MCP 工具执行；本 Skill 不执行脚本、不开放任意命令。

支持的意图：

| 意图 | 主路径 |
| --- | --- |
| 完整预约 | 选人 → 找空档 → 找会议室 → 确认 → `room.reserve` → `calendar.verify` |
| 仅查忙闲 | 选人 → `calendar.get_freebusy` 或 `calendar.find_slots` |
| 仅订会议室 | 时间已定 → `room.search` → 确认 → `room.reserve` → `calendar.verify` |
| 查询我的会议 | `meeting.list_mine` |
| 取消会议 | `meeting.list_mine` → 确认 → `meeting.cancel` |

不适用：

- 仅个人待办、差旅/酒店/餐饮预订
- 仅操作系统（登录、审批、故障），即使名称与会议室同名
- 取消他人发起的会议（现网只允许发起人取消未开始会议）
- 宣称设备条件已精确过滤（`equipment` 当前不参与服务端过滤）

操作者身份来自平台已认证登录手机号（请求头），模型与用户均不得指定或替换操作者手机号。参会人手机号只用于选对象，不改变发起人。

## 2. 会议室与系统同名消歧

公司会议室名称与自研系统重名。读 `references/room-directory.md` 获取名录；禁止编造会议室信息。

消歧规则：

1. 出现开会、会议室、预订、楼层、容纳、16F/17F/18F、约人、场地 → 按**会议室**处理。
2. 出现系统、平台、登录、OA、审批、故障、账号、密码、项目管理、运营、安全 → 按**对应系统**处理，不走本 Skill 写会议室。
3. 无法区分时（如“帮我去郁金香”）必须先向用户澄清，消除歧义前禁止调用 `room.reserve`。

## 3. 确认类型（不得混用）

| 类型 | 何时 | 效果 |
| --- | --- | --- |
| 人员选择确认 | `identity.resolve` 为 `CANDIDATES`，或模糊匹配即使只返回 1 人 | 用户选定具体员工；**不**授权预约/取消 |
| 写操作确认 | 预约或取消前，展示本次具体参数 | 仅当前登录用户确认后，才允许调用 `room.reserve` 或 `meeting.cancel` |
| 结果核验 | 预约返回后调用 `calendar.verify` | 系统核验，**不再**问用户是否同意 |

用户最初说“帮我约个会”或“取消那个会”**不能**代替写操作确认。确认卡须含可核对的具体字段（见各流程）。

## 4. 槽位与 MCP 参数映射

### 4.1 业务槽位

| 槽位 | 说明 | 必填 | 默认 / 约束 |
| --- | --- | --- | --- |
| meetingTheme | 会议主题 | 预约时是 | 缺省可暂用「工作会议」并告知用户；最终 ≤35 字 |
| attendeePhones | 参会人登录手机号列表 | 预约时是 | 至少 1 人，去重后 ≤20；须含所有应参会者 |
| startTime | 开始时间 | 预约时是 | 格式 `yyyy-MM-dd HH:mm:ss`；时长与开始须满足服务端规则 |
| durationMinutes | 时长（分钟） | 预约时是 | 默认 30；须 ≥15 且为 5 的整数倍 |
| roomId | 会议室 ID | 预约时是 | 来自 `room.search` 的 `chamberId`，禁止用名称当 ID |
| floor | 楼层偏好 | 否 | 仅 `16` / `17` / `18` |
| attendeeCount | 人数（搜会议室） | 搜会议室时是 | 通常 = 参会人数（含发起人若其参会） |
| meetingNote | 会议说明 | 否 | ≤500 字；对应旧槽位 Instruction |
| requestId | 写操作幂等键 | 写操作是 | 见 §4.3 |

不支持的槽位：`attachment`（无对应 MCP 工具，勿假装已上传）。

`location` / 会议室名称不是预约 API 字段：先 `room.search`，再用返回的 `chamberId` 作为 `roomId`。

### 4.2 时间规则

- 所有时间按满天星服务端时区解释；区间为左闭右开 `[startTime, endTime)`。
- 相对时间（下周三、下午、3 点后）先换成绝对 `startTime`/`endTime` 再调工具。
- 用户未给开始时间：可追问；或给出基于工作时段的候选并**等待用户确认**，不要静默拍板。
- `calendar.find_slots` 只在工作日及配置工作时段内返回空档（当前配置约 `08:30`–`17:00`）；不要推荐明显超出该范围的开始时间，除非用户明确要求且后续仍可能被服务端拒绝。
- 午休偏好（约 11:30–13:00）仅作排序/推荐参考，不是硬拒绝。

### 4.3 requestId 与重试

- `room.reserve`、`meeting.cancel` 必须带 `requestId`：8～64 位英文字母、数字、下划线或横线。
- **同一笔逻辑操作**（含网络重试）必须使用相同 `requestId` 且参数不变。
- **新操作**必须使用新 `requestId`。
- 收到 `IN_PROGRESS`、结果无法确认、或长期无明确成败：停止自动换号重试，说明情况并转人工核对。
- 读工具失败可谨慎重试 1 次；写工具禁止“换 requestId 再试一次”式盲重试。

## 5. 共用子流程

### 5.1 解析参会人

1. 对每个姓名/部门线索调用 `identity.resolve`（可选 `name`、`deptId`、`postId`、`pageNum`；每页 10 人）。
2. 同名或范围过大时，先 `department.search`（可选 `keyword`），再把 `deptId`/`postId` 传给 `identity.resolve`。
3. 按 `resolutionStatus` 处理：
   - `RESOLVED`：精确唯一；展示部门/岗位后请用户点头确认（仍属人员确认）。
   - `CANDIDATES`：列出候选（姓名、部门、岗位），让用户选定；需要时翻页。
   - `NOT_FOUND`：说明未找到，请用户改名或给部门。
   - `INVALID_ARGUMENT` / `UNAUTHENTICATED` / `SERVER_ERROR`：说明原因，勿编造员工。
4. 选定后只保留其 `phone` 进入后续工具。勿在无关回复中扩散完整手机号；对用户展示优先用姓名+部门。
5. **发起人默认视为参会人**：若用户未排除自己，将当前登录用户手机号一并列入 `attendeePhones`，并在确认卡标明「含发起人」。用户明确说自己不参会时，可去掉，并告知不影响其作为发起人身份。

### 5.2 查找空档

1. 组装 `phones` = 全部参会人手机号（含发起人若参会），人数 ≤20。
2. 需要看忙闲明细：`calendar.get_freebusy`（跨度 >0 且 ≤31 天）。
3. 需要共同空档：`calendar.find_slots`，并传 `durationMinutes`。
4. 无日程 ≠ 保证能到场；如实说明。
5. 冲突处理：
   - 目标时段全员空闲 → 进入会议室查找。
   - 部分冲突但有其他共同空档 → 给出 2–3 个候选（优先贴近原要求、全员空闲、避开午休/下班后），**等用户选**。
   - 目标日无共同空档 → 依次扩大到前后 1 天、前后 3 天；仍无则请用户手指定时间。
   - 用户声明某人必须参加 → 优先保留其时间；否则询问谁可缺席。
   - 无解 → 报告冲突，不创建。

### 5.3 查找会议室

1. 调用 `room.search`：`startTime`、`endTime`、`attendeeCount`；可选 `floor`、`equipment`。
2. `equipment` 可传入，但**当前不参与过滤**；返回的 `facility` 仅供参考展示，勿承诺“已按设备筛好”。
3. 查询结果**不锁定**会议室；以 `room.reserve` 事务结果为准。
4. 无合适会议室 → 建议改时间或放宽楼层/人数，不要强行预约。

### 5.4 预约确认卡（写前必做）

至少包含：

- 主题、开始时间、时长、结束时间（可展示）
- 地点：会议室名称 + 楼层/位置（来自 search 结果）
- 参会人姓名列表（标明是否含发起人）
- 内部已备好但可对用户省略：`roomId`、`attendeePhones`、`requestId`

示例：

> 建议：2026-10-17（周三）15:30–16:30  
> 地点：17楼 郁金香会议室  
> 参会人：张三、李四、我（发起人）  
> 主题：产品评审会  
> 是否创建该会议？

用户明确确认后才能调用 `room.reserve`。

### 5.5 执行预约与核验

```text
room.reserve 参数：
  roomId, attendeePhones, startTime, durationMinutes,
  meetingTheme, requestId, [meetingNote]
```

1. 成功 `status: CREATED` 且拿到 `meetingId` 后，调用 `calendar.verify`：
   - `meetingId`、`phones` = **与预约时相同的** `attendeePhones`（不要擅自加发起人）
   - `startTime` / `endTime`（结束 = 开始 + 时长）
2. 仅当 `verified: true` 且 `status: VERIFIED` 时，向用户报告「会议已预订成功」，并可告知会议编号。
3. `CONFLICT` → 参会人日程冲突，给候选时间或改名单。
4. `BUSINESS_ERROR` → 会议室占用/容量等问题，改会议室或时间。
5. `FORBIDDEN` → 说明权限不足，引导在满天星授权，勿伪装成功。
6. 核验 `NOT_FOUND` / `MISMATCH` 等 → 不宣称成功，进入核对说明。

## 6. 意图流程

### 6.1 完整预约

1. 消歧会议室/系统名称（若涉及）。
2. 抽槽；缺必填则一次追问 2–3 个关键问题。
3. §5.1 选人（含发起人规则）。
4. 时间未定则 §5.2；已定则校验格式与时长约束。
5. §5.3 找会议室；用户点名会议室时用 search 结果匹配名称/楼层得到 `roomId`。
6. §5.4 确认卡 → §5.5 预约与核验。

### 6.2 仅查忙闲

1. §5.1 选人。
2. 确定查询窗口，调用 `calendar.get_freebusy` 和/或 `calendar.find_slots`。
3. 用姓名展示忙闲或候选空档；不创建会议。

### 6.3 查询我的会议

1. 调用 `meeting.list_mine`（可选同传 `startDate`+`endDate`，`yyyy-MM-dd`；`pageNum`/`pageSize`）。
2. 只展示未开始、有效、未取消的会议。
3. 展示主题、时间、会议室、参会人名称、是否 `canCancelMeeting`（仅表示是否发起人，不代替真实取消权限）。

### 6.4 取消会议

1. `meeting.list_mine` 定位目标；同名/多场时请用户选定 `meetingId`。
2. 取消确认卡：主题、时间、会议室、`meetingId`。
3. 用户确认后调用 `meeting.cancel(meetingId, requestId)`。
4. 成功 `CANCELLED` 后再告知用户；`FORBIDDEN` 说明仅发起人可取消且需权限；已开始/已取消按业务失败说明。
5. 不要尝试“取消他人会议”或承诺审批代取消（当前工具不支持）。

## 7. 安全与审计约束

- 所有写操作必须先完成写操作确认。
- 单次会议参会人去重后最多 20 人。
- 只读忙闲区间，不编造或泄露日程主题等详情（工具未返回的不要猜）。
- 不在日志或与业务无关的回复中扩散员工完整手机号。
- 权限以会议系统与平台策略为准；`tools/list` 与账号授权决定实际可调用工具。

## 8. 失败兜底

| 场景 | 处理 |
| --- | --- |
| 会议室被占 / 容量不足 | 推荐备选会议室或改时间，再走确认 |
| 参会人冲突 | 候选时间或调整名单，不自动创建 |
| 读工具短暂失败 | 重试 1 次；仍失败则说明并建议稍后再试或转人工 |
| 写工具 `IN_PROGRESS` / 未知结果 | 停止换号重试，转人工核对 |
| `IDEMPOTENCY_CONFLICT` | 说明同号不同参数冲突，生成新操作与新 `requestId` 前须重新确认 |
| HTTP `401` | 身份/验签问题，不归因为业务冲突 |
| 工具 `FORBIDDEN` | 满天星业务权限不足 |

## 9. 示例（完整预约）

**用户：** 帮我约下周三下午和张三、李四开个 1 小时产品评审会，最好在 17 楼，3 点后。

**Agent（摘要行为）：**

1. `identity.resolve` 解析张三、李四；人员确认后得到手机号；发起人手机号一并加入。
2. 将「下周三下午 3 点后、60 分钟」转为查询窗口，调用 `calendar.find_slots`。
3. 用户确认候选时段后，`room.search`（`floor: "17"`, `attendeeCount: 3` 等）。
4. 展示确认卡；用户同意后 `room.reserve`（含 `requestId`）。
5. `calendar.verify` 通过后回复预订成功。

**用户：** 可以。

**Agent：** 会议已预订成功。（仅在核验通过后）
