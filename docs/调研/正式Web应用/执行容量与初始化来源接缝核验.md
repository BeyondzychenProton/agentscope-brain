| 候选 | 与既定规格的关系 |

## 2. Q19 的容量与优先级边界

现有 [02 号 DDL](../../../db/schema/02_会话运行消息建表.sql)第 161—178 行：普通 Run 默认 `ACCEPTED`，只有成功／失败／取消终态释放 `busy_session_id`；没有 `QUEUED` 枚举。#19 第 241 行已确认新增 `WAITING_INPUT`，尚未落 DDL。排队事实可作为持久调度控制，不能因界面显示“排队”擅自改写上述业务状态；是否需要新增列／枚举仍应由后续结构规格明确。

候选未发现必须推翻既定业务语义的冲突，但需要以下界限才能成立：

- **“2”应明确计数什么。** 前台受控执行许可、原 Run 数和 Java／SDK 内部线程数并不天然相等；“16”也应明确是普通新任务待执行容量，不能把等待用户、已接纳 FORM 回答、操作确认账本和 RECONCILING 一并当作普通队列。原 Session 活动占用与执行资源占用保持独立。
- **等待用户不占执行线程，不等于释放 Session。** 既定 native 挂起会结束本次调用，但必须完成 checkpoint／等待就绪核验；不能仅收到等待事件就按界面释放所有控制。状态异常仍按既定 RECONCILING／Session 阻断处理。
- **普通容量检查与成功去重分别处理。** 同键已经接纳的请求回查原 Session／消息／Run，不能因为今天队列已满改答“未接纳”。新输入若容量耗尽且确定未接纳，不得产生半条正式消息／Run；原 submission_key、提交控制及草稿仍按已定 Q12／#21 返回准确事实，未知时先核对，不自动换键重发。
- **已有回答不能被容量丢弃。** FORM 已完成 SQL 接纳就保留正式回答及 `ACCEPTED` 事实；暂时没有执行许可只能等待受控调度，不能改成回答未保存、删除消息或要求再填一次。续接优先不允许抢占／重复已领取 SDK 调用，不允许按租约超时自动重送回答。
- **操作确认不是 FORM 再消费。** 确认的 `CONSUMED` 与操作待发送已经同事务落盘；发送领取及当前鉴权仍由工具模块处理。优先级不能成为第二次消费授权或重放 UNKNOWN 写请求的入口。
- **优先不是绕过门槛。** 续接仍核验登录、归属、原版本／状态、未领取证明及 fence；取消／失效处理不能被普通队列长期阻挡。优先策略也不撤销已经开始的前台工作。
- **持久队列不授权启动重放。** 重启只恢复可读性和允许的只读核对；即使有 `ACCEPTED` 调度记录，仍须按既定明确继续／重试及状态证明启动后续执行。不能把“持久化”解释为扫描后自动调用模型／会议写操作。

本节只核验边界，没有决定新的状态枚举、队列算法、抢占策略或调度表。对应依据：#19 第 97—107、121—145、161—180、188—190 行；[#21 规格](../../正式应用设计/工作台交互与前端工程设计规格.md)第 111—119、163 行；[普通输入接纳](../../数据库设计/会话运行与消息/一期会话运行消息数据库设计草案.md#41-接纳输入与重试)第 88—91 行。

## 3. Q20 已定参数与新增参数

[Issue9 规格第 196—202 行](../../数据库设计/状态记忆与工作区/Issue9实体与约束评审及记忆控制建表规格.md#43-重试策略)已经确认应用配置默认值：最大领取 **5 次**；从 **30 秒翻倍退避，上限 15 分钟，±20% 抖动**；租约 **10 分钟**，实际值需结合模型耗时校准。这些默认值不是本轮新推荐。

独立单 worker、5 秒扫描及不与前台共用执行池尚待 Q20 确认。它们不改变：只学成功来源、有效代次／授权版本、任务唯一性、条件领取与应用后核对；扫描只找已到 `next_attempt_at` 的任务，不能每 5 秒重新执行全部任务。租约过期先核对是否已应用，不盲目重做；`FAILED` 不新增人工重试入口。见同规格第 137、174—186、283 行及 [03 号 DDL](../../../db/schema/03_记忆控制建表.sql)第 59—75 行。

前台 2 与后台 1 若分别计算，可能同时存在前台与记忆模型调用；不能把它宣传成全系统总 SDK 并发恰好为 2。分池也不自动隔离数据库／模型服务资源，本页不据此增加新配额或外部限流方案。

## 4. Q21 对现有结构的最小影响

### 4.1 已有可空与来源字段

[01 号 DDL](../../../db/schema/01_用户与管理员建表.sql)已经允许：`platform_user.created_by_user_id/modified_by_user_id` 为空（第 15—16 行）、`identity_audit_event.actor_user_id` 为空（第 121 行）；`phone_reservation.ownership_checked_by` 也可空，但其注释只写管理员初始化（第 65 行）。[05 号 DDL](../../../db/schema/05_员工配置发布与授权建表.sql)的 `employee_draft.saved_by` 可空，仅初始化草稿（第 29、34 行）。这些是局部先例，不是通用 SYSTEM_BOOTSTRAP 机制。

现有 `fixed_admin_assignment.initialization_ref`（01 第 46 行）只属于管理员绑定，不应为复用它而新建管理员；手机号 `ownership_source_ref`（第 64 行）是号码归属核对来源。身份审计 `request_id` 仅为可空、非唯一关联标识（第 134、141 行）；配置审计 `request_id/change_summary` 是请求和脱敏摘要（05 第 114—117 行）。**没有一组现成、受约束的通用“系统初始化来源类型＋来源编号”覆盖预置账号、授权、绑定与发布。**

### 4.2 需要调整的既有表／约束

若采用 Q21，下列四表的操作者列需支持**仅系统预置分支**为空，同时保留其他来源正数操作者的要求；不是对全部记录无条件放空：

| 既有表 | 非空列与受影响约束；05 号 DDL 行号 |
| --- | --- |
| `employee_release` | `published_by`、`availability_changed_by`：48、52；`chk_employee_release_positive`：61。 |
| `tool_binding_revision` | `created_by`：74；`chk_tool_binding_positive`：81。 |
| `employee_use_grant` | `granted_by`：90；`chk_employee_grant_positive`：99。当前 ACTIVE／REVOKED 配对约束不因初始化而自动放宽。 |
| `employee_configuration_audit_event` | `actor_user_id`：106；`chk_employee_config_audit_positive`：126；成功收据唯一键：122。 |

最小新增责任是把上述初始化行可靠关联到 `SYSTEM_BOOTSTRAP` 和非空来源编号，并写入真实初始化审计；具体采用逐表字段或关联一份受控初始化事实，本页不替用户决定。既有可空列和注释也应明确该来源，不能把所有 NULL 泛化成合法系统操作。来源码与动作码分开：配置审计动作 CHECK 目前只有 DRAFT_SAVE／EMPLOYEE_PUBLISH／RELEASE_DISABLE／RELEASE_ENABLE（第 127 行）；若另定义初始化动作须同步评审，不能直接把来源字符串塞入该列。

**成功收据不能只改 actor 为 NULL。** 当前 `uk_actor_success_request(actor_user_id, success_request_id)` 以操作者划定成功请求唯一范围；MySQL 的 UNIQUE 允许可空列出现多个 NULL（[MySQL 8.0 官方索引说明](https://dev.mysql.com/doc/refman/8.0/en/create-index.html)）。允许系统 actor 为空后，必须仍为系统来源提供确定的、可唯一约束的成功请求范围，不能假称原键自然维持系统幂等。来源编号也不能仅写自由文本摘要而失去关联及查重依据。这里标记结构缺口，不在本页选择新索引。

现有 [09 号全库巡检](../../../db/tests/09_一期全库关联巡检.sql)第 10—20、94—95 行把发布、绑定、配置审计、授权操作者连到 `platform_user`，NULL 会按原查询报告孤儿。采用系统来源后需同步来源条件和巡检责任；没有必要伪造管理员、第二账号、用户 ID=0 或普通用户执行管理动作来让旧巡检通过。

## 5. 当前结论

Q19／Q20 没有与既定 Session 独占、持久接纳及恢复规则不可调和的冲突，但容量／优先级不能覆盖那些协议；数值仍待确认。Q21 是新增初始化来源语义，最少触及上述四表、来源关联、系统收据唯一范围及相应巡检，并非仅给一列放开 NULL 即完成。三项均须在用户采纳后进入字段／事务规格和隔离验收；本次未修改任何 DDL、正式设计或数据。
