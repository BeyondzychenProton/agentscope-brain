## 1. 研究回答与证据边界

现有方案能够复用事件类型、浏览器客户端、声明式组件和表单校验；**没有一项被核验的协议或组件直接交付本项目要求的业务 Session／Run 持久事实、可信身份、服务端业务校验、重启核对及一次性操作确认。**这部分仍须由平台设计和实际验收证明。

需要分开判断三层：

| 层次 | 主要候选 | 可以复用什么 | 不能由它推导什么 |
| --- | --- | --- | --- |
| Agent 与应用之间的事件／交互协议 | AG-UI | 流式文本、工具调用、状态、进度、中断与回应的线格式和行为规则 | 数据库事务、外部工具权限、原流断点续传或平台业务 Run 自动恢复。依据：[协议范围][ag-spec]、[SSE 绑定][ag-sse]。 |
| 动态界面表达与渲染 | A2UI；JSON Schema + JSON Forms；受控自有组件 | A2UI 的组件目录和界面更新；JSON Forms 的表单布局、控件、数据绑定与校验 | 业务任务执行引擎、写操作授权和耐久工作流。依据：[A2UI 渲染器职责][a2-renderers]、[JSON Forms 介绍][jf-intro]。 |
| 平台运行与业务控制 | 本项目平台 + AgentScope 适配 | 原业务 Run、交互关联、已接纳输入、工具提案、确认、执行及恢复事实 | 不能把上两层的内存状态或演示行为作为已落地能力。依据：[一期总体设计](../../一期总体设计.md)、[通用素材与工具操作设计](../../数据库设计/会话运行与消息/通用素材与工具操作设计.md)。 |

因此 AG-UI 与 A2UI 可以组合；JSON Forms 也可以搭配 AG-UI 或平台自己的事件接口。它们不是三个互相替代的完整应用框架。[AG-UI 官方层次说明][ag-intro]、[A2UI 传输职责][a2-transports]支持这一划分。

本研究足以回答纯研究问题：“哪些能力可复用、边界是什么、下一步需验证什么。”是否采用某个组合，仍需下游设计确认及小范围兼容性验证；关闭研究议题不表示实现或验收完成。

## 2. 已确认输入与参照原型

研究沿用[一期总体设计](../../一期总体设计.md)和[平台术语](../../../GLOSSARY.md)的现行边界：普通用户工作台是唯一 Web 入口；固定管理员不开放 Web 登录；不开发管理页面或管理 API；一期单节点、低并发。用户已经确认通用动态表单采用“数字员工按任务提出结构 → 服务端校验 → 前端受控组件渲染”。前端技术栈尚未确定。

本次参照为用户提供的 `海卓大脑原型-v1.0.2-20261021.html`，接收细节见[参照原型接收记录](../../正式应用设计/参照原型接收记录.md)。源码中的多字段澄清、人员选择、候选时间、操作确认、故障备选和回执可以提供讨论场景；它采用硬编码 HTML／JavaScript 和内存等待机制，不具备通用 Schema、服务端或持久恢复。本研究没有把原型中的管理功能、工具名及业务重试文字扩充为正式契约，也没有对其作浏览器运行验收。

表单集中收集主题、时间、人员等输入；人员选择确定候选身份；预约／取消确认授权本次固定提案。这三件事沿用本项目现有区分，**提交表单不能顺带授权预约或取消。**确认参数变更后旧确认失效、十分钟有效期、同一提案的一次性消费和发送前再次鉴权，已有规格继续适用，不因采用交互协议而重定。

## 5. AG-UI：事件可复用，业务运行边界需要适配

### 5.1 事件顺序与展示含义

AG-UI 1.0 要求流以 `RUN_STARTED` 或 `RUN_ERROR` 开始；正常结束、等待外部输入和取消有不同 outcome。断开连接只说明流被截断，客户端不能自行补出成功或取消。HTTP 200 也不能证明 Run 成功，流打开后的错误通过 `RUN_ERROR` 报告。[生命周期][ag-lifecycle]、[SSE 绑定][ag-sse]。

文本按 Start／Content／End 累积；工具按 `toolCallId` 关联 Start／Args／End／Result。`TOOL_CALL_END` 仅代表参数文本完成，不能证明参数有效，更不能表示工具已执行；End 前不能据部分参数触发动作。工具回执应依据服务端实际操作结果投影。[文本规则][ag-text]、[工具规则][ag-tools]。

`STATE_SNAPSHOT`／`STATE_DELTA` 适合共享状态；`ACTIVITY_SNAPSHOT`／`ACTIVITY_DELTA` 适合结构化过程组件。Activity 在显示序列中有位置，但按规范不能作为正式对话回传给 Agent。用这些事件展示阶段进度是可行选项；它不改变项目“正式回复与 Run 过程输出分别保存”的规则。[状态][ag-state]、[Activity][ag-activity]。

### 5.2 中断续接与业务 Run 不可直接等同

AG-UI 的中断会关闭当前**协议 run**，由下一协议 run 的 `resume` 回答。其输入须覆盖前一个中断 run 的所有 interrupt，并沿用 thread、消息及状态；规范甚至允许 producer 不记住旧中断仍然符合协议。因而 `interruptId`、`responseSchema` 或客户端“已回答”都不能充当服务端持久确认台账。[中断与回应][ag-interrupt]。

本项目已有“确认和取消仍属于原业务 Run、同 Session 只有一个活动 Run”的设计。若采用 AG-UI，需在下游明确业务 Run 与一个或多个协议 run 的关联，不能因协议要求新 `runId` 就自动创建第二条并发业务任务。建议评审“原业务 Run 关联多个协议交互片段”的映射；这只是候选，尚未确认。普通动态表单等待是否占用原业务 Run，也须在交互契约中明确。

### 5.3 断流、历史与恢复

AG-UI 1.0 HTTP+SSE 绑定明确：不使用 `Last-Event-ID`，不能重新进入断开的流；重新运行需要新 `runId`。浏览器应使用能发 POST 并消费 SSE 的客户端，例如 `HttpAgent`，不能把只做 GET 的原生 `EventSource` 直接视为默认运行请求接口。[SSE 绑定][ag-sse]、[HttpAgent][ag-http-agent]。

官方 serialization 说明给出事件保存、恢复和压缩的模型，示例仍由宿主提供 `storage.save/load`。这可帮助重建 UI，不证明本项目已实现事件落盘、重连追赶、AgentScope checkpoint 或外部写操作安全恢复。断线后的读取应恢复已知状态，不能把用户刷新页面实现为重跑整轮模型或重发会议写操作。[序列化说明][ag-serialization]及本项目[业务会话恢复要求](../../数据库设计/会话运行与消息/业务会话运行消息与跨渠道续传设计规格.md)。

### 5.4 Java 与前端成本

TypeScript client 不要求 React，Vue／React 均可接入事件与自己的组件；协议本身不交付完整工作台。Java 社区 core 已有 resume／outcome 类型，但框架事件到 AG-UI 的投影、可信业务输入重建和 Spring Boot 3 接入仍要做适配与编译验证。当前社区 Spring POM 的 Boot 4.1 声明既不是升级本项目的理由，也不是 Boot 3 兼容证据。[TS client package][ag-client-pkg]、[Java 中断类型][ag-java-resume]、[Java interrupt outcome][ag-java-interrupt]、[Spring POM][ag-java-spring]。

## 6. A2UI：较完整的动态界面语言，仍需受控目录和服务端交互

### 6.1 表达与校验

A2UI v0.9.1 以 `createSurface`、`updateComponents`、`updateDataModel`、`deleteSurface` 表达界面生命周期。组件以 ID 组成邻接表，结构与数据分开，可增量生成；这比仅传字段集合开放得更多，也增加了组件关系、生命周期和无效更新的校验工作。[组件结构][a2-components]、[v0.9.1 规范][a2-spec]。

目录是允许使用的组件、函数和主题的契约。可沿用 Basic Catalog 或定义受控目录；接纳一个 A2UI 外壳并不表示应该允许模型使用所有组件、函数、外链或任意 inline catalog。本项目若采用，服务端须校验选定协议 Schema、目录 Schema 及自身约束；前端只注册受控实现。[目录机制][a2-catalogs]、[自定义目录][a2-custom-catalog]。

输入组件有本地双向绑定；用户打字不会自动发送服务端，`action` 的 context 或 `sendDataModel` 才携带当前值。checks 调用预注册函数提供输入错误与按钮禁用。这有助于体验，但不等于服务器已验证人员候选、时间范围、会议可用性或操作者权限。[数据绑定][a2-data]、[动作][a2-actions]、[Basic Catalog 指引][a2-basic]。

### 6.2 响应、顺序与持久化缺口

v0.9.1 的 action 含名称、surface、来源组件、时间及 context；这些都是客户端消息。尤其 `timestamp` 不是服务端接纳顺序，`surfaceId` 不是认证归属，一次点击不是一次性消费事实。v1.0 的 action ID／RPC 能力也不能替代项目现有确认控制。[动作][a2-actions]、[当前／候选版本区别][a2-home]。

A2UI 要求底层按生成顺序交付并明确消息边界，否则先更新后建 surface 可能损坏 UI。协议不替平台提供断线重放、已提交动作去重、过期判断或重启 checkpoint。恢复界面可以重建受控 surface／data 快照；恢复业务动作必须先读取平台事实。不能由餐厅预约演示推出耐久恢复。[传输职责][a2-transports]、[v0.9.1 传输契约][a2-spec]、[服务端示例定位][a2-agents]。

### 6.3 Java 与 Vue／React 成本

Java 后端可以生成／校验 JSON 并通过选定事件接口传递，无需为采用 A2UI 改用示例中的 ADK；但本次没有核验出可直接替本项目完成 AgentScope 运行接入的 Java A2UI 引擎。这个结论是本次已查资料的边界，不是断言生态绝无 Java 实现。[服务端职责][a2-agents]、[传输独立性][a2-transports]。

React 可以评估维护的 renderer，仍须处理版本化入口及自有视觉组件；Vue 可评估嵌入 Lit Web Components 或实现自己的 renderer。后者涉及自定义元素注册、事件和数据绑定、主题、键盘／焦点与打包验证，不能说“协议框架无关”就认定零成本。当前维护列表没有 Vue 原生包，也不代表 Vue 无法使用 A2UI。[渲染器表][a2-renderers]、[客户端共同核心][a2-client-setup]、[固定 React README][a2-react-readme]。

## 7. JSON Schema + JSON Forms：更聚焦表单的数据与布局

JSON Forms 把数据 Schema 与 UI Schema 分开，并允许注册自定义 renderer。React 独立组件以 props 接收数据／Schema、通过 `onChange` 提供数据与校验结果；Vue 3 有官方绑定、HTML5 和 Vuetify renderer。它适合在聊天中挂载一块多字段表单，不负责聊天流、运行过程或等待恢复。[介绍][jf-intro]、[React API][jf-react]、[Vue 状态][jf-vue]。

这里的“官方组件”指 JSON Forms 维护方的 renderer，不是 JSON Schema 规范指定的唯一组件。JSON Schema 官方工具目录也明确：收录不代表推荐或背书。Java 需要另选并固定与前端一致的校验实现／草案，而非把浏览器 Ajv 当作服务端校验。[JSON Schema 工具说明][js-tools]。

需要评审两个不同契约：一是约束“数字员工可以提出什么 Schema／布局”，二是按接纳后的 Schema 约束“用户可以提交什么值”。JSON Forms 默认 Ajv 的 `strict:false` 允许一些严格模式本会拒绝的 Schema；不能把“能渲染／编译”当作平台已接纳全部关键字。复杂或外部 `$ref` 还需要预先解析，故应由平台控制引用及允许的 Schema 子集。[默认校验][jf-validation]、[固定实现][jf-validator]、[引用解析][jf-refs]。

Draft 2020-12 的默认 `format` 是 annotation；若需要 assertion，必须约定实现／配置。日期格式合法也不能证明结束晚于开始、时区一致、会议室可用，人员枚举合法也不能证明候选仍有效。这些继续由应用业务校验负责。[JSON Schema Validation][js-validation]。

一期可评审的最小字段集合为短文本／长文本、数值、布尔、单选／多选、日期时间、人员候选引用以及只读说明；布局先限分组与纵向排列。该集合只是用于估算和验证的建议，未形成产品决定。候选人员显示名和真实引用应来自服务端可信查询，模型可以提出需要收集什么，不能自行捏造可执行人员标识或操作者。

## 8. 可评审组合与选择顺序

以下组合用于讨论，不作最终推荐；同一表单 renderer 也可与不同事件协议组合。

| 组合 | 适用收益 | 实质成本与待证项 |
| --- | --- | --- |
| AG-UI 1.0 + JSON Schema／JSON Forms 受控子集 | 复用运行／文本／工具事件及局部表单；保持“字段数据”和“工作台布局”边界较清晰 | Java 事件桥接、业务 Run 与协议 run 映射；草案一致性；Vue preview／具体 renderer 的组件覆盖和主题成本。 |
| AG-UI 1.0 + A2UI v0.9.1 受控目录 | 复用事件传输与动态表单之外的结构化卡片／布局表达，后续组件能力较开放 | 双层协议及目录版本；surface 生命周期；服务端生成约束；React 入口或 Vue/Lit 兼容；更大表达面与渲染成本。 |
| 平台事件投影 + JSON Schema／受控组件（可局部用 JSON Forms） | 可直接围绕已有 Session／Run／操作状态设计；动态表单表达面可以较小 | 自己承担事件顺序、客户端状态合并、断流恢复、兼容与工具可视化；不能把“少引依赖”算作已减少整体工作量。 |

建议先明确“等待输入／确认期间的业务 Run、协议 run、恢复读取怎样关联”，再由参照原型收敛“字段表单还是更开放的组件目录”；最后用相同 fixture 比较前端实现成本。不能仅因某 SDK 提供 React 演示就先锁 React，也不能仅因用户曾使用 Vue 就先排除 React。该顺序为研究建议，下游仍由用户确认。

不在本研究追加工作流平台、任意页面生成、远程前端工具执行、管理后台或 A2A 组网选型；它们不是完成当前用户工作台和动态表单的前提。

## 9. 无论选择哪种组合，都需补齐的平台交互契约

以下是下游需作出的设计，不是本研究新增的已确认字段或建表决定：

1. **交互归属和版本。** 哪个业务 Run 在等待哪份表单／人员选择／操作确认；交互 ID、受控 Schema／目录修订、候选集合、已展示内容和失效条件如何固定。客户端只能回答服务端已经提出且本人可见的当前交互。
2. **服务端接纳。** 分开校验模型提出的结构与用户提交的值；检查规模、类型、引用、选项、业务语义和当前权限。身份、会话归属与发布版本由服务端重建，不从模型状态、A2UI context 或前端隐藏字段取得。AG-UI 也明确要求跨信任边界校验，不能将流内容作为可执行标记。[安全要求][ag-spec]。
3. **响应去重与竞争。** 双击、网络重试、多标签、旧卡片与新卡片同时提交时，如何一次接纳并返回一致结果；输入未通过校验时如何保留用户填写值；模型晚到更新如何避免悄悄覆盖正在编辑的数据。
4. **展示投影和恢复读取。** 正式消息、过程片段、表单、确认卡和操作状态各自保存什么；刷新怎样取得可信快照，随后接收新增事件；序号／版本缺口、重复及不认识的组件怎样处理。若使用 AG-UI，需要明确平台恢复接口与标准“不可续入原 SSE 流”的关系，不能把自己的游标恢复宣称为标准绑定自带能力。
5. **等待、取消和重启。** 待表单输入、待操作确认和外部结果不明怎样显示；关闭页面不等于取消业务；重启先恢复事实或转待核对，不自动重跑会议写操作。
6. **输入与执行授权分离。** 表单提交／选人先形成被接纳的输入；预约或取消再生成固定 `tool_operation`，展示确切参数，走已有 `operation_confirmation`。执行前重新鉴权、稳定 `requestId`、未知结果核对继续执行原设计，不由一条 `resume` 或 `action.name` 越过。

普通输入、交互响应与操作确认在 Web 上可以相邻展示，但后端不能将它们合成一个“任意 JSON → 任意工具执行”的入口。工具效果类型和需要确认与否由受控策略决定；浏览器不持有会议 MCP 密钥，也不直接执行预约／取消。依据：[一期总体设计](../../一期总体设计.md)及[通用素材与工具操作设计](../../数据库设计/会话运行与消息/通用素材与工具操作设计.md)。

## 10. 最小验证建议与通过标准

本节未执行。可在用户确定候选之后，先用固定的合成 fixture 验证，不需要付费模型或真实会议写操作。

| 验证 | 最小输入／动作 | 要证明的结果 |
| --- | --- | --- |
| 版本和 Java 接入 | Java 17／目标 Spring Boot 3 编译依赖；固定 TS 包；若用 A2UI，显式选择 v0.9 入口，输入 v0.9.1 消息 | 实际依赖、入口与线格式一致；不因社区 starter 改动既定后端大版本；记录通过／不通过及原因。 |
| 流与阶段 | 文本分片穿插工具参数、Activity／State；错误序列、缺 terminal、HTTP 200 后 `RUN_ERROR` | 不提前执行工具；有序投影；缺 terminal 保留未知／中断事实；不展示为成功。 |
| 动态表单覆盖 | 同一组主题、日期时间、人员多选、数字／布尔、必填／枚举、字段错误 fixture | 能表达一期所需字段；Vue／React 候选分别测焦点、键盘、错误提示和原型视觉适配；不以演示页面代替组件覆盖。 |
| 结构和业务校验 | 未知字段／组件、越界、伪造人员引用、外部引用、无效时间、过期候选 | 服务端拒绝未允许结构与无效值；错误能定位到字段并保留其余输入；客户端绕过 checks 不能获得业务权限。 |
| 数据竞争 | 正在填写时收到晚到默认值／schema 修订，多标签提交同一交互 | 采用事先约定的覆盖／失效规则；不丢已输入值；过时响应可解释地拒绝，只有一次接纳。 |
| 页面断连与重开 | 服务端任务持续；关闭再打开页面 | 从持久事实恢复消息、过程和待办，再接新增投影；不重启模型或重发工具来重建页面；若有平台游标恢复，明确它是自有契约。 |
| 等待与进程重启 | 持久保存一份待表单和一份待确认；重启后响应 | 归属、修订、过期、授权均重新检查；已接受响应不重复；无法安全续接时进入明确待核对状态。 |
| 表单与写确认分离 | 提交表单后查看发送记录；再确认固定提案；改参数／十分钟后／重复确认 | 仅表单提交不发送写工具；旧确认无效；同一提案最多一次发送领取；发送后结果未知走核对，不换请求号重发。 |

前两行主要消除协议／SDK 接入不确定性；中间几行支持交互设计；最后几行需要平台持久化与状态机完成后实际验收。不能因静态研究或一个浏览器 demo 通过，就宣称耐久恢复和真实业务闭环通过。

## 11. 研究议题的关闭依据及公开安全摘要

可将“核验动态表单与交互协议复用方案”按研究完成处理：已取得官方版本与固定源码、分层能力比较、Java／浏览器成本、表单／确认边界、恢复缺口和最小验证建议。未选择最终方案，未改变已确认业务规则，也未修改远端议题。

后续仍需决策：事件投影及业务 Run 映射、动态表单／组件目录允许范围、用户响应与恢复协议、Vue／React 和 renderer、服务端校验草案与实现。这些属于后续设计，不能由本研究代替用户决定。

以下可用于 GitHub resolution 评论，引用本文件的可审阅版本即可；不包含本机个人路径、测试凭据或业务个人信息：

- 已按官方规范与固定源码完成核验：AG-UI 1.0，A2UI v0.9.1 当前生产规范及 v1.0 候选边界，JSON Forms v3.8.0 与 JSON Schema 草案差异。
- AG-UI 是 Agent／应用事件协议，A2UI 是动态界面表达，JSON Forms 是表单 renderer；能够组合，不能当作互斥完整方案。
- AG-UI HTTP+SSE 标准绑定不提供 `Last-Event-ID` 原流续传；interrupt/resume 使用新的协议 run，不自动等同平台业务 Run。持久恢复、可信身份、业务校验、响应去重和操作确认仍由平台负责。
- Java 社区 SDK、A2UI 渲染入口、Vue preview／Lit 嵌入等已列明确实质成本；没有据演示或包存在宣称兼容与恢复通过。
- 表单提交／人员选择与预约或取消的一次性确认保持分离。已有固定提案、有效期、重新鉴权、稳定请求号及未知结果核对规则继续有效。
- 研究已足以支持下游设计评审；前端框架、事件方案和表单 renderer 尚未确定，最小验证和应用／真实会议验收仍未执行。
