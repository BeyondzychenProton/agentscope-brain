## 2. SSE 的原生行为与应用责任

### 2.1 官方事实

- EventSource 接收服务端推送的 `text/event-stream`，接口没有发送用户回答的方法；构造请求沿用 Fetch 默认 GET。连接断开后，浏览器可自动重连。[WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events)、[Fetch 请求方法](https://fetch.spec.whatwg.org/#concept-request-method)。
- `id` 设置 last event ID；自动重连时，非空值通过 `Last-Event-ID` 回传。它是字符串，不自带数字递增、持久日志或确认语义；空 `id` 会清除该值。[WHATWG Last-Event-ID](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)、[事件解析与分发](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)。
- 浏览器先更新 last event ID，再排队分发 JavaScript 事件；未以空行结束的残缺事件不分发。因此解析位置不证明业务处理成功。[WHATWG 分发算法](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)。
- GET 的标准语义是安全读取，但规范也区分方法语义与服务器实际行为；只使用 GET 不能证明实现没有副作用。[RFC 9110 安全方法](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.1)。

### 2.2 项目推论，尚非接口决定

可把 SSE GET 设计为仅读取平台已持久投影的单向通道，用户提交／确认仍走既有写入口。服务端必须独立落实鉴权、归属、历史查询、去重和不触发 SDK 的约束；这些能力不是 SSE 自动提供。

必须区分浏览器解析到达位置与应用成功应用位置。只有完整校验并应用一批投影后，应用才能前移自己的恢复游标；SSE 的 last event ID 不是用户接纳、操作确认或持久消费凭据。应用处理失败时，应停止该消费链，按已应用位置补读或重建，不能借自动重连越过失败事件。这是依据分发算法作出的应用层推论，不是浏览器提供的业务 ACK。

## 3. SQL 事务、单会话顺序与提交游标

### 3.1 官方事实

- MySQL 明确示例：读取并递增共享计数器可以使用 `SELECT ... FOR UPDATE`；其排他行锁持续到事务提交或回滚。普通一致读不足以保护这种读改写。[MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。
- `COMMIT` 提交当前事务的变更，`ROLLBACK` 取消变更；默认 autocommit 下，各条语句各自形成事务，不能据此认为多条业务／事件写入原子关联。[MySQL 事务控制](https://dev.mysql.com/doc/refman/8.0/en/commit.html)。
- `AUTO_INCREMENT` 的分配控制不保持到事务结束：传统 AUTO-INC 锁至语句结束，简单插入的分配互斥可更短；回滚也不回收已分配值。[MySQL 自增锁及空洞](https://dev.mysql.com/doc/refman/8.0/en/innodb-auto-increment-handling.html)。
- `CURRENT_TIMESTAMP` 是 `NOW()` 的同义词；`NOW()` 表示语句开始执行的时间，不是事务提交时间。[MySQL NOW 与 CURRENT_TIMESTAMP](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-functions.html#function_now)。

### 3.2 项目推论，候选构造而非已定表结构

要让 `seq > cursor` 的查询可靠追赶，同一 Session 的可见序列应形成提交前缀：不能先对外可见较大序号，随后才提交更小序号。

一种可证明的候选是：所有相关写路径遵守统一锁顺序，在同一 SQL 事务内锁定同一 Session 的序号行，分配下一段 `seq`，保存业务变更、确定的投影载荷及对应日志，然后提交；后续写者在前一个事务提交／回滚后才能取得该行锁。多对象变化可作为一个投影批次，客户端完整应用后再推进游标。具体字段、批次格式及锁顺序仍待设计与验证，不能只靠内存单线程约定。

普通自增主键不能单独承担此保证。例如 A 已分配 41 尚未提交，B 分配 42 先提交，读者推进到 42；A 随后提交的 41 会被 `id > 42` 永久漏掉。这是由官方分配／锁语义推导的反例，不是本项目实测。时间戳同样在提交前产生，不能单独证明提交顺序；补一个自增 ID 作排序也不会消除上述竞争。

因此，“业务事实已写，稍后在另一事务补事件”也不能自动保证快照与事件的同一水位。若采用事务内关联方案，所有会改变 Web 投影的写路径都须覆盖该关联；事务外通知只能唤醒读取，不能成为唯一事件事实。

## 4. 跨表快照与 watermark

### 4.1 官方事实

InnoDB 在 `REPEATABLE READ` 下，同一事务内的一致读使用首次一致读建立的快照；`READ COMMITTED` 则每次一致读建立新快照。普通一致读不会阻止其他事务修改数据。[MySQL Consistent Nonlocking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。

`START TRANSACTION WITH CONSISTENT SNAPSHOT` 不会改变隔离级别；该选项须配合 `REPEATABLE READ` 才得到该一致快照保证。锁定读取读取最新可用数据，与普通一致读的历史视图不同。[MySQL 事务快照](https://dev.mysql.com/doc/refman/8.0/en/commit.html)、[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。

### 4.2 项目推论，快照方案仍待确认

若采用非锁定一致读构造跨表快照，消息、Run、交互、操作投影和 watermark 须来自同一 read view；只把多条查询放进 RC 事务，或混用最新锁定读，不能自动证明它们处于同一水位。watermark 还须满足上一节的提交前缀条件。

反例：先读旧消息与交互，随后某事务提交新状态和事件 51，最后再从当前视图读取 `MAX(seq)=51`。客户端拿到旧内容却从 51 之后追赶，事件 51 被跳过。问题是混合视图；不是禁止在同一一致视图内读取最大可见序号。

因此应证明返回快照与其 watermark 对应，再从该水位之后读取持久增量。采用什么事务入口、查询组织和快照格式，留给 #20 后续确认；本文没有宣布这一方案已经决定或实现。

## 5. 断线、慢消费者与缺口

**官方事实：**SSE 定义连接重建和事件解析，没有要求服务器保存历史，也没有定义应用日志、保留期限或慢消费者补偿；不完整事件可在断线时被丢弃。[WHATWG 处理模型](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events)。

**项目推论：**在“已持久内容可恢复”的约束下，连接、内存通知和发送队列只能是可丢失的传输设施。断线或消费积压后，应从持久日志按应用已成功使用的游标补读；队列溢出不能丢掉中间事件后继续前移。若所需日志已不可用、协议不兼容或缺口无法补齐，应明确要求重新读取一致快照或停止展示更新，不能无声跳过。

重读的是已保存输出，不是重新执行模型或工具。持久化前合并正文不会破坏此边界；日志记录一旦提交，其序号和含义应保持可核验，不能为迁就慢客户端而悄悄改写历史。

## 6. 后续须证明的最小场景

以下为研究推导的验证要求，尚未运行：

1. 两个同 Session 写者交错、回滚与提交，游标不会跨过晚提交的小序号；业务与投影不会单边提交。
2. 生成跨表快照时并发产生新事件，返回内容与 watermark 一致，追赶不漏事件。
3. 重复事件、残缺帧、处理失败、多对象批次未完整应用，应用游标不提前前移。
4. 慢消费者、发送队列溢出和通知丢失后，持久补读仍完整；不可补读时明确重建，不静默跳号。
5. 初次订阅、自动重连和快照恢复的模型调用、SDK 执行及会议写发送数均为零。

这些场景只能证明设计在实际实现中的成立程度；静态规范研究不等于 #20 实现或运行验收完成。
