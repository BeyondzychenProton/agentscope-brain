## 2. 官方事实可以支持什么

**MySQL。** InnoDB 的 `SELECT ... FOR UPDATE` 在事务中锁定最新可用记录，相关锁于提交／回滚时释放；普通一致读不提供同等互斥。唯一索引、INSERT 与重复键处理涉及记录锁，竞争还可能产生死锁；具体锁范围受索引和查询条件影响。[MySQL 8.0：锁定读取](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)、[各类语句取得的锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)

**项目推论。** 一次普通查询“暂时查不到正式消息”，不能证明迟到请求不会随后提交；现有消息成功唯一键也不能独立表达“原键已永久结束接纳”。需要所有竞争路径共享的持久控制身份和状态门槛，不能用进程 Map、一次查无记录或跳过锁定行的查询替代。新增记录必须纳入原全局锁序；唯一冲突／死锁后的重试仍使用原键和原语义，不能重放已经发送的会议操作。

**JDK。** Java 17 的 `Cipher` 标准变换包含 `AES/GCM/NoPadding`；GCM 为加密内容提供认证标签，解密时核验标签。官方特别要求：同一密钥下，每次 GCM 加密使用不同 IV，重复 IV 会带来伪造风险；调用方须管理这个唯一性，不能只因使用 API 就认为已自动满足。[JDK 17：Cipher API](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/Cipher.html)

`GCMParameterSpec` 承载 IV 和认证标签位数。[JDK 17：GCMParameterSpec](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/crypto/spec/GCMParameterSpec.html)

**项目推论。** 可以保留既定随机 token 与 SHA-256 校验，另以成熟 AES-GCM 保存可恢复的加密副本；算法能力不替平台提供 keyId、独立密钥管理、nonce 唯一性、归属检查或一次性消费。此处是新增恢复机制候选，不改变随机生成 token 的既定选择，也不采用 HMAC 重签来替换它。

## 3. 候选机制的最小结构责任

以下是判断候选是否完整的最小责任清单，不是已通过的字段规格、表名或状态枚举。

### 3.1 图片暂存记录

需要持久表达：服务端上传 ID／上传幂等键、可信 owner、目标 Session 或新建意图及员工／固定能力上下文；受控对象定位和验证后的类型／字节／像素／摘要；上传／校验／可接纳／绑定正式素材／禁止绑定／清理等语义状态；固定到期时间、版本／fence、绑定正式消息／素材结果与核对原因。

- 待确认 Q11 的“24 小时”只用于未发送暂存，起算点须明确；刷新／重试不能悄悄续期。正式绑定后退出临时 TTL 清理范围，不能让历史图片跟随暂存过期删除。
- 到期与物理删除是不同阶段：清理须先持久阻止新绑定，排除在途接纳／结果待核对，再处理对象删除；对象删除失败保留可重试事实，不能反向开放绑定。
- 上传未知回查原上传 ID／键及对象验证事实，不能自动分配新对象或按客户端文件名重建。对象元数据和 SQL 不天然原子。

### 3.2 普通提交控制记录

需要持久表达：`actor + submission_key` 唯一身份、固定规范语义摘要、目标 Session／新建意图、参与接纳的暂存引用；处理／已接纳／确定未接纳且已封闭等语义状态、行版本或 fence、正式消息／Run／Session 结果和终结原因。现有正式消息唯一键继续保留为成功底线。

- 提交回查只读展示原事实；没有记录时最多说明当前未知，不能直接返回可安全换键重试。
- 待确认 Q12 若采用“封闭原键”，它是明确的受鉴权写动作，必须与接纳竞争同一控制记录：接纳先提交就返回原结果；封闭先提交则所有迟到／旧 fence 接纳被拒绝。不能在 GET 回查中隐式修改状态。
- 首次创建控制记录的竞争、消息已存在而控制记录缺失的异常、事务提交结果不明，都须有回查／修复规则；不能仅对不存在的正式消息做一次锁定读取就宣布形成持久封闭。
- 正式接纳时，控制记录的成功结果、图文消息／素材／Run、暂存绑定及 #20 投影须服从既有同事务协议；所有路径复核语义摘要与当前权限。封闭记录不能按图片 TTL 删除后使旧请求复活；最终保留边界仍须与请求重试有效期一并明确，不在本页新增正式留存策略。

### 3.3 随机确认 token 的加密恢复副本

待确认 Q13 的推荐是：仍随机生成原 token、保存既有 SHA-256 用于校验；额外持久保存 AES-GCM 加密副本。最小结构责任包括密文及认证标签的明确格式、加密格式／算法版本、原加密 keyId、nonce／IV，以及现有确认身份、原十分钟截止时间和消费状态。nonce 长度、标签位数、字节编码和列形态须在后续结构规格明确，本页不生成 DDL。密钥独立于数据库保管，不能随密文写进确认行或日志。

- 每次**加密**在同一 keyId 对应密钥下保证 nonce 唯一；进程重启、并发签发及轮换重加密都不能复用 nonce。重复领取仅解密已存副本，不重新生成 token，不需要为每次读取重新加密。
- 本人通过当前有效登录及 CSRF 校验的专用 POST 领取原 token；返回前复核归属、当前账号／授权／安全／身份版本、原提案、PENDING 状态与原截止时间，解密后核对已有 token SHA-256。响应不应进入缓存；领取端点不调用模型或发送工具操作。
- 刷新返回同一 token，不更换确认、不延长原十分钟、不重置消费状态。原随机 token、摘要、加密副本及原期限须作为同一签发事实一致保存，不能一边已可确认而另一边尚未可恢复。
- 按保存的原 keyId 解密；密钥轮换和联合恢复须能核验仍有效的原确认。原密钥丢失、密文或标签损坏、摘要不符时保持不可确认并进入允许的核对／安全终结，不能从 SHA-256 还原、重新生成或偷偷重签旧 token。既有仅有摘要的行也不能伪装为已具备恢复副本。
- 加密不提供一次性业务保证；既有确认条件消费、真实发送领取及 UNKNOWN 核对继续负责。token 明文、加密副本、nonce／密钥材料均不进投影、普通消息／草稿、审计、URL 或普通日志；加密副本仅保存在受控持久化位置。keyId 可在必要内部诊断中作为非秘密标识使用，不输出密钥值。

## 4. 待确认与待验证边界

Q11 暂存 24 小时、Q12 独立暂存／普通提交控制记录及原键封闭、Q13 随机 token 的加密恢复副本均为候选；MinIO 提供方选择已定。本页未改变原十分钟确认、成功去重、正式图文原子接纳或未知结果规则。后续最小验证包括：TTL／接纳竞争、原键首次插入及迟到接纳竞争、GET 回查无副作用、POST 封闭与回查超时、确认重复领取／双击消费、并发／重启下 nonce 唯一、密文篡改／原密钥缺失／轮换及恢复；DDL 单表检查不能替代这些应用并发与恢复证据。
