# Agent 定义升级后会话如何处理：AgentScope 与 QwenPaw 源码调研

> 核对日期：2026-10-18。AgentScope Java SDK 以 `v2.0.4` 标签所指的提交 `0b6743b263ba8e39eb417e35048026f1e0196548` 为基线；另把当前 `main` 的 Managed Service 文档固定在 `4ee58ec2018970b7dd362543b3639d9f83760a81`，只作后续产品 API 的参考。QwenPaw 固定在 `697aeb669f42f223d060772eb7a313eec78ebd20`。以下为静态文档和源码核对，未运行升级场景集成测试。

## 先区分两种“升级”

- **Agent 定义版本升级**：数字员工的提示词、模型、工具、权限或工作区配置发生变化。本文要解决的是旧会话继续对话时用哪一版定义，以及历史消息与状态如何保留。
- **框架程序升级**：例如 AgentScope Java SDK 从一个依赖版本升到下一个依赖版本，涉及状态序列化或存储表的兼容性。这不等于数字员工发布新版本。QwenPaw 的 `1.x` 会话数据转 `2.0` `AgentState` 是程序数据格式迁移，不是员工定义版本迁移。[QwenPaw 格式加载源码](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/src/qwenpaw/agents/react_agent.py#L383-L450)

## 结论

1. **AgentScope Java SDK `v2.0.4` 没有替业务决定定义升级后的 Session 归属。** `ReActAgent` 每次调用按 `RuntimeContext` 的 `(userId, sessionId)` 找 `agent_state`。已有状态直接返回；状态字段没有发布版本，读取路径也没有定义版本匹配检查。若新版 Agent 实例沿用同一状态后端和同一标识，旧状态会被读到；新版实例自己的提示词、模型和工具配置会参与后续调用。最后一句是由读取与调用源码推得的行为，具体工具兼容及安全性仍须针对版本变更验证。[状态加载](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L421-L446)、[调用时激活状态](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L658-L704)、[状态字段](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/state/AgentState.java#L42-L68)、[实例配置和模型调用](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L330-L355)
2. **较新的 AgentScope Managed Service 提供了另一种、明确的产品语义。** 其固定提交的 API 文档说：创建 Session 时可指定 Agent `version`；省略时解析当前版本并冻结到该 Session，后续 Turn 沿用冻结目标。它还提供定义版本列表和按版本读取。[官方 Managed Agents 文章](https://github.com/agentscope-ai/agentscope-java/blob/4ee58ec2018970b7dd362543b3639d9f83760a81/docs/v2/en/blogs/managed-agents-agentscope-rumtime.md#L310-L343)进一步说明：Agent 更新创建新版本，旧 Session 可继续记录并恢复**当前支持的历史字段**；Session 创建时记录版本，运行时按版本与环境等构建 Agent。文章也坦承当前运行时只部分重建历史定义字段，因此不能把这句话扩展为“任意历史版本均完整兼容”。这里是 `main` 的 *Managed Service 控制面和数据面*，不能倒推为 Java SDK `v2.0.4` 已有的 API，也不能证明本项目已部署该服务。[当前 Service API 文档](https://github.com/agentscope-ai/agentscope-java/blob/4ee58ec2018970b7dd362543b3639d9f83760a81/docs/v2/en/service/api-reference.md#L29-L69)、[同一文件在 v2.0.4 的旧版内容](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/docs/v2/en/service/api-reference.md#L30-L62)
3. **QwenPaw 是 Python AgentScope 应用，不是 AgentScope Java 的标准契约。** 当前依赖 `agentscope[model-ollama]==2.0.10`；每个 Agent 有独立工作区、配置和对话历史。前端保存配置会安排新 Workspace 实例替换；磁盘 watcher 只对渠道和心跳配置变化触发此替换。替换时已在执行的任务留在旧实例，新请求由新实例处理；会话状态文件仍以当前 Agent 工作区加 `(sessionId, userId, channel)` 寻址。已检查的路径没有把 `ChatSpec` 绑定到不可变的 Agent 定义版本，也没有在配置变更时按定义版本自动创建新业务会话。[依赖](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/pyproject.toml#L1-L16)、[多 Agent 文档](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/website/public/docs/multi-agent.en.md#L1-L30)、[热重载](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/src/qwenpaw/app/multi_agent_manager.py#L551-L704)、[watcher](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/src/qwenpaw/app/agent_config_watcher.py#L175-L244)、[ChatSpec 字段](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/src/qwenpaw/app/chats/models.py#L101-L164)

## AgentScope Java SDK `v2.0.4`：旧状态会发生什么

`ReActAgent` 的 builder 保存 `sysPrompt`、`model`、`toolkit` 等实例配置；每次调用从运行上下文取得用户和会话 ID，在状态后端读取 `agent_state`。找到记录后，`loadOrCreateAgentStateForSlot` 直接返回该记录；只在没有记录时生成新 `AgentState`。`AgentState` 保存对话、摘要、权限、工具与任务上下文等，但未携带数字员工定义版本。[Builder 与配置](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L330-L355)、[读取分支](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L421-L465)、[AgentState](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/state/AgentState.java#L42-L110)

源码中的 `VersionedState.version()` 和 `saveIfVersion(...)` 是**状态存储记录的并发控制版本号**，用于检测同一槽位的覆盖冲突；它不是数字员工定义的发布版本，也不会决定此会话应运行哪一版 Agent。[存储接口](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/state/AgentStateStore.java#L63-L137)、[读取与保存](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L421-L446)

**推论**：如果新版实例仍指向同一存储槽，旧对话上下文和旧的工具/权限状态可能与新版系统提示词、模型及工具定义共同作用。源码显示系统提示词来自当前实例，模型与工具 Schema 也来自当前实例；是否有某个插件自行做兼容检查，需要另查该插件。[系统提示词生成](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L769-L783)、[模型输入和工具 Schema](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L2403-L2450)

官方同版本的直接使用文档只说明：稳定 `(userId, sessionId)` 可在新 Agent 实例加载同一状态；没有给出“定义升级后旧会话自动归档、自动迁移或绑定旧定义”的 SDK 策略。`HarnessAgent` 封装了此类调用，并可把默认状态目录放在 `~/.agentscope/state/<agentId>/`，但若显式共用后端或路径，不能只依赖目录默认值完成版本隔离。[SDK 状态文档](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/docs/v2/en/docs/building-blocks/agent.md#L490-L533)、[Harness 默认状态目录](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-harness/src/main/java/io/agentscope/harness/agent/HarnessAgent.java#L1122-L1141)

## 对本项目 Q18 的已确认规则与待细化点

本项目已有“数字员工发布版本不可变、运行可追溯”的业务前提。用户于 2026-10-18 进一步确认：**发布 V2 不会自动使 V1 Session 只读；仅当用户针对某条 V1 Session 显式选择“在新版继续”时，那条旧 Session 才转为只读。** 其他 V1 Session 仍绑定 V1，其能否继续发起 Run 还受旧版本可用状态等既有规则约束。切换时由平台创建绑定 V2 的新业务 Session 和独立框架状态槽；原 Session、消息及原框架状态保留，在新会话元数据中记录来源旧 Session ID，页面提供“查看旧对话”入口。用户又确认：**切换时自动把旧会话全部对话消息带入 V2 模型**，不先做摘要，也不逐条征求确认。“对话消息”指用户与数字员工的消息及其图片、音频、文件等多模态素材；旧版系统指令、工具调用与工具结果不在导入范围内，仍留在旧会话审计记录中。因此新旧会话的引用关系之外，还需要一条实际的消息导入流程；它应保留来源消息 ID 与内容引用，不能仅复制旧框架状态。多模态素材可用性仍待细化；超出模型上下文窗口时的规则见下文。以上是**本项目业务规则及其设计映射**，不是 AgentScope Java `v2.0.4`、Managed Service 或 QwenPaw 的自动行为。[SDK 状态键](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L421-L446)、[Managed Service 冻结版本](https://github.com/agentscope-ai/agentscope-java/blob/4ee58ec2018970b7dd362543b3639d9f83760a81/docs/v2/en/service/api-reference.md#L29-L41)、[Managed Agents 文章的继续范围](https://github.com/agentscope-ai/agentscope-java/blob/4ee58ec2018970b7dd362543b3639d9f83760a81/docs/v2/en/blogs/managed-agents-agentscope-rumtime.md#L312-L343)

QwenPaw 式沿用原 Session 会在配置更新后由新实例读取旧状态。本项目已选择“显式在新版继续时创建新 Session”，因此不能把 QwenPaw 的原地沿用当作本项目的升级流程；它仍可作为运行中任务切换与历史保存的参考。[QwenPaw 热重载](https://github.com/agentscope-ai/QwenPaw/blob/697aeb669f42f223d060772eb7a313eec78ebd20/src/qwenpaw/app/multi_agent_manager.py#L551-L704)、[SDK 读取逻辑](https://github.com/agentscope-ai/agentscope-java/blob/0b6743b263ba8e39eb417e35048026f1e0196548/agentscope-core/src/main/java/io/agentscope/core/ReActAgent.java#L421-L446)

用户于 2026-10-18 进一步确认：若旧 Session 尚有运行中的 Run 或待确认的写操作，先完成或取消 Run，并处理待确认操作；这些事项进入终态后才允许执行“在新版继续”。切换应在平台侧把旧会话转只读与新会话创建作为同一业务动作处理，避免旧会话已锁定但新会话未建立，或重复点击产生多个新会话。这里的原子性与幂等实现仍须在业务 Session 设计中细化。

用户同日确认**切换当下严格全量**：若全部旧对话消息超过 V2 模型可接收的上下文，暂不切换、旧 Session 保持可用，并提示历史超限；不得在这次切换中悄悄截断或压缩消息。后续普通对话可使用 AgentScope Harness 自带的对话压缩，不另造压缩算法。`v2.0.4` 文档证实 `CompactionConfig` 可在阈值触发时把旧对话前缀压成摘要、保留尾部；模型返回上下文溢出时的强制压缩重试，需要显式配置 `.compaction(...)`。这压缩的是**模型可见上下文**，不等同于原始业务消息，也不能代替切换时的全量校验。实现时还须核实压缩触发时机，保证首次 V2 模型输入满足“严格全量”，之后才按已配置策略压缩。[v2.0.4 记忆与压缩文档](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/docs/v2/zh/docs/harness/memory.md#L20-L30)、[压缩配置与溢出恢复](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/docs/v2/zh/docs/harness/memory.md#L64-L91)

用户随后补充：正常续聊时希望模型上下文使用量达到**约 80%**即自动触发框架压缩。这里的 80% 是**触发阈值**，不是“压缩后保留 80% 原文”。`v2.0.4` 的 `CompactionConfig` 没有直接的触发百分比字段：`triggerTokens=0` 采用 `contextWindow - reserved`，默认 `reserved=20_000`；`triggerMessages` 默认 50，也会独立触发压缩；`keepTokensRatio` 用于确定压缩后保留尾部的 token 预算，不能拿它表示触发比例。因此要按实际模型上下文窗口换算约 80% 的 token 阈值，并避免条数阈值抢先触发。框架在模型推理前检查压缩条件，故首次 V2 调用仍须优先满足“严格全量”：若全量输入可容纳但已超过 80% 的普通续聊阈值，本次切换不能让压缩中间件提前改写它；首轮完成后再启用正常的约 80% 阈值。这里是基于两项已确认业务规则的**实现约束**，具体配置方式和模型 token 估算须做运行验收。[CompactionConfig 字段与默认值](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-harness/src/main/java/io/agentscope/harness/agent/memory/compaction/CompactionConfig.java#L151-L210)、[Builder 字段](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-harness/src/main/java/io/agentscope/harness/agent/memory/compaction/CompactionConfig.java#L273-L339)、[阈值计算与推理前压缩](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-harness/src/main/java/io/agentscope/harness/agent/middleware/CompactionMiddleware.java#L80-L114)、[动态阈值计算](https://github.com/agentscope-ai/agentscope-java/blob/v2.0.4/agentscope-harness/src/main/java/io/agentscope/harness/agent/middleware/CompactionMiddleware.java#L155-L217)

按“严格全量”规则推导：若所需图片、音频、文件等素材无法读取或无权读取，本次切换也不能视为成功；旧会话应保持可用并提示具体缺失。**待设计与验收**：素材持久保存和访问授权、切换前的模型输入大小校验、真实模型拒绝时的回滚边界，以及首次 V2 调用如何避免被框架阈值提前压缩。若旧版因安全原因停用，之前确认的“禁止新 Run、历史可查看”仍可独立生效。
