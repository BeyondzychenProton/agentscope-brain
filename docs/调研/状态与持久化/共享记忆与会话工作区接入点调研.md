# 共享记忆与会话工作区接入点调研

> 对应 [Issue #7](https://github.com/BeyondzychenProton/agentscope-brain/issues/7)。核对日期：2026-10-20。以下是一手源码的静态核对，固定到 AgentScope Java 提交 [`0b6743b263ba8e39eb417e35048026f1e0196548`](https://github.com/agentscope-ai/agentscope-java/tree/0b6743b263ba8e39eb417e35048026f1e0196548)，该提交可读取。本文不选定本项目物理后端、不实现适配器，也不表示隔离、并发或删除恢复已经验收。

## 1. 本次要回答的问题

本轮已确认：用户可整份查看、修改、清空个人偏好文档；不同 Session 可并行，同 Session 只允许一个活动 Run；会话运行文件默认只供本会话，跨会话须显式引用；清空禁止旧日志、摘要和排队任务恢复既有偏好，但允许之后的新输入重新学习。

因此需核对：框架能否把共享偏好与会话文件送入不同命名空间，以及原生写入是否能阻止用户修改前的异步结果覆盖新文档。

## 2. Memory 和文件工具确实共用文件系统，但路由可扩展

Harness 构建一个 `WorkspaceManager`，交给 Workspace 上下文、Memory Flush、合并及记忆工具；普通文件工具使用同一个 `AbstractFilesystem`。内置 Memory hooks 也沿用主文件系统的 `IsolationScope`。未发现分别配置 `memoryFilesystem`、`memoryIsolationScope` 的 builder 入口。[构建与 hooks][harness-wiring]、[工具注册][harness-tools]

可用接入点有 `abstractFilesystem(AbstractFilesystem)`、`filesystemRoute(prefix, AbstractFilesystem)`，后者构建额外的 `CompositeFilesystem` 路由；还可添加自定义 middleware。它们是扩展能力，不是已经完成的共享 Memory 与会话隔离适配。[文件系统注入与路由][harness-routes]、[自定义 middleware][harness-middleware]

路由对 Memory 实际生效，调用链如下：

```text
读取 MEMORY.md / 日记
  WorkspaceManager -> filesystem.read(rc, 工作区相对路径)
追加日记 / 覆盖 MEMORY.md
  WorkspaceManager -> filesystem.uploadFiles(rc, 工作区相对路径)
  -> CompositeFilesystem 先按路径选 backend
  -> 所选 backend 收到原 RuntimeContext，再解析自己的 namespace
```

`WorkspaceManager` 这些读写方法不会先把 Session namespace 拼到 `MEMORY.md` 或 `memory/...` 前面。`CompositeFilesystem` 原样转交 `RuntimeContext`；`RemoteFilesystem` 的 namespace factory 在每次操作时运行。因此路径路由可连接采用另一套 namespace factory 的后端，不能据主 scope 为 `SESSION` 就断言共享 Memory 路由无法接入。[Workspace 读取][workspace-read]、[Workspace 追加][workspace-append]、[Workspace 覆盖][workspace-write]、[Composite 读写][composite-read]、[Composite 上传][composite-upload]、[动态 namespace][remote-namespace]

这只证明读写链路有接入点。路径匹配、枚举/搜索、工具权限、版本映射及共享记忆任务协调仍需组合验证。

## 3. RemoteFilesystemSpec 的默认 namespace 与 MySQL 能力

默认共享路由包括 `MEMORY.md`、`memory/`、Skills、Session 日志及任务；每类增加独立的 route segment，但这些默认路由共用该 spec 的一个 scope。`USER` 默认生成 `[agents, agentId, users, userId, routeSegment]`；`SESSION` 则生成 `[agents, agentId, sessions, sessionId, routeSegment]`。所以只把 spec 改为 `SESSION`，默认 Memory 也会按 Session 分开；不会自动同时满足跨 Session 共享偏好。[默认路由及 namespace][remote-spec]

`RemoteFilesystem` 可直接接收 `BaseStore` 与自定义 `NamespaceFactory`。`BaseStore` 以 namespace 加 key 寻址，提供 `get/put/delete/search` 和可选 `putIfVersion`，默认 CAS 实现总返回 `false`；接口未提供多 key 事务。[动态 namespace][remote-namespace]、[BaseStore 契约][base-store]

官方 `JdbcStore` 实现 `BaseStore`，声明支持 MySQL 等方言，并实现服务端条件更新。各方法单独取得 JDBC Connection；不能由“使用同一个 MySQL”推导多文件与平台业务表处于同一事务。本次仅证明有候选后端，没有核对本项目数据库配置、DDL 或恢复结果。[JDBC 实现][jdbc-store]

文件写入语义也有区别：`RemoteFilesystem.write` 使用 CAS 创建，`edit` 使用版本 CAS 重试；`uploadFiles` 使用无条件 `put`。`WorkspaceManager` 的追加和覆盖走 `uploadFiles`；追加只有该 manager 内的路径锁，没有跨副本 CAS。因此底层支持 CAS，不等于 Memory 合并已经受到内容 CAS 保护。[Remote 写入][remote-cas]、[Remote 上传][remote-upload]、[Workspace 追加][workspace-append]

## 4. 用户修改和清空仍需平台协议

`MemoryFlushMiddleware` 在响应完成后异步执行，同隔离 key 有进程内 Flush 队列；排队任务执行时再读取 AgentState 的当前上下文。该队列不是用户编辑锁，也没有在这条调度/执行链路中校验平台“记忆代次”或业务 Run 成功状态。[Flush 队列与输入][memory-flush]

`MemoryConsolidator` 读取当前 `MEMORY.md` 与日记，等待模型输出后整份覆盖。其 `BaseStore` CAS 用于合并 watermark，不是 `MEMORY.md` 内容版本；本次检查的合并提交点没有用户编辑版本检查。旧任务覆盖新文档的窗口不能靠 watermark CAS 排除。[合并与提交][memory-consolidate]、[watermark 写入][memory-watermark]

另有清空细节：`WorkspaceManager.readWithOverride` 在文件系统读取结果为空字符串时回退到本地工作区模板。因此写入空文档不等于读取必然为空；本地 `MEMORY.md` 模板和 overlay 基线也要纳入核验。[空内容回退][workspace-fallback]、[Remote overlay][remote-spec]

已有扩展入口包括自定义文件系统、路由及 middleware，也可关闭内置记忆 hooks/tools；没有查到可直接满足“用户手改优先、旧任务禁止回写、只从清空后的新输入学习”的专用删除协议。关闭开关本身不证明全部提炼路径、旧上下文或工具写入已经受控；压缩内嵌提炼等路径尚需接入时核查。[关闭开关][harness-disable]、[文件系统注入与路由][harness-routes]

## 5. 接入时需要补齐的证据

- 两个 Session 并行时，共享偏好可读，运行文件不能通过读、列举、搜索、下载或猜测路径越界。
- 用户保存/清空与旧 Flush、旧合并交错时，旧结果不能提交；之后新输入可提炼，新输入不携带旧上下文中的已删除事实。
- 空文档、删除上层文件、本地模板与 overlay 回退均符合清空语义。
- namespace 中的员工、发布版本、会话和记忆代次如何映射，由后续规格决定，并以实际适配测试验证；本文不把可行接入点写成既定存储方案。

本次研究后的项目选择已由用户确认，见[状态、记忆与工作区隔离存储设计规格](../../数据库设计/状态记忆与工作区/状态记忆与工作区隔离存储设计规格.md)；本调研保留框架事实及静态证据边界。
